## 1. 产品定位与四条铁律

### 1.1 一句话定位
**COOLFLY 客服知识的唯一生产地。** 知识在这里写、在这里审、在这里翻译、从这里一键上线到 Zendesk 帮助中心，上线后的效果再回流到这里指导下一次修改。

### 1.2 边界（用户会问的三个问题，界面要能自己回答）
| 问题 | 答案（写进界面引导文案） |
|---|---|
| 客户在哪看到这些内容？ | Zendesk 帮助中心 + Zendesk AI 客服机器人。本台负责生产，不负责接客 |
| 工单量、客服人效在哪看？ | Zendesk Explore。本台只看**知识的效果**（有没有被引用、有没有解决问题） |
| 能不能直接在 Zendesk 改文章？ | 能，但不该。改了本台会检测到并提醒你「有人在外面动了这篇」 |

### 1.3 四条铁律（产品硬约束，不可通过任何配置绕开）

| 铁律 | 用户能感知到的表现 |
|---|---|
| **⓪ 本台是唯一权威源** | 知识只在本台生产与修改，单向推送 Zendesk；Zendesk 侧被直接改写会被检测并生成「有人在外面改了这篇」待办，由主编处置（覆盖 / 收回来 / 挑几段收回来） |
| **① 都得过审** | 任何内容——手写的、AI 挖的、批量导进来的、从 Zendesk 拉回来的——都必须走「审」这一步才能上线。界面上不存在任何「直接发布」入口 |
| **② 英文必须人看过** | 英文没人点过「校对完成」，「上线」这一步的按钮就不会出现（改为显示「还差：英文没人校对」+ 跳转） |
| **③ 一切留痕** | 谁、什么时候、改了什么、改前改后，全部记下且**任何人不能删**。界面上没有删除日志的入口 |

> 注：原「四眼原则」（不可审核自己提交的条目）已于 08-05-2026 由用户拍板取消——自审合法但全程留痕（含提交人与审核人为同一人的情形）。单人模式（§2.2）与此一致。

### 1.4 两层界面（本版核心结构）

| 层 | 页面 | 文案基调 | 服务对象 |
|---|---|---|---|
| **工作流面** | 今日待办 P1 / 知识资产 P2 / 知识详情 P3 / AI 建议 P4 / 向导 W1–W4 | 零术语、系统派活、一屏一事 | 每天写知识、审知识的人 |
| **专业面 ★** | 同步·Zendesk P10 / 效果数据 P5 / 操作留痕 P7 / 设置 P8 / 高级权限（§2.3）/ 技术视图（§12.7）/ 列设置 | 精确术语 + 人话注解、表格化、批量操作 | 排查问题、治理数据、管连接的人 |

两层通过**待办卡与深链**衔接：工作流面出事（推送失败、冲突），待办卡给一句人话 + 主按钮，点进去落到专业面的对应行。

## 2. 角色与权限（3+1 预设 + 高级矩阵）

### 2.1 四个预设角色

| 角色 | 一句话定位 | 能做 | 不能做 |
|---|---|---|---|
| **编辑**（Editor，原"知识管理员"） | 写知识的人 | 写 / 改 / 建目录（含 Zendesk 结构联动）/ 处理 AI 建议 / 送审 / 校对英文 | 审核、上线、回滚、下架 |
| **主编**（Publisher，原"知识审核员"） | 把关和上线的人 | 编辑的一切 + 审核 + 上线 + 回滚 + 下架 + 处理 Zendesk 冲突 + 同步重试 | 管成员 |
| **数据观察员**（Analyst，原"AI 运营"）★专业面 | 看数据、提建议的人 | 看全部内容与数据（只读）/ 提优化建议（进审核队列） | 改任何内容、审核、上线 |
| **管理员**（Admin，原"系统管理员"） | 管人和看账的人 | 管成员 + 高级权限 + 看全量留痕 + 看数据 + 系统设置 | 不参与内容编审与上线（可看不可动） |

> v2.1 曾把角色砍成 3 个并删除权限矩阵界面。本版恢复为 **4 个预设角色卡 + 高级矩阵**：日常用户只见角色卡（选卡即完成授权），矩阵收进管理员的「高级」里——认知负担靠收纳解决，不靠砍功能解决。

### 2.2 单人模式（Solo Mode）
- 场景：团队只有 1–2 人，主编就是编辑本人。
- 开关位置：`运营中心 → 设置 → 团队与分工`，选「就我一个人 / 小团队（2–5 人）/ 分工明确（6 人以上）」。
- 选「就我一个人」时：**审这一步不消失，但允许自审**，界面提示「你既是作者也是主编，这次审核会记在留痕里」。铁律①不破。
- 选「分工明确」时：可在设置里给「审 / 译 / 发」三步各指派默认负责人，待办自动派到人。

### 2.3 高级权限：权限矩阵（管理员 · 默认收起）★专业面
- 位置：`运营中心 → 成员与分工 → 高级：权限矩阵`（默认收起，展开需点一次并显示说明「99% 的团队用角色卡就够了」）。
- 内容：**10 权限项 × 4 角色**矩阵（新建编辑条目 / 提交审核 / 审核与驳回 / 上线到 Zendesk / 版本回滚 / 管理目录章节 / 查看效果数据 / 提交优化建议 / 成员与权限管理 / 查看全量留痕），仅管理员可点格修改，每次修改写留痕。
- 角色卡 = 矩阵的预设模板；某角色被改出预设后，其角色卡标「已自定义」并给「恢复默认」入口。
- 不做的事：不允许新建角色、不允许新增权限项（见 §17）。

### 2.4 界面权限表现（G3/G4 的补充）
- 不能做的功能**直接不出现在界面上**（不是置灰）。
- 唯一例外：审核相关按钮对编辑显示为**信息条**「这一步等主编 <姓名> 处理，已通知」，让编辑知道卡在哪。
- 数据观察员打开编辑器时整体只读，顶部一行「你现在只能看。想改的话，可以提个建议。」+ `提建议` 按钮（建议进审核队列，来源标「优化建议」）。

## 3. 核心心智模型：五步流水线

### 3.1 五个字
```
  写  ─────▶  审  ─────▶  译  ─────▶  发  ─────▶  盯
 起草内容    主编把关    英文校对    推上 Zendesk   看效果·到期复核
  编辑        主编        编辑        主编         系统 + 全员
```

- 五步**固定不可配置**，用户只需记住这五个字。
- 每步的「谁来做」可指派（§2.2）。
- **异常不是第六步**，而是贴在卡片上的两枚贴纸：`被退回`（审这一步没过）、`已下架`（发过又撤了）。
- 「盯」这一步是**常驻的**——上线后条目永远处在「盯」，直到被改动重新进入「写」。
- 与既有状态机的映射（后端不重写状态，只加派生字段，见 §15）：写=草稿/编辑中/已驳回；审=待审核/审核中；译=英文待校对（审核通过后触发）；发=审核通过待上线/推送中；盯=已发布。

### 3.2 五步进度条组件（全局强制，G5）
```
 ①写 ━━●━━ ②审 ────  ③译 ────  ④发 ────  ⑤盯
 └ 已完成    └ 进行中（等主编 王琳 · 已等 2 天）
```
规格：
- 已完成步：实心绿 + `✓`；进行中步：实心青蓝 + 脉冲点；未开始步：空心灰。
- 进行中步下方一行小字：**「等谁 · 等了多久」**（超过 3 天变黄，超过 7 天变红并自动生成催办待办）。
- 有异常贴纸时，进度条右端追加红/灰贴纸，点击展开原因。
- 组件三种尺寸：`lg`（详情页顶部）/`md`（看板卡片）/`sm`（列表行内，只显示 5 个点）。

### 3.4 版本模型：一篇 · 多版 · 双语

> **统计口径、回滚策略、改动对照、双语状态，全都挂在「条目 + 版本」上**。

#### 3.4.1 三层对象

```
知识条目（Entry，永久 id，客户看到的那篇文章）
  └─ 版本（Version v1, v2, v3 …  只增不改不删）
        ├─ 中文内容（段落数组，每段有稳定段落锚点）
        ├─ 英文内容（与中文按段落锚点一一对应）
        ├─ 信息快照（放在哪 / 谁能看 / 客户会怎么问 / 适用型号 / 体检周期 …）
        └─ 效果数据（该版上线期间累计：引用、命中、解决、采纳、被踩、样本量）
```

| 规则 | 说明 |
|---|---|
| **版本是快照，不是补丁** | 一个版本 = 中文 + 英文 + 全部信息字段的完整快照，任意两版可直接对照（含信息改动） |
| **中英同版** | 英文不单独编版本号。中文改了，同版英文进入「要重看」 |
| **只增不减** | 版本永不删除、永不覆盖。回滚也是**新增一版**（§10.4） |
| **一次上线冻结一版** | 只有「发」成功推到 Zendesk 才把草稿冻结为正式版本并开始计效果数据；写作/审核期间的自动保存不产生版本号 |
| **效果数据归属版本** | 每一次引用/解决/点踩都记在「当时线上是哪一版」上，这是回滚决策的唯一依据 |

#### 3.4.2 版本状态（用户可见的四种）

| 状态 | 界面说法 |
|---|---|
| current | **客户现在看到的就是这版**（有且只有一版） |
| history | 第 N 版（已被替换），保留全部内容与效果数据 |
| draft | 正在改的（还没上线），基于 current 派生 |
| rolled_back | 这版被撤下了（曾上线、因效果差被回滚，卡片带灰色贴纸） |

#### 3.4.3 版本号出现在哪里（强制）

### 5.3 文案规范

| 场景 | 规则 | 例 |
|---|---|---|
| 主按钮 | 动词 + 宾语，≤6 字 | ✅「送去审核」❌「提交」 |
| 空态 | 「一句话现状 + 一句话建议」 | 「还没有待办 —— 去看看 AI 发现的 12 个新话题？」 |
| 报错 | 「发生了什么 + 你能做什么」，不出现错误码 | 「推送到 Zendesk 失败了：对方服务暂时没响应。可以点重试，或等 5 分钟系统自动再试一次。」 |
| 阻塞 | 「还差什么 + 去哪补」 | 「还差 1 件事：英文还没人校对 → 去校对」 |
| 危险确认 | 后果写具体，不写「此操作不可撤销」空话 | 「下架后：客户搜不到这篇了；Zendesk 上会归档不会删；历史和数据都还在；想再上线，改完重新走一遍审核即可。」 |
| **语气分寸** | 专业、克制。emoji 仅用于区块图标（🔥📋✨），不进正文句子；不用「干得漂亮」「太棒了」类夸奖话术；成就感靠「今天已完成 4 件」这类事实陈述传达 | v3.0 修订：内部专业工具不卖萌 |

#### 6.3.4 「还差 N 件事」卡（`MissingList`，G3）
- 只在**当前用户下一步动作被阻塞**时出现，位于头部下方。
- 每条格式：`✗ <人话缺什么>` + `去处理 →`（跳到对应位置并高亮）。
- 三项体检对应人话：
  - 字段没填全 → 「还没说清楚放在哪 / 客户会怎么问」
  - 内部内容没标 → 「有段落是内部口径但没标出来，会漏给客户看到」
  - 英文没校对 → 「英文还差 N 段没人校对」/「英文标题还空着」
- 全部通过时不显示这张卡，改为在主按钮旁一行绿字「体检通过，可以上线」。

#### 6.3.6 侧栏「这篇的信息」（字段减负）
只保留用户要拍板的，其余 AI 填或系统算：

| 字段 | 谁填 | 交互 |
|---|---|---|
| 放在哪（库 › 目录 › 章节） | AI 建议 + 人确认 | 级联下拉，AI 建议项带 ✨ 标 |
| 谁能看 | 人 | 三选一大按钮组：`所有人` / `只有客服` / `大部分公开，少数内部`（选第三项时提示去正文标 🔒） |
| **客户会怎么问** | ✨AI 生成 4–6 条，人可增删 | 标签串（§13.3）。替代旧版「场景一级/二级 + 标签」三个字段——用户想不出分类，但说得出客户怎么问 |
| 适用型号 | 人（默认全型号） | 多选 |
| 要不要英文版 | 人（默认跟随全局设置） | 三选一：`跟随默认` / `要` / `只发中文`（§11.5） |
| 时效性 | 人（默认长期有效） | 二选一：`长期有效` / `有时限` + 失效日期（到期前 7 天自动生成待办，§13.4） |
| 多久体检一次 | 人（默认 180 天） | 三选一：90 / 180 / 365 天 |
| 谁负责这篇 | 人（默认创建者） | PersonPicker |
| 场景（一级/二级） | **系统派生，只读** | 直接等于「目录 › 章节」，灰字展示「统计时算作：售后与退款 / 退货政策」（§13.2） |
| 也会在这些场景被问到 | 人（可空，≤3 个） | 次要场景多选，只影响统计与推荐，不影响存放位置和 Zendesk 结构（§13.2） |
| 一句话摘要 | ✨AI 生成 | AIBlock，`我改改` 后不再被覆盖，显示「你改过，AI 不会再动它」。用途注明：本台重复检查的比对基准 |
| 来源 | 系统 | 只读徽章：手写 / AI 发现 / 批量导入 / Zendesk 收回 |

> 侧栏所有字段**随版本快照**：改了目录、改了「谁能看」、增删了问法标签，都会出现在改动对照的「信息改动」区（§12.3），并需要过审。

- 默认展示最近 10 版，其余折叠；历史最佳的那一版永远置顶固定显示一行「🏆 到目前为止表现最好的是第 2 版」。
- 每张卡片：版本号 + 谁 + 何时 + 动作类型贴纸（首发 / 例行修改 / 按 AI 建议改的 / 从 v2 换回来的 / Zendesk 冲突合并 / 批量导入）+ AI 改动摘要 + **该版效果** + 两个按钮。
- 效果行受样本量保护：样本 <30 时不显示百分比对比，改显「才上线 3 天，数据还不够（已积累 12 次）」。
- 勾选任意两版 → `对比这两版` → 全屏 DiffView（M7，§12）；只点单张卡的 `看改了哪里` = 与前一版对比。
- `把这版换回去`（仅主编）→ M8 回滚确认（§10.4）。编辑看不到此按钮，改为一行信息条「觉得老版更好？告诉王琳 →」。
- 页签底部挂「这篇的全部留痕」（非上线类操作：送审、退回、改目录、改负责人、认领审核……含字段级前后值），与版本时间线分开，避免混淆「版本」与「操作」。

#### 6.3.8 页签「效果」（按版本看）

顶部一行口径开关：`看当前版（v3）`（默认）/ `看历史全部` / `按版本对比`。这一行是回滚决策的入口，不可省。

- 四个大数字卡：被引用次数 / 命中率 / 解决率 / 采纳率，每个带一句人话解释（如「客户问相关问题时，有 78% 的情况找到了这篇」），数字下方标明统计口径「第 3 版上线至今 3 天」。
- `按版本对比` 模式：一张折线图，横轴按版本分段（每次上线画一条竖虚线并标 `v3 上线`），一眼看出「哪次改动把数据改差了」；下方配 `VersionCompareBar`（§10.3）。
- 样本 <10：整块替换为「刚上线不久，数据还不够，再等等」+ 已积累样本数。
- 解决率 <60%：顶部红条「这篇效果不太好」+ 三条 AI 给的可能原因 + `照建议修改`。
- 新版不如老版时（判定见 §10.3）：顶部红条换成「改完之后反而变差了：第 3 版 61%，第 2 版 78%」+ `看改了哪里` / `把 v2 换回去`。
- 「客户反馈原声」列表：被踩、客服标记、追问原文摘录（每条带来源渠道 + **当时是哪一版** + 信号确定性说明，hover 显示「这类信号是<档位>：<解释>」）。原声展示前统一脱敏（§13.5）。

│ 上次退回意见（1 条，已折叠 ▾）                              │
│ 上线体检：✓ 信息填全了  ✓ 内部内容标好了  ✗ 英文还没校对    │
│ ─────────────────────────────────────────────────────────  │
│              [通过]        [退回改改]                       │
└─────────────────────────────────────────────────────────────┘
```
- **打开即认领 ★**：主编打开审核浮层，条目进入「审核中 · 王琳在审」，其他主编的待办卡与看板卡同步显示，防止两人重复审同一条；重复打开不报错，显示「你正在审这条」。
- 头部带 **来源徽章**（手写 / AI 发现 / 批量导入 / Zendesk 收回 / 优化建议），批量导入与 AI 类来源附证据入口（原对话 / 原文档片段）。
- `通过`：直接过 + 撤销条；若体检全绿且我有上线权，通过后顺手问一句「要现在就上线吗？」`马上上线` / `待会儿再说`。
- `退回改改`：展开理由输入（**必填**，placeholder 给范例「例如：计费周期与财务口径不符，请附财务确认截图」）+ 可选「勾出有问题的段落」（在改动对照上圈选，退回后作者看到高亮）→ 退回后自动生成作者的待办。
- **历史意见可见**：重新提交的条目，浮层显示「上次退回意见」折叠区，审核者不用去翻留痕。
- 自审时（单人模式或主编改自己的稿）：顶部一行「这是你自己写的，直接过也行，会记在留痕里」。
- **信息改动必须单独呈现**：正文没改但改了目录/可见性/问法标签，也要能审——独立区块列出「改前 → 改后」。
- 审核意见支持**挂在段落上**（在改动对照里选中某段 `留个意见`），退回后作者在编辑器同位置看到批注气泡。

#### 6.4.2 建议卡四类（v3.0 恢复第 4 类）

| 类型 | 触发来源 | 主按钮 | 采纳后 |
|---|---|---|---|
| 📝 **该写新的** | 对话里高频出现（≥10 次/周）且重复检查未比中 | `用这个草稿开写` | 带 AI 草稿进入 W1 向导第 2 步，来源标记「AI 发现」 |
| 🔧 **该改现有的** | 文章被踩 / 客服标记 / 对话里出现与文章冲突的说法 / 解决率跌破 60% | `去改这篇` | 打开该条目详情并进入「写」，AI 意见以批注形式挂在相关段落旁 |
| 🔍 **标题不好搜** | 帮助中心搜索无结果关键词，但库里其实有对应内容 | `改个好搜的标题` | 打开条目，AI 建议的新标题与「客户会怎么问」预填在侧栏，一键采纳 |
| 🧬 **重复合并 ★** | 重复检查发现两篇既有条目高度相似（≥0.85）或新话题与既有条目撞车 | `去合并` | 打开 M9 合并面板（§6.4.6）；合并产物进审核，另一篇过审后在 Zendesk 归档并重定向 |

#### 6.4.3 卡片必备三要素（可信度设计）
1. **AI 为什么这么判断**——必须写清依据，且**按三重准入逐条列出**：①被问了多少次（频次）②重复检查结果（相似度 + 比中哪篇 + 判定理由）③缺口/冲突判定。
2. **客户原话**——至少 2 条真实摘录（脱敏后），可展开全部，点击可跳 Zendesk 原工单。
3. **一键可用的产物**——不是只给结论，要给草稿/新标题/合并预览，用户点一下就能用。

#### 6.4.4 交互规则
- `不用了` = 直接消失 + 撤销条；**同一话题下次达到阈值会再出现**（卡片底部小字注明，避免用户以为永久删了）。丢弃动作留痕。
- 采纳率统计显示在页头（「你采纳了 68% 的建议」），低于 30% 时页头出现一行：「建议不太准？告诉我们哪里不对 →」收集反馈。
- AI 不可用时（模型没配/失败）：整页顶部诚实告知——「AI 分析暂时不可用（<原因>），下面是按关键词粗略统计的结果，仅供参考」，不假装正常。
- `重新分析`：手动触发，按钮上标注上次分析时间；执行中显示进度「正在读取 47 通对话… 12/47」。

#### 6.4.5 四态
- 空：「AI 还没发现值得做的事——说明现有知识覆盖得不错」+ 副行「下次分析：今晚 6 点」+ 次按钮 `立即分析`。
- 空（从未跑过）：「还没连上客服对话数据」+ `去设置里连接 Zendesk`（管理员）/「让管理员配置一下」（其他角色）。
- 加载：3 张骨架卡。
- 出错：错误态 + 重试 + 「上次成功的结果（3 天前）」入口。

- 首次登录：整卡替换为「先设个你自己的密码」+ 新密码（≥8 位）+ 强度条 + 主按钮 `设好了，开始用`。
- 首次进入主界面时自动弹 60 秒引导：三屏动画讲清「五步流水线 / 系统会派活给你 / AI 会帮你写」，可跳过，可在帮助气泡里重看。
- 错误：卡内红条人话提示（「邮箱或密码不对」/「试太多次了，1 分钟后再试」）。

## 7. 向导规格

### 7.0 向导通用规范

| 规则 | 说明 |
|---|---|
| 形态 | 居中模态 880px（W3 上线向导 640px），遮罩不可点关闭（防误触丢内容） |
| 顶部 | 步骤条（`①说清楚 ─ ②写内容 ─ ③补信息 ─ ④送审`）+ 右上 `×`（关闭时若有内容，问「存成草稿还是丢掉？」） |
| 底部 | 左 `上一步`（文本按钮）/ 右主按钮（必须带下一步内容，如 `下一步：写内容`）；最后一步主按钮是终态动词 |
| 随时可退出 | 任何一步都自动存草稿，退出后在「知识资产 › 写」列能找到 |
| 键盘 | `Enter` 下一步、`Esc` 询问退出 |
| 不做的事 | 不在向导里做复杂编辑（正文只做粗稿，精修去详情页）；不在向导里问用户答不上来的问题 |

### 7.1 W1 · 新建知识向导（4 步）

**入口**：`+ 新建知识 → 我自己写 / 让 AI 帮我写`、AI 建议卡 `用这个草稿开写`、目录页 `在这里新建`。

#### 步骤 ① 说清楚要写什么
```
你想写什么？
┌────────────────────────────────────────────────────┐
│ 客户会怎么问这个问题？                              │
│ [ 太阳能板阴天充不满电怎么办                      ] │
│ 💡 用客户的话，别用内部术语。比如写「摄像头没电了」 │
│    而不是「电源模块异常」                          │
└────────────────────────────────────────────────────┘
✨ 检查了一下：库里没有类似内容，可以放心写
   （若有相似）⚠️ 库里已经有《太阳能板安装》和这个有点像 —— 
              [看看那篇] [还是新建一篇] [改那篇就行]
                                    [下一步：写内容 →]
```
- **只问一个问题**，输入即标题。
- 实时**重复检查**（防呆核心）：相似度 ≥0.85 时不给直接新建，强制三选一，避免重复建条目。
- 检查不可用时如实说「重复检查暂时用不了，可能会撞车」，不阻塞。

#### 步骤 ② 写内容
- `✨ 让 AI 先起个草稿` 大按钮（3 秒出草稿），或直接自己写（富文本编辑器，工具条含 🔒 仅客服可见）。
- AI 草稿以浅紫底逐段出现，每段带 `用这段` / `删掉`——**逐段可采纳可删，不是一坨全塞**。
- 引导问句随条目类型变化（问题排查类 / 政策说明类 / 操作步骤类，由 AI 判断）：「写不下去？试试回答：为什么会这样 / 怎么解决 / 什么情况要联系客服」。
- 空内容不允许进下一步，提示「至少写点什么，哪怕一句话也行」。

#### 步骤 ③ 补信息（AI 全预填）
```
我帮你填好了，看看对不对：
  放在哪    [政策与售后 › 售后与退款 › 退货政策 ▾]   ✨ AI 建议
  谁能看    ( ) 所有人  (•) 大部分公开，少数内部  ( ) 只有客服
            ↑ AI 发现你有 1 段标了「仅客服可见」，所以选了这个
  客户会怎么问  [太阳能充电慢 ×] [阴天没电 ×] [板子坏了 ×] [+ 加一个]  ✨
  适用型号  [全型号 ▾]        多久体检一次  [180 天 ▾]
                          [← 上一步]  [下一步：送审 →]
```
- **全部预填，用户只做确认**。每个 AI 填的项带 ✨ 并说明理由。
- 不做必填校验轰炸：缺项时字段旁一行黄字提示，不拦截；真正拦截发生在「上线体检」。

#### 步骤 ④ 送审
```
准备好了吗？
  ✓ 内容写了 5 段（含 1 段仅客服可见）
  ✓ 信息填全了
  · 英文：审核通过后系统会自动翻译，到时候需要你校对一下
  这篇会交给 [王琳 ▾] 审核
     [先存草稿，待会儿再说]        [送去审核]
```
- 清单式确认，不是空白确认。审核人可改（默认走分工设置）。
- 点 `送去审核` → 关闭向导 → 回「今日待办」→ 顶部绿条「已送审，等王琳处理」+ 撤销条。

### 7.2 W2 · 批量导入向导（3 步）

| 步 | 内容 |
|---|---|
| ① 把文档给我 | 大拖拽区「把 Word / Markdown / txt 拖进来，或点击选择」+「也可以直接粘贴文字」文本域。支持多文件。说明：「我会自动按标题切成一篇一篇，一次最多 500 篇」 |
| ② 看看切得对不对 | 左侧切出来的条目列表（可勾选/取消），右侧预览选中条目；每行可改标题、改放哪（✨AI 预填目录与章节归类建议）、改谁能看；**「内部：/【内部】开头的段落已自动标为仅客服可见」提示 ★**（预览里内部段落浅黄底可逐段改判）；✨AI 同时给每条预填「客户会怎么问」标签建议；顶部统计「切出 23 篇 · 其中 4 篇疑似重复 [只看重复]」；重复项默认不勾选并标注「库里已有《XX》」 |
| ③ 导进来 | 确认条「23 篇会全部进审核队列，需要人过一遍才会上线」+ 主按钮 `导入 19 篇`（只导勾选的）；执行进度条；结果页：成功清单 + 失败清单（**带行号、原因和原文片段**，逐条报告不整批静默失败）+ `去审核这批` / `再导一批` |

- 导入产物一律进「审」（铁律①），结果页明确写出来；来源标记「批量导入」。
- 失败不影响成功项。

### 7.3 W3 · 上线向导（3 步，主编）

```
① 体检                    ② 英文确认              ③ 上线
✓ 信息填全了              左中右英对照最终稿       将要发生：
✓ 内部内容标好了          [英文没问题，上线]       · 客户 3 分钟内能搜到
✓ 英文已校对（12/12 段）                           · 中英文各推一篇
  全部通过 ✅                                      · 内部段落不会推出去
                                                   [确认上线]
```
- 体检有不通过项：向导停在第 ① 步，展示 MissingList，每条带 `去处理`；不显示「下一步」。
- 第 ② 步是**最后一道人工闸**（铁律②的界面落点），必须人点一次。
- 第 ③ 步文案必须告知版本变化：「上线后这就成为**第 4 版**，第 3 版会存进历史，随时能换回来」。
- 若本次上线包含合并（§6.4.6）：第 ③ 步追加一行「《退货邮费说明》会同时下架，Zendesk 上归档并跳转到本篇」。
- 上线成功即冻结新版本并开始按该版采集效果数据；只推成功一侧语言时不冻结版本，转「推送失败」待办（避免半截版本）。
- 推送失败：不回滚状态，转待办「推送失败」并给人话原因 + `重试`（批量处置去 P10）。

## 8. 易用性 16 条法则（原型生成时逐条自检）

| # | 法则 | 反例 → 正例 |
|---|---|---|
| 1 | **一屏一个主按钮**（次要动作可存在，但不与主按钮并列同权重） | 详情页并排「保存/提交/发布/下线」四个按钮 → 只留当前该做的那一个，其余收进 `⋯` |
| 2 | **按钮说人话** | 「提交」→「送去审核」；「同步」→「上线到帮助中心」 |
| 3 | **不给灰按钮，给清单** | 灰掉的「发布」+ tooltip → 「还差 1 件事：英文还没人校对 [去校对]」 |
| 4 | **撤销优于确认** | 每个动作都弹确认框 → 直接执行 + 10 秒撤销条。**仅 4 个动作保留确认**：下架、回滚版本、覆盖 Zendesk 上别人的修改、停用成员 |
| 5 | **AI 先填，人只改** | 空白表单 8 个必填 → AI 预填全部，人做确认题；每个 AI 填的项带 ✨ 和填写理由 |
| 6 | **系统主动派活** | 用户自己去各页面巡检 → 12 类事件自动生成待办进收件箱（§9） |
| 7 | **工作流面零术语** | 「同步状态：blocked」→「暂时不能推送到 Zendesk：英文还没人校对」 |
| 8 | **进度永远可见** | 用户不知道条目卡在哪 → 五步进度条 + 「等谁 · 等多久」全局强制 |
| 9 | **防呆前置** | 建完才发现重复 → 建之前就查重并强制三选一 |
| 10 | **错误给出路** | 「操作失败」→「推送失败了：Zendesk 暂时没响应。[重试] 或等 5 分钟系统自动再试」 |
| 11 | **默认值能跑** | 让用户先配一堆才能用 → 所有设置都有推荐默认值，不配也能完成全流程 |
| 12 | **诚实标注降级** | AI 挂了却装作正常 → 「AI 分析暂时不可用，下面是粗略统计，仅供参考」 |
| 13 | **改动永远可退** | 「发布即终局」→ 每次上线都冻结一版，任何时候能看「改了哪里」、能一键换回老版（§10） |
| 14 | **不拿小样本吓人** | 「解决率 40%，效果差！」（其实只有 5 次）→ 样本不足统一显示「数据还不够，下不了结论」（§10.3） |
| 15 | **分类不让人想** | 让用户填一级/二级分类 + 标签 → 场景由目录派生、标签只问「客户会怎么问」（§13） |
| 16 | **收纳优于删除（v3.0 新增，总纲）** | 觉得功能复杂就砍掉 → 默认收起、按需展开、按角色显隐；专业能力必须可达（G15/G17） |

| 6 | Zendesk 上被人改了 | 漂移检测命中 | 主编 | 🔥 | 对比一下（→P10 冲突区） |

| 8 | 这篇效果不好 | 引用 ≥10 次且解决率 <60%，每条目每 30 天最多提醒一次 | 条目负责人 | 📋 | 去改改 |
| 9 | 有人指派给你 | 手动指派 | 被指派人 | 📋 | 去处理 |
| 10 | 新版不如老版 | 新版上线 ≥7 天 且样本 ≥30 且解决率比历史最佳版低 ≥10pp（§10.3） | 主编 + 条目负责人 | 📋 | 看改了哪里 |
| 11 | 内容快到期了 | 「有时限」条目距失效日期 ≤7 天（§13.4） | 条目负责人 | 📋 | 处理一下 |
| 12 | 接手交接 | 成员被停用/移出范围，手上还有活 | 新接手人（默认主编） | 🔥 | 接下来 |

**防打扰规则**：
- 同类待办合并：3 篇推送失败 = 1 张卡「3 篇文章推送失败」，点开是列表（深链 P10）。
- 📋 类每人每天新增上限 20 条，超出排队到次日；**🔥 类不设上限、不排队（G16）**。
- 待办 7 天未处理 → 通知其上级/主编（不是继续骚扰本人）。

## 10. 版本管理与回滚

> 心智模型见 §3.4。本节是页面级落地规格。核心命题：*用户改了一版，效果反而变差了，系统要能让他毫不费力地发现、看清、退回去。*

### 10.1 版本何时产生（唯一入口）

| 动作 | 是否产生新版本 | 说明 |
|---|---|---|
| 自动保存 / 编辑草稿 | ❌ | 只在草稿里滚动保存，界面显示「正在改的（还没上线）」 |
| 送审 / 审核通过 | ❌ | 仍是草稿，只是流转到下一步 |
| **上线成功（推 Zendesk 成功）** | ✅ 冻结为 vN | 同时开始按该版本采集效果数据；旧的 current 转为 history |
| 回滚 | ✅ 新增 vN+1（内容 = 老版） | 见 §10.4 |
| 下架 | ❌ | current 保留但标「已下架」，效果数据停止累计 |
| Zendesk 侧被人改后「把对方改动收回来」 | ✅（走一遍写→审→发） | 不允许绕过审核直接成版（铁律①） |

> **为什么不在保存时就发版本**：用户改十次存十次 = 版本列表变垃圾场，效果数据也无法归属。只有客户真正看到过的内容才配拥有版本号。

### 10.2 版本时间线（P3 › 版本与改动，组件 `VersionTimeline`）

| 规格 | 说明 |
|---|---|
| 排序 | 倒序，current 置顶 |
| 每卡字段 | 版本号 / 作者 / 上线时间 / 在线时长 / 动作类型 / AI 改动摘要（1 句）/ 改动处数 / 该版效果（解决率 + 样本）/ 中英是否齐全 |
| 动作类型贴纸 | `首发` / `例行修改` / `按 AI 建议改的` / `从 v2 换回来的` / `Zendesk 冲突合并` / `批量导入` / `合并自《XX》` —— 来源可追溯，用于事后复盘「AI 建议到底靠不靠谱」 |
| 最佳版高亮 | 🏆 历史解决率最高且样本 ≥30 的那版，永远显示在顶部提示条 |
| 对比 | 勾选任意两版 → 全屏 DiffView；未勾选时单卡 `看改了哪里` = 对上一版 |
| 权限 | 编辑：可看、可对比、不可回滚；主编：全部；管理员与观察员：只读 |
| 保留策略 | 全量保留不清理。>20 版时折叠中间部分为「中间还有 12 版 ▾」 |

### 10.3 版本效果对照与「该回滚了」判定（`VersionCompareBar`）

```
┌────────────────────────────────────────────────────────────┐
│ 第 2 版          vs         第 3 版（现在线上）             │
│ 解决率 78%  ████████████     解决率 61%  ████████           │
│ 样本 312 · 在线 40 天        样本 84 · 在线 7 天            │
│ 采纳率 71% → 55%   被踩 3 → 11                              │
│ 🔴 结论：第 3 版明显不如第 2 版（差 17 个点，数据已足够）    │
│                [看改了哪里]      [把第 2 版换回去]          │
└────────────────────────────────────────────────────────────┘
```

**判定规则（同时满足才提示回滚，避免误报）**

| 条件 | 阈值 | 理由 |
|---|---|---|
| 新版在线时长 | ≥7 天 | 给新版足够曝光 |
| 新版样本量 | ≥30 次引用 | 小样本不下结论（法则 14） |
| 解决率差距 | 比历史最佳版低 ≥10pp | 低于此视作波动 |
| 对照版样本量 | ≥30 | 老版数据本身也要可信 |

> 与现行 PRD §13.2「回滚建议判定线 = 下降 ≥15pp（建议值）」的关系：本版以「10pp + 三重护栏（时长/双侧样本量）」**取代**单一 15pp 线——护栏比高阈值更能防误报。落地时需回写 PRD 建议值。

- 三档结论文案：`数据还不够，下不了结论`（灰）/ `差不多，看不出区别`（灰）/ `第 3 版明显不如第 2 版`（红）。
- 满足红档 → 自动生成待办 #10，派给主编 + 条目负责人，每条目每 30 天最多提醒一次。
- 反向也提示：新版明显更好时显示绿字「这次改得好，比上一版高 12 个点」（不生成待办）。

### 10.4 回滚（M8，危险动作之一）

**语义**：回滚 = 把老版内容重新上线，**生成一个新版本**，不是删除新版。

```
v1 → v2 → v3(差) → v4（内容 = v2，动作类型「从 v2 换回来的」，current）
                    v3 标记为「这版被撤下了」
```

**M8 确认弹窗**
```
┌── 把第 2 版换回去？ ──────────────────────────────────┐
│ 会发生什么：                                          │
│ · 客户 3 分钟内看到的就是第 2 版的内容（中英一起换）   │
│ · 这会生成第 4 版，第 3 版不会删，随时还能换回来       │
│ · 第 3 版这 7 天的数据会保留，记在第 3 版名下          │
│ · 这件事会记在留痕里，并通知李娜（第 3 版作者）        │
│ 对照：v2 解决率 78%（312 次） / v3 61%（84 次）        │
│ 输入条目名确认：[                    ]                 │
│                        [取消]   [换回第 2 版]          │
└────────────────────────────────────────────────────────┘
```

| 规则 | 说明 |
|---|---|
| 谁能做 | 仅主编。编辑只能「告诉主编」 |
| 要不要重新过审 | **不需要**——该版本历史上已审过、也上线过，回滚是恢复既有已审内容，不破铁律①。但必须：留痕 + 通知原作者 + 时间线标「从 v2 换回来的」 |
| 中英一起回 | 回滚回的是整版快照，英文同回，避免中英错位（§3.4.1） |
| 回滚后想接着改 | 基于 v4 继续写 → 走完整五步。界面提示「你现在改的是第 2 版的内容」 |
| Zendesk 侧 | 文章 id 不变，等同一次更新推送；失败则转「推送失败」待办，不留半截状态 |
| 连续回滚保护 | 同一条目 24 小时内第二次回滚时，弹窗加一行「这篇今天已经换过一次版本了，确定还要换？」 |

### 10.5 版本与其他机制的关系（避免设计打架）

| 机制 | 与版本的关系 |
|---|---|
| 上线体检 | 体检针对待上线的草稿，通过后才允许冻结成版 |
| 定期复核（W4） | 复核对象是 current 版；选「还准」→ 只重置复核期，不产生新版本 |
| Zendesk 冲突 | 对比基准 = current 版内容；「以我们的为准」= 重推 current，不产生新版 |
| AI 建议「该改现有的」 | 采纳后基于 current 派生草稿，版本类型记为「按 AI 建议改的」，便于统计 AI 建议的真实收益 |
| 合并（§6.4.6） | 合并稿上线时保留篇冻结新版（类型「合并自《XX》」），被并篇同时下架归档 |
| 效果数据看板（P5） | 「拖后腿」榜单按 current 版计算；点进去能立刻看到是否「换个老版就好了」 |

## 11. 语言配置与双语模型

### 11.1 三条原则

| 原则 | 说明 |
|---|---|
| **中文是源，英文是派生** | 只在中文侧组织结构（段落、顺序、内部标记）。英文永远跟着中文段落走，不允许英文单独增删段 |
| **段落级对齐，段落级状态** | 每段有稳定锚点，中英按锚点配对。改了第 3 段中文，只有第 3 段英文变「要重看」，不是整篇作废 |
| **英文不单独发版** | 中英同属一个版本（§3.4） |

### 11.2 段落级英文状态（`LangBadge`）

| 状态 | 界面 | 何时产生 |
|---|---|---|
| ⚪ AI 待校对 | 「机器翻的，还没人看过」 | AI 翻译产出 |
| 🟢 已校对 | 「有人看过了」 | 人点了这段的「这段没问题」或手改过 |
| 🟡 中文改了要重看 | 「中文改过了，这段英文要重看」 | 对应中文段落内容变化 |
| 🔒 不翻译 | 「内部内容，不翻译也不推送」 | 该段标了「仅客服可见」 |

**上线体检的英文项**：所有非 🔒 段落都是 🟢 时才算通过。体检文案：「英文还差 3 段没人看过 → 去校对」（直接说差几段）。

### 11.3 英文校对页（「译」这一步的落点）

```
┌── 校对英文《摄像头离线了怎么办》         已校对 8/12 段 ────┐
│ [只看还没看的（4）]  [全部看]      [✨ 重新翻译还没校对的]   │
├──────────────────────┬───────────────────────────────────┤
│ 中文（只读）          │ 英文（可编辑）                     │
│ 摄像头离线通常由…    │ Camera offline is usually caused… │
│                      │ ⚪ [这段没问题]  [我改改]           │
├──────────────────────┼───────────────────────────────────┤
│ 🔒 内部：先查工单…   │ 内部内容不翻译，客户看不到          │
├──────────────────────┼───────────────────────────────────┤
│ 固件升级后需重启…    │ After firmware upgrade…  🟡        │
│ （中文 3 天前改过）  │ 上次校对的英文：[看一眼旧的 ▾]      │
└──────────────────────┴───────────────────────────────────┘
       全部校对完 → 底部出现主按钮 [英文校对完了]
```

| 规格 | 说明 |
|---|---|
| 进度 | 顶部「已校对 8/12 段」，进度条实时更新 |
| 逐段确认 | 每段一个 `这段没问题`（点一下变 🟢）；改过的自动变 🟢，带「人工修订」标注留痕 |
| 一键 | `全部标为没问题` 仅在 ≤3 段未校对时出现，防止一键糊弄整篇 |
| 🟡 段落 | 显示「上次校对的英文」可展开对照，避免推倒重来 |
| 术语高亮 | 命中固定译法表的词高亮，悬浮显示「产品词：Solar Panel（固定译法）」；改成别的译法时黄字提醒（§11.7） |
| 标题与摘要 | 页面顶部单独一栏校对英文标题、英文摘要、英文问法标签，与正文同一进度计入（**英文标题空 = 体检不过**） |
| 表述自由边界 | 英文允许改表述（如 buyer's remorse → change of mind），但不得改变政策口径——校对页顶部一句话提醒 |
| 完成 | 全部 🟢 → 主按钮 `英文校对完了` → 进入「发」 |

### 11.4 阅读态的语言切换

详情页头部三切片 `中英对照` / `只看中文` / `只看英文`（记忆选择）。看板/列表默认显示中文标题，英文缺失时标题右侧一枚 `EN` 灰徽章表示「英文还没齐」。

### 11.5 「要不要英文版」的条目级配置

| 取值 | 行为 |
|---|---|
| `跟随默认`（默认） | 用设置里的全局开关（默认：要英文） |
| `要` | 走完整五步，英文未校对不能上线（铁律②） |
| `只发中文` | 「译」这一步显示为跳过态：`③译 —（这篇只发中文）`，上线只推中文站；卡片标灰徽章「只中文」。**选择原因必填一句话**，记入留痕，防止被滥用来绕过铁律② |

### 11.6 图片与附件的双语

| 规则 | 说明 |
|---|---|
| 一图两版 | 带界面文字的截图需中英两张；上传中文图时提示「这张图里有中文界面，要不要传一张英文版？」（可选，不阻塞） |
| 未提供英文图 | 英文文章沿用中文图 + 图注英文化，体检不拦截，但在校对页标黄「这张图是中文界面」 |
| 媒体库 | 图片统一入库，替换一张图会影响所有引用它的条目，替换前提示「另有 2 篇在用」 |
| 推送 | 上线时图片随文上传到 Zendesk，失败按「推送失败」处理并指明是哪张图 |

### 11.7 固定译法表（Glossary）

- 位置：`运营中心 › 设置 › 固定译法表`。
- 内容：中文词 / 英文译法 / 备注（如「产品名，不加复数」）/ 是否强制。
- 作用：AI 翻译时强制套用；校对页高亮；违反强制译法时校对页黄字提示（不拦截）。
- 开箱预置：产品线名称、功能名、品牌词。

## 12. 改动对照（Diff 视图规格）

> 默认人话呈现（不显示行号、hunk、+/-，只显示「第几段 · 什么小标题 · 改了什么」）；**技术视图保留为切换项**（§12.7）。

### 12.1 三种人话视图

| 视图 | 何时默认 | 说明 |
|---|---|---|
| **只看改动**（默认） | 审核、版本对比 | 未改动段落折叠成一行「省略 6 段没改的 ▾」，只展开改动段及其上下文一段 |
| **并排对照** | 大屏（≥1280px）默认 | 左「改前」右「改后」，同段落横向对齐，滚动同步 |
| **合并视图** | 窄屏 / 移动端默认 | 改前段落（浅红）紧跟改后段落（浅绿），上下相邻 |

切换器统一在左上角：`[只看改动 ▾] [并排 | 合并] [人话 | 技术视图]`。

### 12.2 高亮粒度

| 粒度 | 呈现 |
|---|---|
| 段落级 | 整段新增 = 浅绿左边条 + 「新增第 4 段」；整段删除 = 浅红 + 删除线 + 「删掉了原第 5 段」 |
| **词级** | 段内修改时只高亮变化的词/短句（红底删除、绿底新增），其余正常显示——用户一眼看清「15 天 → 7 天」 |
| **移动识别** | 段落只是换了位置 → 不显示为一删一增，显示为紫色标记「这段挪到了第 2 段前面」 |
| 格式改动 | 只改了加粗/列表等格式 → 折叠为一行「第 3 段只改了排版」，默认不展开（降噪） |
| 内部段落 | 带 🔒，底色不同，并注明「这段客户看不到」——内部内容剥离后不进对外文章的事实在对照里直接可见 |

### 12.3 「信息改动」区

正文之外的字段改动必须同样可审、可追溯，独立区块置于正文改动之上：

```
❗ 信息改动（3 处）
  放在哪        售后与退款 › 退货政策  →  售后与退款 › 退款到账
  客户会怎么问  + 固件升级失败   − 板子坏了
  谁能看        所有人  →  大部分公开，少数内部
```

覆盖字段：目录位置、谁能看、客户会怎么问、适用型号、时效性、体检周期、负责人、标题、摘要、相关文章、图片替换。

### 12.4 语言维度

顶部一组切片：`中文` / `英文` / `两边都看`。「两边都看」= 上下两块，分别是中文改动与英文改动，便于审核判断「中文改了英文有没有跟上」。英文块顶部显示段级状态汇总（🟢8 🟡3 ⚪1）。

### 12.5 三处复用同一组件

| 场景 | 左（基准） | 右（对照） | 附加动作 |
|---|---|---|---|
| 审核（M2） | 线上 current 版 | 待审草稿 | 段落上 `留个意见`；`通过` / `退回改改` |
| 版本对比（M7） | 选中的旧版 | 选中的新版 | `把左边这版换回去`（主编） |
| Zendesk 冲突（P10 冲突区 / 待办 #6） | 我们这边（current） | Zendesk 上现在的 | `以我们的为准（覆盖对方）` / `把对方改动收回来` / **`挑几段收回来`（逐段勾选合并）** |

> 「挑几段收回来」：现实中同事在 Zendesk 上只改了一段，全盘二选一太粗暴。逐段勾选后生成草稿 → 仍需走「审」。

### 12.6 空态与降级
- 两版内容完全相同（只有信息字段变了）：正文区显示「正文一个字都没改，只改了信息」。
- 改动过大（>80% 内容变化）：顶部提示「这次几乎是重写了，建议直接看全文」+ 默认切到「看全文」。
- AI 改动摘要不可用时：显示「改了 4 处（摘要暂时生成不了）」，不影响对照本身。

### 12.7 技术视图（git 风格，切换项 ★）

- 触发：DiffView 右上 `[人话 | 技术视图]` 切片；选择记忆到本人。
- 呈现：逐行 diff——删除行红底、新增行绿底、未变更上下文灰字折叠（默认前后各留 1 行，可「展开全部」）、行首带变更前/后行号槽；字段变更以键值行同形呈现；内部段落带 🔒 标记。
- 定位：给习惯逐行核对的审核者与排查场景用（长文档、格式敏感内容、批量导入的切分核对）。**这是用户 08-05 拍板的既有功能（审核中心两层对照·git diff 详情层），本版保留为非默认视图，不得删除。**
- 移动端不提供技术视图（屏幕不够宽，只保留合并视图）。

## 13. 元数据与分类体系

> 回答两个问题：**(a) 该不该有问题标签？(b) 问题的一二级分类跟不跟目录走？**

### 13.1 结论先行

**分成两个正交维度，各管各的，绝不让用户填两遍：**

| 维度 | 是什么 | 谁维护 | 用途 | 基数 |
|---|---|---|---|---|
| **存放位置**（结构维度） | `库 › 目录 › 章节`，一篇只能在一处 | 人（AI 建议） | 浏览导航、Zendesk Category/Section 映射、权限范围、统计聚合的一二级场景 | 树内固定两级（目录 ~8 个、章节 ~40 个），库为切换器 |
| **问法标签**（检索维度） | `客户会怎么问`，多对多 | AI 生成 + 人增删 | AI 检索召回、搜索、缺口分析、Zendesk labels | 每篇 4–6 条，上限 10 |

### 13.2 (b) 一二级分类跟着目录走——是，但补一个「次要场景」

**为什么跟着目录走**：
1. 一二级分类的真实用途只有一个——统计聚合（覆盖率、缺口按场景看）。目录本身就是按客户场景组织的树，两套并行必然对不齐。
2. 让用户在「放哪个目录」之外再选一次「属于哪个场景」，是同一件事问两遍（法则 15）。
3. Zendesk 侧只有 Category/Section 两级，目录已与之一一映射。

**所以**：`场景一级 = 目录`，`场景二级 = 章节`，系统派生、界面只读（侧栏灰字展示统计口径）。

**补丁——次要场景**：一篇文章可能被多个场景问到。允许填「也会在这些场景被问到」（≤3 个章节）：
- 只影响：缺口统计的分母、AI 检索的场景过滤、相关推荐。
- 不影响：存放位置、Zendesk 结构、目录树中的显示位置。

> 落地注记：此设计废除现行 PRD §4.1 的「两级问题场景 + 标签」人填字段，属需求级变更，须走 prd-master 增量回写（PRD §4.1 / requirements 对应 REQ 修订）；同时覆盖缺口统计的对照基准（工单场景分布）需建立「Zendesk 工单场景 → 目录」的映射口径。

### 13.3 (a) 该有问题标签——就是「客户会怎么问」，但必须治理

| 治理规则 | 说明 |
|---|---|
| **只问人话** | 输入引导：「用客户的原话，比如『摄像头没电了』，不要写『电源模块异常』」 |
| AI 预填 | 建条目时 AI 从相似对话里生成 4–6 条；上线后持续从真实搜索词/对话里推荐新问法（详情页「相关」页签一键加入） |
| **同义归并** | 输入时实时提示「库里已有相近问法『摄像头没电』，用它？」——避免标签爆炸 |
| 问法词典 | `运营中心 › 设置 › 问法词典`：查看全部问法、使用次数、合并/重命名（合并后同步更新所有引用条目，留痕） |
| 冷却清理 | 90 天零命中的问法灰显，词典里给 `清理建议` 批量删除入口 |
| 上限 | 每篇 ≤10 条，超出时提示「问法太多反而不准，挑最典型的」（现行「标签 ≤20」相应收紧，随 §13.2 增量一并回写） |
| 与 Zendesk | 上线时派生为文章 labels（中英各一套）；英文问法在校对页一并校对 |

### 13.4 其余元数据全清单

| 字段 | 人填/派生 | 作用 | 备注 |
|---|---|---|---|
| 标题（中/英） | 人 | 展示、搜索 | 英文标题空 = 体检不过 |
| 一句话摘要（中/英） | AI | 重复检查比对基准、列表预览 | 人改过后 AI 不再覆盖 |
| 放在哪 | 人 | 结构 | 见 13.1 |
| 客户会怎么问 | AI + 人 | 检索 | 见 13.3 |
| 也会在这些场景被问到 | 人（可空） | 统计/推荐 | 见 13.2 |
| 谁能看 | 人 | 可见性 + 内部段落 | 三选一 |
| 适用型号 | 人 | AI 检索过滤（客户报型号时优先匹配） | 默认全型号 |
| 时效性 | 人 | 促销/活动类内容到期自动提醒 | `长期有效` / `有时限 + 失效日期`；到期前 7 天生成待办 #11；过期后列表标红「已过失效日期」，**不自动下架** |
| 多久体检一次 | 人 | 复核节奏 | 90/180/365 |
| 谁负责这篇 | 人 | 派活、交接 | 成员停用时触发待办 #12 |
| 来源 | 系统 | 复盘 AI/导入/手写的质量差异 | `手写` / `AI 发现` / `批量导入` / `Zendesk 收回` / `优化建议` |
| 版本相关字段 | 系统 | §3.4 | current 版本号、上线时间、在线时长 |

### 13.5 客户原声的脱敏（合规）

AI 建议卡、效果页原声、对话摘录中出现的手机号、邮箱、订单号、地址一律自动打码（`138****5678`），并在区块底部注明「已自动隐去联系方式」。原始内容不落地到知识条目里；需要看完整工单时跳 Zendesk（在 Zendesk 侧鉴权）。

## 17. 非目标（明确不做，防止发挥过度）

| 不做 | 原因 |
|---|---|
| 自定义新角色 / 新权限项 | 权限矩阵只在既有 10 项 × 4 角色内调整（§2.3）；角色体系不开放扩展 |
| 可配置工作流引擎 | 五步固定，拍板结论 |
| 客服工单/CSAT/人效报表 | Zendesk Explore 已有，不重建 |
| 多语言扩展界面（日/德/法） | 本期只做中英；架构上预留，界面不体现 |
| 站内实时协同编辑（多人同时打字） | 用「有人也在改」提示 + 版本对照解决即可 |
| 三级及以上目录 | 结构深度固定两级，Zendesk 侧也只有 Category/Section；库为切换器不算层级 |
| 条目物理删除 | 只有「下架」，历史与留痕不可毁 |
| 深色模式 | 本期不做 |
| 版本分支 / 并行维护两条线 | 版本只有一条线性历史，不做 branch/merge（逐段合并仅用于 Zendesk 冲突与条目合并场景） |
| 按版本回滚单个字段 | 回滚是整版快照（想只改一段就正常编辑） |
| 自动回滚 | 永不自动换客户看到的内容，只生成建议待办，由主编拍板 |
| 自定义分类体系 / 多维标签组 | 只有「目录›章节」+「客户会怎么问」两个维度（§13.1） |
| 内容到期自动下架 | 只提醒不自动动，避免误伤线上（§13.4） |
| 知识库（库级）CRUD 界面 | 库为预置分组（现状无库级接口）；库的增删本期走后台配置，界面只做切换与范围授权 |
