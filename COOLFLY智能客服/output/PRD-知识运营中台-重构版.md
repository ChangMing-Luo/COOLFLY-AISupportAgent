# COOLFLY 知识运营中台 · PRD（重构版 v2.1）

> 生成时间：08-05-2026 17:15
> 定位：**面向 AI 直接生成后台原型**的产品需求文档。旧版 `PRD-界面规格版.md`（v1.0）是对现役实现的 as-is 快照，本文是 **to-be 重设计**——菜单层级、页面骨架、交互范式全部重来。
> 设计基调：**傻瓜式**。用户不需要懂状态机、不需要懂 Zendesk、不需要记流程；系统主动派活，AI 先填人只改，一屏一个主按钮。
> 拍板依据（08-05-2026）：交互范式 = 混合式（收件箱 + 向导 + 看板）；流程 = **固定五步流水线**，不可配置，但每步「谁来做」可指派；角色精简为 3 个 + 单人模式。
>
> **v2.1 补充（08-05-2026 晚）**：补回四块被初稿想浅了的核心设计——§3.4 + §10 **版本管理与回滚**（指标挂在「条目 + 版本」上，支持回滚决策）、§11 **语言配置与双语模型**（段级英文状态、固定译法表）、§12 **改动对照**（人话化的 Git diff）、§13 **元数据与分类**（场景派生于目录 + 问法标签治理），并新增 §14 **数据闭环**自查。

## 0. 给 AI 的生成约束（读这一节就能开工）

生成原型时必须遵守，违反即视为不合格：

| # | 约束 | 说明 |
|---|---|---|
| G1 | **一级菜单只有 4 项，禁止出现二级菜单** | 见 §4.1。任何"分组 → 子项"结构都不允许 |
| G2 | **每屏只有一个主按钮（Primary）** | 主按钮文案必须是动词短语，禁止用「保存 / 提交 / 确认 / 下一步」这类无信息量词（向导内的「下一步」除外，且必须带内容提示，如「下一步：补齐信息」） |
| G3 | **禁止渲染 disabled 按钮** | 条件不满足时不画灰按钮，改画「还差 N 件事」清单卡，每条带跳转修复入口 |
| G4 | **界面禁止出现技术术语** | 黑名单：状态机、门禁、drift、乐观锁、同步队列、幂等、locale、payload、schema、API。用 §3.3 术语对照表的中文替换 |
| G5 | **五步进度条是全局强制组件** | 任何展示单个知识条目的地方（卡片、抽屉、详情页、通知）都必须带它 |
| G6 | **非危险动作不弹二次确认** | 直接执行 + 底部「已完成 X，撤销」条（10 秒）。只有 §8 法则 4 列出的 4 个动作弹确认 |
| G7 | **空态必须给出下一步动作** | 禁止只写「暂无数据」，必须是「一句话解释 + 一个主按钮」 |
| G8 | **每页必须画出 4 种状态** | 正常 / 空 / 加载（骨架屏）/ 出错（含重试按钮） |
| G9 | **配色遵循 §5.1 语义色**，不引入第五种强调色 | 绿=已完成、黄=等你处理、红=出问题、蓝紫=AI 产出 |
| G10 | **宽度基线 1440px**，侧栏 220px 固定，内容区最大 1180px 居中；<1024px 侧栏收成图标条 | 移动端只需支持「今日待办」与「审核」两页（§6.7） |
| G11 | **版本徽章与五步进度条同进同出** | 有 StepBar 的地方就必须有 `v3` 徽章；任何效果数字旁必须标明「哪一版 / 多少样本」（§3.4、§10） |
| G12 | **改动对照禁止工程化** | 不出现行号、hunk、`+/-`、commit 类元素；只能说「第几段 · 小标题 · 改了什么」（§12） |
| G13 | **英文状态只能是段级** | 禁止出现「整篇英文未确认」这类粗粒度提示，必须能说出「还差几段」（§11.2） |
| G14 | **不让用户填分类** | 界面不得出现可编辑的一级/二级分类字段；场景一律由「目录›章节」派生（§13） |

## 1. 产品定位与三条铁律

### 1.1 一句话定位
**COOLFLY 客服知识的唯一生产地。** 知识在这里写、在这里审、在这里翻译、从这里一键上线到 Zendesk 帮助中心，上线后的效果再回流到这里指导下一次修改。

### 1.2 边界（用户会问的三个问题，界面要能自己回答）
| 问题 | 答案（写进界面引导文案） |
|---|---|
| 客户在哪看到这些内容？ | Zendesk 帮助中心 + Zendesk AI 客服机器人。本台负责生产，不负责接客 |
| 工单量、客服人效在哪看？ | Zendesk Explore。本台只看**知识的效果**（有没有被引用、有没有解决问题） |
| 能不能直接在 Zendesk 改文章？ | 能，但不该。改了本台会检测到并提醒你「有人在外面动了这篇」 |

### 1.3 三条铁律（产品硬约束，不可通过任何配置绕开）

| 铁律 | 用户能感知到的表现 |
|---|---|
| **① 都得过审** | 任何内容——手写的、AI 挖的、批量导进来的、从 Zendesk 拉回来的——都必须走「审」这一步才能上线。界面上不存在任何「直接发布」入口 |
| **② 英文必须人看过** | 英文没人点过「校对完成」，「上线」这一步的按钮就不会出现（改为显示「还差：英文没人校对」+ 跳转） |
| **③ 一切留痕** | 谁、什么时候、改了什么、改前改后，全部记下且**任何人不能删**。界面上没有删除日志的入口 |

## 2. 角色与权限（3 + 1）

### 2.1 三个角色

| 角色 | 一句话定位 | 能做 | 不能做 |
|---|---|---|---|
| **编辑**（Editor） | 写知识的人 | 写 / 改 / 建目录 / 处理 AI 建议 / 送审 / 校对英文 | 审核、上线、回滚、下架 |
| **主编**（Publisher） | 把关和上线的人 | 编辑的一切 + 审核 + 上线 + 回滚 + 下架 + 处理 Zendesk 冲突 | 管成员 |
| **管理员**（Admin） | 管人和看账的人 | 管成员 + 看全量留痕 + 看数据 + 系统设置 | 不参与内容审核与上线（可看不可动） |

> 设计取舍：旧版 10 个权限点 × 4 角色的矩阵对用户是纯认知负担。新版**取消权限矩阵界面**，角色写死；成员管理页只需选三选一的角色卡。

### 2.2 单人模式（Solo Mode）
- 场景：团队只有 1–2 人，主编就是编辑本人。
- 开关位置：`运营中心 → 设置 → 团队规模`，选「就我一个人 / 小团队（2–5 人）/ 分工明确（6 人以上）」。
- 选「就我一个人」时：**审这一步不消失，但允许自审**，界面提示「你既是作者也是主编，这次审核会记在留痕里」。**铁律①不破**。
- 选「分工明确」时：可在设置里给「审 / 译 / 发」三步各指派默认负责人，待办自动派到人。

### 2.3 界面权限表现（G4 的补充）
- 不能做的功能**直接不出现在界面上**（不是置灰）。
- 唯一例外：审核相关按钮对编辑显示为**信息条**「这一步等主编 <姓名> 处理，已通知」，让编辑知道卡在哪。

## 3. 核心心智模型：五步流水线

### 3.1 五个字
```
  写  ─────▶  审  ─────▶  译  ─────▶  发  ─────▶  盯
 起草内容    主编把关    英文校对    推上 Zendesk   看效果·到期复核
  编辑        主编        编辑        主编         系统 + 全员
```

- 五步**固定不可配置**，用户只需记住这五个字。
- 每步的「谁来做」可指派（§2.2）。
- **异常不是第六步**，而是贴在卡片上的两枚贴纸：`被退回`（审这一步没过）、`已下架`（发过又撤了）。
- 「盯」这一步是**常驻的**——上线后条目永远处在「盯」，直到被改动重新进入「写」。

### 3.2 五步进度条组件（全局强制，G5）
```
 ①写 ━━●━━ ②审 ────  ③译 ────  ④发 ────  ⑤盯
 └ 已完成    └ 进行中（等主编 王琳 · 已等 2 天）
```
规格：
- 已完成步：实心绿 + `✓`；进行中步：实心蓝紫 + 脉冲点；未开始步：空心灰。
- 进行中步下方一行小字：**「等谁 · 等了多久」**（超过 3 天变黄，超过 7 天变红并自动生成催办待办）。
- 有异常贴纸时，进度条右端追加红/灰贴纸，点击展开原因。
- 组件三种尺寸：`lg`（详情页顶部）/`md`（看板卡片）/`sm`（列表行内，只显示 5 个点）。

### 3.3 术语对照表（G4 强制，界面只准用右列）

| 内部概念 | 界面必须这么说 |
|---|---|
| draft / editing | 写作中 |
| pending_review / reviewing | 等待审核 |
| approved | 审核通过，待上线 |
| published | 已上线 |
| rejected | 被退回 |
| offline | 已下架 |
| en_status = pending_human | 英文待校对 |
| en_status = stale | 中文改过了，英文要重看 |
| en_status = confirmed | 英文已校对 |
| sync_status = queued/running | 正在推送到 Zendesk |
| sync_status = failed | 推送失败（附人话原因 + 重试按钮） |
| sync_status = blocked | 暂时不能推（附「差什么」） |
| 发布门禁 | 上线体检 |
| gate check 未通过 | 还差 N 件事 |
| drift（内容漂移） | 有人在 Zendesk 上改过这篇 |
| 乐观锁冲突 409 | 这篇刚被别人改过，你的改动可能会覆盖他 |
| 语义查重 | 重复检查 |
| 挖掘候选 | AI 发现的新话题 |
| 知识缺口 | 客户在问、我们没写 |
| 复核到期 | 该体检了 |
| 审计日志 | 操作留痕 |
| RBAC / 权限矩阵 | 成员与分工 |
| version / v3 | 第 3 版（界面可显示「v3」，但必须配「第 3 版」或日期） |
| rollback | 把老版本重新上线 |
| diff | 改了哪里 / 改动对照 |
| glossary | 固定译法表 |
| blockId（段落锚点） | 段落（用户只感知「第 3 段 · 小标题」） |
| cherry-pick（逐段合并） | 挑几段收回来 |
| 置信度 / 样本量不足 | 数据还不够，下不了结论 |

### 3.4 版本模型：一篇 · 多版 · 双语（核心补充）

> 这是 v2.0 初稿最大的遗漏。**统计口径、回滚策略、改动对照、双语状态，全都挂在「条目 + 版本」上**，没有版本模型上面四件事都立不住。

#### 3.4.1 三层对象

```
知识条目（Entry，永久 id，客户看到的那篇文章）
  └─ 版本（Version v1, v2, v3 …  只增不改不删）
        ├─ 中文内容（段落数组，每段有稳定段落锚点）
        ├─ 英文内容（与中文按段落锚点一一对应）
        ├─ 信息快照（放在哪 / 谁能看 / 客户会怎么问 / 适用型号 / 体检周期 …）
        └─ 效果数据（该版上线期间累计：引用、命中、解决、采纳、被踩、样本量）
```

| 规则 | 说明 |
|---|---|
| **版本是快照，不是补丁** | 一个版本 = 中文 + 英文 + 全部信息字段的完整快照。所以任意两版都能直接对照，包括「信息」的改动 |
| **中英同版** | 英文不单独编版本号。禁止出现「中文 v3 配英文 v2」这种错位——中文改了，同版英文就进入「要重看」 |
| **只增不减** | 版本永不删除、永不覆盖。回滚也是**新增一版**（见 §10.4） |
| **一次上线冻结一版** | 只有「发」这一步成功推到 Zendesk，才把当前草稿冻结为正式版本并开始计效果数据。写作/审核期间的自动保存不产生新版本号 |
| **效果数据归属版本** | 每一次 AI 引用、每一次解决/未解决、每一次点踩，都记在「当时线上是哪一版」上。这是回滚决策的唯一依据 |

#### 3.4.2 版本状态（用户可见的四种）

| 状态 | 界面说法 | 说明 |
|---|---|---|
| current | **客户现在看到的就是这版** | 有且只有一版处于此状态 |
| history | 第 N 版（已被替换） | 保留全部内容与效果数据 |
| draft | 正在改的（还没上线） | 基于 current 派生，未冻结 |
| rolled_back | 这版被撤下了 | 曾上线、因效果差被回滚，卡片带灰色贴纸 |

#### 3.4.3 版本号出现在哪里（强制）

五步进度条右侧统一挂一枚版本徽章：`v3` / `v4 草稿`。出现位置与 StepBar 一致（待办卡、看板卡、列表行、详情页、审核浮层、通知）。悬浮显示「第 3 版 · 王琳 · 3 天前上线」。

## 5. 设计系统（原型元件库）

### 5.1 语义色（G9，只有 4 种强调色）

| 语义 | 用途 | 建议色值 |
|---|---|---|
| **绿 · 完成** | 已完成步骤、已上线、体检通过 | `#10B981` |
| **黄 · 等你** | 等待处理、快到期、需要注意 | `#F59E0B` |
| **红 · 出问题** | 被退回、推送失败、已过期、效果差 | `#EF4444` |
| **蓝紫 · AI/进行中** | 主按钮、进行中步骤、AI 产出内容 | `#6366F1` |
| 中性灰阶 | 文字/边框/背景 | `#0F172A` → `#F8FAFC` 六档 |

**AI 产出内容统一视觉**：浅蓝紫底 + 左侧 2px 竖线 + 右上角 `✨ AI` 小标，且必须配一个 `采纳` / `我改改` 双按钮。用户一眼分得清「这是机器写的」。

### 5.2 组件清单（原型必须包含）

| 组件 | 说明 |
|---|---|
| `StepBar` | 五步进度条，三尺寸（§3.2） |
| `TaskCard` | 待办卡：图标 + 标题 + 一句话说明 + 一个主按钮 + `稍后` |
| `KnowledgeCard` | 看板卡：标题 + StepBar(md) + 负责人头像 + 停留天数 + 效果小徽章 |
| `AIBlock` | AI 产出块（浅蓝紫 + ✨ + 采纳/我改改） |
| `MissingList` | 「还差 N 件事」清单：每行 = 红叉 + 人话描述 + `去处理 →` |
| `UndoBar` | 底部撤销条（10s 倒计时进度线） |
| `DangerDialog` | 危险确认弹窗：标题 + 后果 3 条 + 输入确认（仅回滚/覆盖需输入条目名）+ 红按钮 |
| `EmptyState` | 插图 + 一句话 + 一个主按钮（G7） |
| `Skeleton` | 骨架屏（列表 5 行 / 卡片 3 张 / 详情三段） |
| `ErrorState` | 「出错了 + 人话原因 + 重试」 |
| `PersonPicker` | 指派人选择（头像 + 姓名 + 当前手上几件活） |
| `DiffView` | 改动对照：三种视图（并排 / 合并 / 只看改动）+ 段落级 + 词级高亮 + 信息字段改动区（完整规格见 §12） |
| `BilingualEditor` | 中英逐段对照编辑器（左中右英，按段落锚点对齐，段级英文状态灯）（§11） |
| `HealthCheck` | 上线体检卡：3 项检查，每项 ✓/✗ + 人话 + 修复入口 |
| `VersionTimeline` | 版本时间线：每版一卡（版本号 / 谁 / 何时 / 改动摘要 / 该版效果 / 对比 / 换回去）（§10.2） |
| `VersionCompareBar` | 两版效果对照条：新旧解决率并排 + 差值 + 样本量与置信提示（§10.3） |
| `LangBadge` | 段级英文状态灯：⚪AI 待校对 / 🟢已校对 / 🟡中文改了要重看 / 🔒不翻译 |
| `TagInput` | 「客户会怎么问」标签输入：AI 建议 + 同义归并提示 + 使用频次角标（§13.3） |

### 5.3 文案规范

| 场景 | 规则 | 例 |
|---|---|---|
| 主按钮 | 动词 + 宾语，≤6 字 | ✅「送去审核」❌「提交」 |
| 空态 | 「一句话现状 + 一句话建议」 | 「还没有待办 —— 去看看 AI 发现的 12 个新话题？」 |
| 报错 | 「发生了什么 + 你能做什么」，不出现错误码 | 「推送到 Zendesk 失败了：对方服务暂时没响应。可以点重试，或等 5 分钟系统自动再试一次。」 |
| 阻塞 | 「还差什么 + 去哪补」 | 「还差 1 件事：英文还没人校对 → 去校对」 |
| 危险确认 | 后果写具体，不写「此操作不可撤销」这种空话 | 「下架后：客户搜不到这篇了；Zendesk 上会归档不会删；历史和数据都还在；想再上线，改完重新走一遍审核即可。」 |

#### 6.1.3 待办卡（`TaskCard`）统一结构

```

```
- **主按钮唯一**，文案：`去审核` / `去校对` / `去修改` / `看看怎么回事` / `对比一下` / `去体检` / `去处理`。

- 处理完成后卡片**原地淡出** + 底部撤销条。

等你审 / 被退回 / 英文待校对 / 中文改过英文要重看 / 推送失败 / Zendesk 冲突 / 复核到期 / 效果掉队 / 指派给你的活 / **新版不如老版（建议回滚）** / **内容快到期了** / **新成员接手交接**。

>    第 3 版 61%（样本 84）· 第 2 版 78%（样本 312）· 已观察 7 天
>    ①写✓ ②审✓ ③译✓ ④发✓ ⑤盯●  v3    [看改了哪里] [稍后]
> ```

| 写作中 | `送去审核` | `送去审核` |

| 已下架 | `重新启用` | `重新启用` |
| 推送失败 | 信息条 + `催一下` | `重新推送` |

#### 6.3.4 「还差 N 件事」卡（`MissingList`，G3）
- 只在**当前用户下一步动作被阻塞**时出现，位于头部下方。
- 每条格式：`✗ <人话缺什么>` + `去处理 →`（跳到对应位置并高亮）。
- 三项体检对应人话：
  - 字段没填全 → 「还没说清楚放在哪 / 客户会怎么问」
  - 内部内容没标 → 「有段落是内部口径但没标出来，会漏给客户看到」
  - 英文没校对 → 「英文还没人校对」/「英文标题还空着」
- 全部通过时**不显示这张卡**，改为在主按钮旁一行绿字「体检通过，可以上线」。

#### 6.3.5 正文编辑器
| 规格 | 说明 |
|---|---|
| 布局 | 左中文 / 右英文，**逐段严格对齐**（内部段落的英文格显示「内部内容不翻译，客户看不到」） |
| 工具条 | 加粗 / 斜体 / 删除线 / 小标题 / 列表 / 引用 / 图片 / **🔒 仅客服可见**（段落级开关，是全系统唯一的内部标记入口） |

| 保存 | **自动保存**（停止输入 2 秒 / 切走页面 / 每 30 秒），顶部显示「已保存 · 刚刚」。不设显式保存按钮 |
| 冲突 | 别人同时在改时顶部黄条：「李娜 3 分钟前也改了这篇」+ `看看她改了什么` / `用我的版本`（不出现 409、锁、版本号等词） |

#### 6.3.6 侧栏「这篇的信息」（字段减负）
只保留 6 个用户要填的，其余 AI 填或系统算：

| 字段 | 谁填 | 交互 |
|---|---|---|
| 放在哪（目录 › 章节） | AI 建议 + 人确认 | 下拉，AI 建议项带 ✨ 标 |
| 谁能看 | 人 | 三选一大按钮组：`所有人` / `只有客服` / `大部分公开，少数内部`（选第三项时提示去正文标 🔒） |
| **客户会怎么问** | ✨AI 生成 4–6 条，人可增删 | 标签串。**这是新增字段**，替代旧版「场景一级/二级 + 标签」三个字段——用户想不出分类，但说得出客户怎么问 |
| 适用型号 | 人（默认全型号） | 多选 |
| **要不要英文版** | 人（默认跟随全局设置） | 三选一：`跟随默认` / `要` / `只发中文`（§11.5） |
| **时效性** | 人（默认长期有效） | 二选一：`长期有效` / `有时限` + 失效日期（到期前 7 天自动生成待办，§13.4） |
| 多久体检一次 | 人（默认 180 天） | 三选一：90 / 180 / 365 天 |
| 谁负责这篇 | 人（默认创建者） | PersonPicker |
| 场景（一级/二级） | **系统派生，只读** | 直接等于「目录 › 章节」，以灰字展示「统计时算作：售后与退款 / 退货政策」（§13.2） |
| 也会在这些场景被问到 | 人（可空，≤3 个） | 次要场景多选，**只影响统计与推荐，不影响存放位置和 Zendesk 结构**（§13.2） |
| ~~条目类型 / 场景一级 / 场景二级 / 标签~~ | **不再让人填**：场景由目录派生，标签合并为「客户会怎么问」 | — |
| 一句话摘要 | ✨AI 生成 | AIBlock，`我改改` 后不再被覆盖，显示「你改过，AI 不会再动它」 |

> 侧栏所有字段**随版本快照**：改了目录、改了「谁能看」、增删了问法标签，都会出现在改动对照的「信息改动」区（§12.3），并需要过审。

#### 6.3.8 页签「效果」（按版本看）

顶部一行口径开关：`看当前版（v3）`（默认）/ `看历史全部` / `按版本对比`。这一行是回滚决策的入口，不可省。

- 四个大数字卡：被引用次数 / 命中率 / 解决率 / 采纳率，每个带一句人话解释（如「客户问相关问题时，有 78% 的情况找到了这篇」），**数字下方标明统计口径「第 3 版上线至今 3 天」**。
- `按版本对比` 模式：一张折线图，**横轴按版本分段**（每次上线画一条竖虚线并标 `v3 上线`），一眼看出「哪次改动把数据改差了」；下方配 `VersionCompareBar`（§10.3）。
- 样本 <10：整块替换为「刚上线不久，数据还不够，再等等」+ 已积累样本数。
- 解决率 <60%：顶部红条「这篇效果不太好」+ 三条 AI 给的可能原因（内容太长 / 没覆盖客户真正问的 / 标题不好搜）+ `照建议修改`。
- **新版不如老版时**（判定见 §10.3）：顶部红条换成「改完之后反而变差了：第 3 版 61%，第 2 版 78%」+ 两个按钮 `看改了哪里` / `把 v2 换回去`。
- 「客户反馈原声」列表：被踩、客服标记、追问原文摘录（每条带来源渠道 + **当时是哪一版**）。原声展示前统一脱敏（手机号 / 邮箱 / 订单号自动打码，§13.5）。

#### 6.3.9 页签「相关」（新增）

把之前漏掉的「这篇和谁有关系」集中到一处：

| 区块 | 内容 |
|---|---|
| 相关文章 | 人工添加 + AI 推荐（带相似度理由），上线时同步为 Zendesk 的相关文章 |
| 谁引用了这篇 | 反向引用列表。**下架前必查**：有人引用时，下架确认弹窗多一条后果「有 3 篇文章链到了这里，会变成断链」+ 清单 |
| 图片与附件 | 这篇用到的图（中/英两套，§11.6），显示「这张图还被另 2 篇用着」 |
| 客户怎么搜到它的 | 帮助中心真实搜索词 Top10（来源搜索词回流，§14.2 环①），可一键加入「客户会怎么问」 |

不是新页面，而是详情页的**审核浮层**：
```
┌── 审核《摄像头离线了怎么办》──────────────────────────────┐
│ 李娜 提交 · 2 小时前 · 这将成为第 4 版（线上现在是 v3）      │

│ [只看改动 ▾] [中文|英文|两边都看]  改动对照（§12）           │
│ ❗ 信息改动 2 处：目录 退货政策 → 退款到账 · 新增问法「固件」 │
│ ─────────────────────────────────────────────────────────  │
│ 参考：线上 v3 解决率 61%（样本 84）· 历史最佳 v2 78%        │
│ 上线体检：✓ 信息填全了  ✓ 内部内容标好了  ✗ 英文还没校对    │
│ ─────────────────────────────────────────────────────────  │
│              [通过]        [退回改改]                       │
└─────────────────────────────────────────────────────────────┘
```
- `通过`：直接过 + 撤销条；若体检全绿且我有上线权，通过后**顺手问一句**「要现在就上线吗？」`马上上线` / `待会儿再说`。
- `退回改改`：展开理由输入（**必填**，placeholder 给范例）+ 可选「勾出有问题的段落」（在 diff 上直接圈选，退回后作者能看到高亮）→ 退回后自动生成作者的待办。

- **信息改动必须单独呈现**：正文没改但改了目录/可见性/问法标签，也要能审——这类改动同样进「审」，浮层里以独立区块列出「改前 → 改后」。
- 审核意见支持**挂在段落上**（在改动对照里选中某段 `留个意见`），退回后作者在编辑器里看到同位置批注气泡，点一下即跳。

#### 6.4.2 建议卡三类

| 类型 | 触发来源 | 主按钮 | 采纳后 |
|---|---|---|---|
| 📝 **该写新的** | 对话里高频出现（≥10 次）且库里查不到相似内容 | `用这个草稿开写` | 带 AI 草稿进入 W1 向导第 2 步，来源标记「AI 发现」 |
| 🔧 **该改现有的** | 文章被踩 / 客服标记 / 对话里出现与文章冲突的说法 / 解决率跌破 60% | `去改这篇` | 打开该条目详情并进入「写」，AI 意见以批注形式挂在相关段落旁 |
| 🔍 **标题不好搜** | 帮助中心搜索无结果关键词，但库里其实有对应内容 | `改个好搜的标题` | 打开条目，AI 建议的新标题与「客户会怎么问」预填在侧栏，一键采纳 |

#### 6.4.3 卡片必备三要素（可信度设计）
1. **AI 为什么这么判断**——必须写清依据（被问了多少次、相似度多少、跟哪句话冲突）。
2. **客户原话**——至少 2 条真实摘录，可展开全部，点击可跳 Zendesk 原工单。
3. **一键可用的产物**——不是只给结论，要给草稿/新标题/改动建议，用户点一下就能用。

#### 6.4.4 交互规则
- `不用了` = 直接消失 + 撤销条；**同一话题下次达到阈值会再出现**（卡片底部小字注明，避免用户以为永久删了）。
- 采纳率统计显示在页头（「你采纳了 68% 的建议」），低于 30% 时页头出现一行：「建议不太准？告诉我们哪里不对 →」收集反馈。
- AI 不可用时（模型没配/失败）：**整页顶部诚实告知**——「AI 分析暂时不可用（<原因>），下面是按关键词粗略统计的结果，仅供参考」，不假装正常。
- `重新分析`：手动触发，按钮上标注上次分析时间；执行中显示进度「正在读取 47 通对话… 12/47」。

#### 6.4.5 四态
- 空：「AI 还没发现值得做的事——说明现有知识覆盖得不错 👍」+ 副行「下次分析：今晚 6 点」+ 次按钮 `立即分析`。
- 空（从未跑过）：「还没连上客服对话数据」+ `去设置里连接 Zendesk`（管理员）/「让管理员配置一下」（其他角色）。
- 加载：3 张骨架卡。
- 出错：错误态 + 重试 + 「上次成功的结果（3 天前）」入口。

- `+ 邀请成员`：只填姓名 + 邮箱 + 选角色 + 选范围，**系统生成初始密码并提示首登改密**。
- `停用`：危险确认，后果三条（会话立刻失效 / 历史留痕和内容全保留 / 随时可恢复）。
- 底部「分工设置」区（对应 §2.2）：团队规模三选一；选「分工明确」时展开三个 PersonPicker——**审谁做 / 译谁做 / 发谁做**（默认负责人，新条目自动派活）。

#### 6.6.2 P7 操作留痕
- 顶部一行说明：「所有操作都记在这里，谁也删不掉。」
- 筛选：时间范围 / 谁做的 / 做了什么（四类：写东西 / 审和发 / 管人 / 系统自动）/ 关键词。
- 每行一句**自然语言**：`王琳 2 小时前 通过了《摄像头离线怎么办》的审核`，右侧 `看详情` 展开改前改后。
- 非管理员/非主编只能看到与自己相关的记录，顶部注明「你只能看到和你有关的记录」。
- 导出 CSV（管理员）。

#### 6.6.3 P8 设置（管理员）
七张设置卡，全部**开箱即用默认值**，用户不配也能跑（后三张为 v2.1 新增）：

| 卡 | 内容 |
|---|---|
| **连接 Zendesk** | 连接状态大徽章（🟢已连接 / 🔴未连接）+ 子域名 + `测试连接`；未连接时给三步引导。**不暴露 token 明文**，只显示后 4 位 |
| **AI 能力** | 三个开关：AI 起草 / AI 翻译 / AI 分析对话；每个显示当前状态（可用 / 未配置密钥 / 最近失败 3 次）。**未配置时明确写「没配密钥，这些功能会退化成人工，不影响主流程」** |
| **团队与分工** | 同 §6.6.1 底部（此处为主入口） |
| **提醒规则** | 多久算「该体检」（90/180/365）、解决率低于多少算「拖后腿」（默认 60%）、待办催办阈值（默认 3 天）、**回滚建议阈值**（默认：上线 ≥7 天 + 样本 ≥30 + 低 ≥10pp，§10.3）；每项带「推荐值」标记 |
| **语言** | `新条目默认要英文`（开/关）、`AI 自动翻译`（开/关）（§11.5） |
| **固定译法表** | 中文词 / 英文译法 / 备注 / 是否强制；开箱预置产品与品牌词（§11.7） |
| **问法词典** | 全部「客户会怎么问」标签 + 使用次数 + 合并/重命名 + 冷却清理建议（§13.3） |

## 7. 向导规格

### 7.0 向导通用规范

| 规则 | 说明 |
|---|---|
| 形态 | 居中模态 880px（W3 上线向导 640px），遮罩不可点关闭（防误触丢内容） |
| 顶部 | 步骤条（`①说清楚 ─ ②写内容 ─ ③补信息 ─ ④送审`）+ 右上 `×`（关闭时若有内容，问「存成草稿还是丢掉？」） |
| 底部 | 左 `上一步`（文本按钮）/ 右主按钮（**必须带下一步内容**，如 `下一步：写内容`）；最后一步主按钮是终态动词 |
| 随时可退出 | 任何一步都自动存草稿，退出后在「知识资产 › 写」列能找到 |
| 键盘 | `Enter` 下一步、`Esc` 询问退出 |
| 不做的事 | 不在向导里做复杂编辑（正文只做粗稿，精修去详情页）；不在向导里问用户答不上来的问题 |

### 7.1 W1 · 新建知识向导（4 步）

**入口**：`+ 新建知识 → 我自己写 / 让 AI 帮我写`、AI 建议卡 `用这个草稿开写`、目录页 `在这里新建`。

#### 步骤 ① 说清楚要写什么
```
你想写什么？
┌────────────────────────────────────────────────────┐
│ 客户会怎么问这个问题？                              │
│ [ 太阳能板阴天充不满电怎么办                      ] │
│ 💡 用客户的话，别用内部术语。比如写「摄像头没电了」 │
│    而不是「电源模块异常」                          │
└────────────────────────────────────────────────────┘
✨ 检查了一下：库里没有类似内容，可以放心写
   （若有相似）⚠️ 库里已经有《太阳能板安装》和这个有点像 —— 
              [看看那篇] [还是新建一篇] [改那篇就行]

                                    [下一步：写内容 →]
```
- **只问一个问题**，输入即标题。
- 实时**重复检查**（防呆核心）：相似度 ≥0.85 时**不给直接新建**，强制三选一，避免重复建条目。
- 检查不可用时如实说「重复检查暂时用不了，可能会撞车」，不阻塞。

#### 步骤 ② 写内容
```
[✨ 让 AI 先起个草稿]  ← 大按钮，点了 3 秒出草稿
或者直接自己写：
┌────────────────────────────────────────────────────┐
│  富文本编辑器（工具条含 🔒 仅客服可见）             │
│  ✨ AI 草稿会以浅蓝底出现，逐段带 [用这段] [删掉]   │
└────────────────────────────────────────────────────┘
💡 写不下去？试试回答这三个问题：为什么会这样 / 怎么解决 / 什么情况要联系客服
                          [← 上一步]  [下一步：补信息 →]
```
- AI 起草：按标题 + 相似条目 + 客户原话生成 3–5 段，**逐段可采纳可删**，不是一坨全塞。
- 引导问句随条目类型变化（问题排查类 / 政策说明类 / 操作步骤类，由 AI 判断）。
- 空内容不允许进下一步，提示「至少写点什么，哪怕一句话也行」。

#### 步骤 ③ 补信息（AI 全预填）
```
我帮你填好了，看看对不对：
  放在哪    [售后与退款 › 退货政策 ▾]        ✨ AI 建议
  谁能看    ( ) 所有人  (•) 大部分公开，少数内部  ( ) 只有客服
            ↑ AI 发现你有 1 段标了「仅客服可见」，所以选了这个
  客户会怎么问  [太阳能充电慢 ×] [阴天没电 ×] [板子坏了 ×] [+ 加一个]  ✨
  适用型号  [全型号 ▾]        多久体检一次  [180 天 ▾]
                          [← 上一步]  [下一步：送审 →]
```
- **全部预填，用户只做确认**（G3 精神）。每个 AI 填的项带 ✨ 并说明理由。
- 不做必填校验轰炸：缺项时在字段旁一行黄字提示，不拦截；真正拦截发生在「上线体检」。

#### 步骤 ④ 送审
```
准备好了吗？
  ✓ 内容写了 5 段（含 1 段仅客服可见）
  ✓ 信息填全了
  · 英文：送审通过后系统会自动翻译，到时候需要你校对一下

  这篇会交给 [王琳 ▾] 审核，大概 1 天内有结果

     [先存草稿，待会儿再说]        [送去审核]
```
- 展示**清单式确认**，不是空白确认。
- 审核人可改（默认走分工设置）。
- 点 `送去审核` → 关闭向导 → 回到「今日待办」→ 顶部绿条「已送审，等王琳处理」+ 撤销条。

### 7.2 W2 · 批量导入向导（3 步）

| 步 | 内容 |
|---|---|
| ① 把文档给我 | 大拖拽区「把 Word / Markdown / txt 拖进来，或点击选择」+ 「也可以直接粘贴文字」文本域。支持多文件。说明一句：「我会自动按标题切成一篇一篇，一次最多 500 篇」 |
| ② 看看切得对不对 | 左侧切出来的条目列表（可勾选/取消），右侧预览选中条目；每行可改标题、改放哪（**AI 预填目录**）、改谁能看；顶部统计「切出 23 篇 · 其中 4 篇疑似重复 [只看重复]」；重复项默认**不勾选**并标注「库里已有《XX》」 |
| ③ 导进来 | 确认条「23 篇会全部进审核队列，需要人过一遍才会上线」+ 主按钮 `导入 19 篇`（只导勾选的）；执行进度条；结果页：成功清单 + 失败清单（带原因和原文片段）+ `去审核这批` / `再导一批` |

- 导入产物**一律进「审」这一步**（铁律①），结果页明确写出来。
- 失败不影响成功项，逐条报原因。

### 7.3 W3 · 上线向导（3 步，主编）

```
① 体检                    ② 英文确认              ③ 上线
✓ 信息填全了              左中右英对照最终稿       将要发生：
✓ 内部内容标好了          [英文没问题，上线]       · 客户 3 分钟内能搜到
✓ 英文已校对                                       · 中英文各推一篇
  全部通过 ✅                                      · 内部段落不会推出去
                                                   [确认上线]
```
- 若体检有不通过项：向导**停在第 ① 步**，展示 MissingList，每条带 `去处理`；不显示「下一步」。
- 第 ② 步是**最后一道人工闸**（铁律②的界面落点），必须人点一次。
- 第 ③ 步执行后：进度反馈（「正在推送… 中文 ✓ / 英文 推送中」），成功后给 `在 Zendesk 上看看 →` 直达链接。
- 第 ③ 步文案必须告知版本变化：「上线后这就成为**第 4 版**，第 3 版会存进历史，随时能换回来」——让用户敏于版本、也安心改动（§10.1）。
- 上线成功即**冻结新版本**并开始按该版采集效果数据；若只推成功一侧语言，不冻结版本，转「推送失败」待办（避免半截版本）。
- 推送失败：不回滚状态，转为待办「推送失败」并给人话原因 + `重试`。

### 7.4 W4 · 定期复核向导（2 步）

**入口**：待办卡「《XX》该体检了」。

| 步 | 内容 |
|---|---|
| ① 还准不准？ | 左：文章正文；右：**AI 体检报告**——「这篇上线 180 天，被引用 234 次，解决率 78%；发现 2 处可能过时：①提到的『15 天退款』与最近 12 通对话里客户说的『7 天』不一致 ②引用的固件版本已经过时」。三个大按钮：`还准，继续用` / `要改，我来改` / `过时了，下架` |
| ② 确认 | 选「还准」→ 复核期重置 180 天 + 留痕，一步完成；选「要改」→ 进详情页「写」；选「下架」→ 危险确认弹窗 |

## 8. 傻瓜化 15 条法则（原型生成时逐条自检）

| # | 法则 | 反例 → 正例 |
|---|---|---|
| 1 | **一屏一个主按钮** | 详情页并排「保存/提交/发布/下线」四个按钮 → 只留当前该做的那一个，其余收进 `⋯` |
| 2 | **按钮说人话** | 「提交」→「送去审核」；「同步」→「上线到帮助中心」 |
| 3 | **不给灰按钮，给清单** | 灰掉的「发布」+ tooltip → 「还差 1 件事：英文没人校对 [去校对]」 |
| 4 | **撤销优于确认** | 每个动作都弹确认框 → 直接执行 + 10 秒撤销条。**仅 4 个动作保留确认**：下架、回滚版本、覆盖 Zendesk 上别人的修改、停用成员 |
| 5 | **AI 先填，人只改** | 空白表单 8 个必填 → AI 预填全部，人做确认题；每个 AI 填的项带 ✨ 和填写理由 |
| 6 | **系统主动派活** | 用户自己去各页面巡检 → 12 类事件自动生成待办进收件箱（§9） |
| 7 | **零术语** | 「同步状态：blocked」→「暂时不能推送到 Zendesk：英文还没人校对」 |
| 8 | **进度永远可见** | 用户不知道条目卡在哪 → 五步进度条 + 「等谁 · 等多久」全局强制 |
| 9 | **防呆前置** | 建完才发现重复 → 建之前就查重并强制三选一 |
| 10 | **错误给出路** | 「操作失败」→「推送失败了：Zendesk 暂时没响应。[重试] 或等 5 分钟系统自动再试」 |
| 11 | **默认值能跑** | 让用户先配一堆才能用 → 所有设置都有推荐默认值，不配也能完成全流程 |
| 12 | **诚实标注降级** | AI 挂了却装作正常 → 「AI 分析暂时不可用，下面是粗略统计，仅供参考」 |
| 13 | **改动永远可退**（新增） | 「发布即终局」→ 每次上线都冻结一版，任何时候能看「改了哪里」、能一键换回老版（§10） |
| 14 | **不拿小样本吓人**（新增） | 「解决率 40%，效果差！」（其实只有 5 次）→ 样本不足统一显示「数据还不够，下不了结论」（§10.3） |
| 15 | **分类不让人想**（新增） | 让用户填一级/二级分类 + 标签 → 场景由目录派生、标签只问「客户会怎么问」（§13） |

## 10. 版本管理与回滚（重点补回）

> 心智模型见 §3.4。本节是**页面级落地规格**。核心命题：*用户改了一版，效果反而变差了，系统要能让他毫不费力地发现、看清、退回去。*

### 10.1 版本何时产生（唯一入口）

| 动作 | 是否产生新版本 | 说明 |
|---|---|---|
| 自动保存 / 编辑草稿 | ❌ | 只在草稿里滚动保存，界面显示「正在改的（还没上线）」 |
| 送审 / 审核通过 | ❌ | 仍是草稿，只是流转到下一步 |
| **上线成功（推 Zendesk 成功）** | ✅ **冻结为 vN** | 同时开始按该版本采集效果数据；旧的 current 转为 history |
| 回滚 | ✅ 新增 vN+1（内容 = 老版） | 见 §10.4 |
| 下架 | ❌ | current 保留但标「已下架」，效果数据停止累计 |
| Zendesk 侧被人改后「把对方改动收回来」 | ✅（走一遍写→审→发） | 不允许绕过审核直接成版（铁律①） |

> **为什么不在保存时就发版本**：用户改十次存十次，产生十个版本 = 版本列表变垃圾场，效果数据也无法归属。**只有客户真正看到过的内容才配拥有版本号**——这也是「效果数据挂版本」能成立的前提。

### 10.2 版本时间线（P3 › 版本与改动，组件 `VersionTimeline`）

页面结构见 §6.3.7。补充规格：

| 规格 | 说明 |
|---|---|
| 排序 | 倒序，current 置顶 |
| 每卡字段 | 版本号 / 作者 / 上线时间 / 在线时长 / 动作类型 / AI 改动摘要（1 句）/ 改动处数 / 该版效果（解决率 + 样本）/ 中英是否齐全 |
| 动作类型贴纸 | `首发` / `例行修改` / `按 AI 建议改的` / `从 v2 换回来的` / `Zendesk 冲突合并` / `批量导入` —— **来源可追溯**，用于事后复盘「AI 建议到底靠不靠谱」 |
| 最佳版高亮 | 🏆 历史解决率最高且样本 ≥30 的那版，永远显示在顶部提示条 |
| 对比 | 勾选任意两版 → 全屏 DiffView；未勾选时单卡 `看改了哪里` = 对上一版 |
| 权限 | 编辑：可看、可对比、不可回滚；主编：全部；管理员：只读 |
| 保留策略 | 全量保留不清理。>20 版时折叠中间部分为「中间还有 12 版 ▾」 |

### 10.3 版本效果对照与「该回滚了」判定（`VersionCompareBar`）

```
┌────────────────────────────────────────────────────────────┐
│ 第 2 版          vs         第 3 版（现在线上）             │
│ 解决率 78%  ████████████     解决率 61%  ████████           │
│ 样本 312 · 在线 40 天        样本 84 · 在线 7 天            │
│ 采纳率 71% → 55%   被踩 3 → 11                              │
│ 🔴 结论：第 3 版明显不如第 2 版（差 17 个点，数据已足够）    │
│                [看改了哪里]      [把第 2 版换回去]          │
└────────────────────────────────────────────────────────────┘
```

**判定规则（同时满足才提示回滚，避免误报）**

| 条件 | 阈值 | 理由 |
|---|---|---|
| 新版在线时长 | ≥7 天 | 给新版足够曝光 |
| 新版样本量 | ≥30 次引用 | 小样本不下结论（法则 14） |
| 解决率差距 | 比历史最佳版低 ≥10pp | 低于此视作波动 |
| 对照版样本量 | ≥30 | 老版数据本身也要可信 |

- 三档结论文案：`数据还不够，下不了结论`（灰） / `差不多，看不出区别`（灰） / `第 3 版明显不如第 2 版`（红）。
- 满足红档 → 自动生成待办 #10（§9），派给主编 + 条目负责人，**每条目每 30 天最多提醒一次**。
- 反向也提示：新版明显更好时，卡片显示绿字「这次改得好，比上一版高 12 个点」，用于正反馈（不生成待办）。

### 10.4 回滚（M8，危险动作之一）

**语义**：回滚 = **把老版内容重新上线，生成一个新版本**，不是删除新版。

```
v1 → v2 → v3(差) → v4（内容 = v2，动作类型「从 v2 换回来的」，current）
                    v3 标记为「这版被撤下了」
```

**M8 确认弹窗**
```
┌── 把第 2 版换回去？ ──────────────────────────────────┐
│ 会发生什么：                                          │
│ · 客户 3 分钟内看到的就是第 2 版的内容（中英一起换）   │
│ · 这会生成第 4 版，第 3 版不会删，随时还能换回来       │
│ · 第 3 版这 7 天的数据会保留，记在第 3 版名下          │
│ · 这件事会记在留痕里，并通知李娜（第 3 版作者）        │
│ 对照：v2 解决率 78%（312 次） / v3 61%（84 次）        │
│ 输入条目名确认：[                    ]                 │
│                        [取消]   [换回第 2 版]          │
└────────────────────────────────────────────────────────┘
```

| 规则 | 说明 |
|---|---|
| 谁能做 | 仅主编。编辑只能「告诉主编」 |
| **要不要重新过审** | **不需要**——该版本历史上已经审过、也上线过，回滚是恢复既有已审内容，**不破铁律①**。但必须：留痕 + 通知原作者 + 在时间线标「从 v2 换回来的」 |
| 中英一起回 | 回滚回的是整版快照，英文同回，避免中英错位（§3.4.1） |
| 回滚后想接着改 | 基于 v4 继续写 → 走完整五步。界面提示「你现在改的是第 2 版的内容」 |
| Zendesk 侧 | 文章 id 不变，等同一次更新推送；失败则转「推送失败」待办，不留半截状态 |
| 连续回滚保护 | 同一条目 24 小时内第二次回滚时，弹窗加一行「这篇今天已经换过一次版本了，确定还要换？」 |

### 10.5 版本与其他机制的关系（避免设计打架）

| 机制 | 与版本的关系 |
|---|---|
| 上线体检 | 体检针对**待上线的草稿**，通过后才允许冻结成版 |
| 定期复核（W4） | 复核对象是 current 版；选「还准」→ 只重置复核期，**不产生新版本** |
| Zendesk 漂移 | 对比基准 = current 版内容；「以我们为准」= 重推 current，不产生新版 |
| AI 建议「该改现有的」 | 采纳后基于 current 派生草稿，版本类型记为「按 AI 建议改的」，便于统计 AI 建议的真实收益 |
| 效果数据看板（P5） | 「拖后腿」榜单按 current 版计算；点进去能立刻看到是否「换个老版就好了」 |

## 11. 语言配置与双语模型

> 回答：**中文和英文到底怎么配、怎么改、怎么保持不错位。**

### 11.1 三条原则

| 原则 | 说明 |
|---|---|
| **中文是源，英文是派生** | 只在中文侧组织结构（段落、顺序、内部标记）。英文永远跟着中文段落走，不允许英文单独增删段 |
| **段落级对齐，段落级状态** | 每段有稳定锚点，中英按锚点配对。改了第 3 段中文，**只有第 3 段英文变「要重看」**，不是整篇作废 |
| **英文不单独发版** | 中英同属一个版本（§3.4） |

### 11.2 段落级英文状态（`LangBadge`）

| 状态 | 界面 | 何时产生 |
|---|---|---|
| ⚪ AI 待校对 | 「机器翻的，还没人看过」 | AI 翻译产出 |
| 🟢 已校对 | 「有人看过了」 | 人点了这段的「这段没问题」或手改过 |
| 🟡 中文改了要重看 | 「中文改过了，这段英文要重看」 | 对应中文段落内容变化 |
| 🔒 不翻译 | 「内部内容，不翻译也不推送」 | 该段标了「仅客服可见」 |

**上线体检的英文项**：所有非 🔒 段落都是 🟢 时才算通过。体检文案：「英文还差 3 段没人看过 → 去校对」（**直接说差几段**，比「英文未确认」有用得多）。

### 11.3 英文校对页（「译」这一步的落点）

```
┌── 校对英文《摄像头离线了怎么办》         已校对 8/12 段 ────┐
│ [只看还没看的（4）]  [全部看]      [✨ 重新翻译还没校对的]   │
├──────────────────────┬───────────────────────────────────┤
│ 中文（只读）          │ 英文（可编辑）                     │
│ 摄像头离线通常由…    │ Camera offline is usually caused… │
│                      │ ⚪ [这段没问题]  [我改改]           │
├──────────────────────┼───────────────────────────────────┤
│ 🔒 内部：先查工单…   │ 内部内容不翻译，客户看不到          │
├──────────────────────┼───────────────────────────────────┤
│ 固件升级后需重启…    │ After firmware upgrade…  🟡        │
│ （中文 3 天前改过）  │ 上次校对的英文：[看一眼旧的 ▾]      │
└──────────────────────┴───────────────────────────────────┘
       全部校对完 → 底部出现主按钮 [英文校对完了]
```

| 规格 | 说明 |
|---|---|
| 进度 | 顶部「已校对 8/12 段」，进度条实时更新，给可完成感 |
| 逐段确认 | 每段一个 `这段没问题`（点一下变 🟢）；改过的自动变 🟢 |
| 一键 | `全部标为没问题` 仅在 ≤3 段未校对时出现，防止一键糊弄整篇 |
| 🟡 段落 | 显示「上次校对的英文」可展开对照，避免推倒重来 |
| 术语高亮 | 命中固定译法表的词高亮，悬浮显示「产品词：Solar Panel（固定译法）」；改成别的译法时黄字提醒（§11.7） |
| 标题与摘要 | 页面顶部单独一栏校对英文标题、英文摘要、英文问法标签，与正文同一进度计入 |
| 完成 | 全部 🟢 → 主按钮 `英文校对完了` → 进入「发」 |

### 11.4 阅读态的语言切换

详情页头部三切片 `中英对照` / `只看中文` / `只看英文`（记忆选择）。看板/列表默认显示中文标题，英文缺失时标题右侧一枚 `EN` 灰徽章表示「英文还没齐」。

### 11.5 「要不要英文版」的条目级配置

| 取值 | 行为 |
|---|---|
| `跟随默认`（默认） | 用设置里的全局开关（默认：要英文） |
| `要` | 走完整五步，英文未校对不能上线（铁律②） |
| `只发中文` | 「译」这一步显示为跳过态：`③译 —（这篇只发中文）`，上线只推中文站；卡片标灰徽章「只中文」。**选择原因必填一句话**，记入留痕，防止被滥用来绕过铁律② |

全局设置（P8 › AI 能力 / 语言）：`新条目默认要英文`（开/关）、`AI 自动翻译`（开/关，关掉则英文靠人写）。

### 11.6 图片与附件的双语（之前完全没考虑）

| 规则 | 说明 |
|---|---|
| 一图两版 | 带界面文字的截图需中英两张；上传中文图时提示「这张图里有中文界面，要不要传一张英文版？」（可选，不阻塞） |
| 未提供英文图 | 英文文章沿用中文图 + 图注英文化，体检不拦截，但在校对页标黄「这张图是中文界面」 |
| 媒体库 | 图片统一入库，替换一张图会影响所有引用它的条目，替换前提示「另有 2 篇在用」 |
| 推送 | 上线时图片随文上传到 Zendesk，失败按「推送失败」处理并指明是哪张图 |

### 11.7 固定译法表（Glossary，新增）

- 位置：`运营中心 › 设置 › 固定译法表`。
- 内容：中文词 / 英文译法 / 备注（如「产品名，不加复数」）/ 是否强制。
- 作用：AI 翻译时强制套用；校对页高亮；违反强制译法时校对页黄字提示（不拦截）。
- 开箱预置：产品线名称、功能名、品牌词。
- 为什么重要：这是**双语一致性最便宜的保障**，否则同一功能出现三种译法，客户与 AI 检索都会乱。

## 12. 改动对照（Diff 视图规格）

> 参考 Git diff 的信息密度，但去掉全部工程气息：**不显示行号、不显示 hunk、不显示 +/- 符号，只显示「第几段 · 什么小标题 · 改了什么」。**

### 12.1 三种视图

| 视图 | 何时默认 | 说明 |
|---|---|---|
| **只看改动**（默认） | 审核、版本对比 | 未改动段落折叠成一行「省略 6 段没改的 ▾」，只展开改动段及其上下文一段 |
| **并排对照** | 大屏（≥1280px）默认 | 左「改前」右「改后」，同段落横向对齐，滚动同步 |
| **合并视图** | 窄屏 / 移动端默认 | 改前段落（浅红）紧跟改后段落（浅绿），上下相邻 |

切换器统一在左上角：`[只看改动 ▾] [并排 | 合并]`。

### 12.2 高亮粒度

| 粒度 | 呈现 |
|---|---|
| 段落级 | 整段新增 = 浅绿左边条 + 「新增第 4 段」；整段删除 = 浅红 + 删除线 + 「删掉了原第 5 段」 |
| **词级** | 段内修改时只高亮变化的词/短句（红底删除、绿底新增），其余正常显示 —— 用户一眼看清「15 天 → 7 天」 |
| **移动识别** | 段落只是换了位置 → **不显示为一删一增**，显示为紫色标记「这段挪到了第 2 段前面」 |
| 格式改动 | 只改了加粗/列表等格式 → 折叠为一行「第 3 段只改了排版」，默认不展开（降噪） |
| 内部段落 | 带 🔒，底色不同，并注明「这段客户看不到」 |

### 12.3 「信息改动」区（关键补充）

正文之外的字段改动必须同样可审、可追溯，独立区块置于正文改动之上：

```
❗ 信息改动（3 处）
  放在哪        售后与退款 › 退货政策  →  售后与退款 › 退款到账
  客户会怎么问  + 固件升级失败   − 板子坏了
  谁能看        所有人  →  大部分公开，少数内部
```

覆盖字段：目录位置、谁能看、客户会怎么问、适用型号、时效性、体检周期、负责人、标题、摘要、相关文章、图片替换。

### 12.4 语言维度

顶部一组切片：`中文` / `英文` / `两边都看`。「两边都看」= 上下两块，分别是中文改动与英文改动，便于审核判断「中文改了英文有没有跟上」。英文块顶部显示段级状态汇总（🟢8 🟡3 ⚪1）。

### 12.5 三处复用同一组件

| 场景 | 左（基准） | 右（对照） | 附加动作 |
|---|---|---|---|
| 审核（M2） | 线上 current 版 | 待审草稿 | 段落上 `留个意见`；`通过` / `退回改改` |
| 版本对比（M7） | 选中的旧版 | 选中的新版 | `把左边这版换回去`（主编） |
| Zendesk 冲突（待办 #6） | 我们这边（current） | Zendesk 上现在的 | `以我们的为准（覆盖对方）` / `把对方改动收回来` / **`挑几段收回来`（逐段勾选合并）** |

> 「挑几段收回来」是之前缺的一环：现实中同事在 Zendesk 上只改了一段，全盘二选一太粗暴。逐段勾选后生成草稿 → 仍需走「审」。

### 12.6 空态与降级
- 两版内容完全相同（只有信息字段变了）：正文区显示「正文一个字都没改，只改了信息」。
- 改动过大（>80% 内容变化）：顶部提示「这次几乎是重写了，建议直接看全文」+ 默认切到「看全文」。
- AI 改动摘要不可用时：显示「改了 4 处（摘要暂时生成不了）」，不影响 diff 本身。

## 13. 元数据与分类体系（想清楚版）

> 回答用户的两个问题：**(a) 该不该有问题标签？(b) 问题的一二级分类跟不跟目录走？**

### 13.1 结论先行

**分成两个正交维度，各管各的，绝不让用户填两遍：**

| 维度 | 是什么 | 谁维护 | 用途 | 基数 |
|---|---|---|---|---|
| **存放位置**（结构维度） | `目录 › 章节`，**一篇只能在一处** | 人（AI 建议） | 浏览导航、Zendesk Category/Section 映射、权限范围、**统计聚合的一二级场景** | 固定两级，目录 ~8 个、章节 ~40 个 |
| **问法标签**（检索维度） | `客户会怎么问`，**多对多** | AI 生成 + 人增删 | AI 检索召回、搜索、缺口分析、Zendesk labels | 每篇 4–6 条 |

### 13.2 (b) 一二级分类跟着目录走 —— 是，但补一个「次要场景」

**为什么跟着目录走**：
1. 一二级分类的真实用途只有一个——**统计聚合**（覆盖率、缺口按场景看）。而目录本身就是按客户场景组织的树，两套并行必然对不齐，最后谁都不信。
2. 让用户在「放哪个目录」之外再选一次「属于哪个场景」，是**同一件事问两遍**，违反法则 15。
3. Zendesk 侧只有 Category/Section 两级，目录已与之一一映射；再造一套分类就要额外维护映射表。

**所以**：`场景一级 = 目录`，`场景二级 = 章节`，系统派生、界面只读（侧栏灰字展示，让用户知道统计口径）。

**补丁——次要场景**：一篇文章确实可能被多个场景问到（「退货运费」在「退货政策」和「运费说明」都会被问）。因此允许填「也会在这些场景被问到」（≤3 个章节）：
- **只影响**：缺口统计的分母、AI 检索的场景过滤、相关推荐。
- **不影响**：存放位置、Zendesk 结构、目录树中的显示位置（避免一篇文章出现在两个地方造成困惑）。

### 13.3 (a) 该有问题标签 —— 就是「客户会怎么问」，但必须治理

**该有**。理由：目录解决「东西放哪」，解决不了「客户用什么话找它」。AI 检索和站内搜索吃的是后者。

| 治理规则 | 说明 |
|---|---|
| **只问人话** | 输入引导：「用客户的原话，比如『摄像头没电了』，不要写『电源模块异常』」 |
| AI 预填 | 建条目时 AI 从相似对话里生成 4–6 条；上线后持续从真实搜索词/对话里推荐新问法（详情页「相关」页签一键加入） |
| **同义归并** | 输入时实时提示「库里已有相近问法『摄像头没电』，用它？」——避免标签爆炸（这是自由标签体系必死的坑） |
| 问法词典 | `运营中心 › 设置 › 问法词典`：查看全部问法、使用次数、合并/重命名（合并后同步更新所有引用条目，留痕） |
| 冷却清理 | 90 天零命中的问法灰显，词典里给 `清理建议` 批量删除入口 |
| 上限 | 每篇 ≤10 条，超出时提示「问法太多反而不准，挑最典型的」 |
| 与 Zendesk | 上线时派生为文章 labels（中英各一套）；英文问法在校对页一并校对 |

### 13.4 其余元数据全清单（含新增项）

| 字段 | 人填/派生 | 作用 | 备注 |
|---|---|---|---|
| 标题（中/英） | 人 | 展示、搜索 | 英文标题空 = 体检不过 |
| 一句话摘要（中/英） | AI | AI 检索、列表预览 | 人改过后 AI 不再覆盖 |
| 放在哪 | 人 | 结构 | 见 13.1 |
| 客户会怎么问 | AI + 人 | 检索 | 见 13.3 |
| 也会在这些场景被问到 | 人（可空） | 统计/推荐 | 见 13.2 |
| 谁能看 | 人 | 可见性 + 内部段落 | 三选一 |
| 适用型号 | 人 | **AI 检索过滤**（客户报型号时优先匹配） | 默认全型号 |
| **时效性** | 人 | 促销/活动类内容到期自动提醒 | `长期有效` / `有时限 + 失效日期`；到期前 7 天生成待办 #11；过期后在列表标红「已过失效日期」，**不自动下架**（避免误伤） |
| 多久体检一次 | 人 | 复核节奏 | 90/180/365 |
| 谁负责这篇 | 人 | 派活、交接 | 成员停用时触发待办 #12 |
| 来源 | 系统 | 复盘 AI/导入/手写的质量差异 | `手写` / `AI 建议` / `批量导入` / `Zendesk 拉回` |
| 版本相关字段 | 系统 | §3.4 | current 版本号、上线时间、在线时长 |

### 13.5 客户原声的脱敏（合规，之前漏了）

AI 建议卡、效果页原声、对话摘录中出现的手机号、邮箱、订单号、地址一律自动打码（`138****5678`），并在区块底部注明「已自动隐去联系方式」。原始内容不落地到知识条目里；需要看完整工单时跳 Zendesk（在 Zendesk 侧鉴权）。

### 14.3 之前断掉、这次补上的四个缺口

| 断点 | 症状 | 补法 |
|---|---|---|
| **效果 → 决策** 断了 | 数据只挂条目不挂版本，改差了也不知道是哪次改的 | §3.4 版本级指标 + §10.3 判定 + 待办 #10 + 回滚 |
| **搜索词 → 问法标签** 断了 | 客户搜不到的词永远进不了知识 | 帮助中心搜索词回流 → P3「相关」页签一键加入问法 → 影响下次检索（§6.3.9） |
| **AI 建议 → 收益评估** 断了 | 不知道 AI 建议采纳后是不是真的有用 | 版本记录「来源类型」→ P5 增加一行「按 AI 建议改的 23 篇，平均解决率 +9pp」 |
| **人员变动 → 活的归属** 断了 | 成员停用后他手上的活成孤儿 | 待办 #12 交接 + 停用弹窗列出待交接清单 |

### 14.4 闭环健康度（P5 新增一块）

在效果数据页底部加一块「闭环体检」，四个数字回答「这套机器在转吗」：

| 指标 | 含义 | 健康线 |
|---|---|---|
| 建议采纳率 | AI 发现的需求有多少变成了内容 | >40% |
| 改动生效率 | 改动后解决率提升的比例 | >50% |
| 回流覆盖率 | 有效果数据的上线条目占比 | >90%（低了说明埋点/回流有问题） |
| 外改回收率 | Zendesk 侧改动被收回中台的比例 | >95%（低了说明有人在外面绕过中台） |

## 16. 验收清单（AI 生成原型后逐条自检）

### 16.1 结构类
- [ ] 侧栏只有 4 个一级菜单，无二级菜单
- [ ] 每个页面都能在 3 次点击内到达任意功能
- [ ] 五步进度条出现在：待办卡、看板卡、列表行、详情页、通知
- [ ] 全局 `+ 新建知识` 与 `Cmd+K` 在所有页面可用

### 16.2 交互类
- [ ] 全站搜不到 disabled 状态的主按钮
- [ ] 全站主按钮文案都是动词短语，无「提交/确认/保存」裸词
- [ ] 只有 4 处弹二次确认（下架、回滚、覆盖 Zendesk、停用成员）
- [ ] 非危险动作后都有撤销条
- [ ] 每个页面都画了正常/空/加载/出错 4 态
- [ ] 每个空态都有一句解释 + 一个主按钮

### 16.3 文案类
- [ ] 全站不出现术语黑名单（状态机/门禁/drift/锁/队列/API/schema/locale）
- [ ] 所有错误提示都是「发生了什么 + 你能做什么」
- [ ] 所有 AI 产出内容都有 ✨ 标记 + 采纳/我改改

### 16.4 流程类
- [ ] 新用户从登录到发布第一篇，全程不需要看文档
- [ ] 不存在任何绕过「审」这一步的路径（含批量导入、AI 采纳、Zendesk 拉回）
- [ ] 英文未校对时，「上线」入口不出现，只出现「还差什么」
- [ ] 任何时刻用户都能看到条目「在第几步、等谁、等了多久」

### 16.5 版本 / 双语 / 分类类（本次新增，必查）
- [ ] 任何展示条目的地方都带版本徽章（§3.4.3）
- [ ] 详情页有「版本与改动」页签，可选任意两版对比
- [ ] 每个版本卡片都显示**该版**的效果与样本量，而不是条目总数
- [ ] 新版明显不如老版时，效果页与待办里都能看到建议回滚，并有一键入口
- [ ] 样本不足时一律显示「数据还不够，下不了结论」，不拿百分比吓人
- [ ] 回滚后版本列表里旧版本仍存在（只增不减），并标「从 v2 换回来的」
- [ ] 改动对照支持只看改动/并排/合并三种视图，且有**词级高亮**与**信息改动区**
- [ ] 改动对照不出现行号、hunk、+/- 等工程元素
- [ ] 英文状态是**段级**的，校对页有「已校对 8/12 段」进度
- [ ] 侧栏不存在让用户手填的一级/二级分类，只有只读的「场景」派生展示
- [ ] 添加问法标签时有同义归并提示

### 16.6 埋点（验证傻瓜化是否奏效）

| 指标 | 目标 | 说明 |
|---|---|---|
| 首次发布耗时 | <15 分钟 | 新用户从登录到第一篇上线 |
| 待办处理率 | >80% | 当天生成的待办当天处理掉的比例 |
| 向导完成率 | >70% | 进入 W1 到点「送去审核」 |
| AI 建议采纳率 | >40% | 反映建议质量 |
| AI 预填修改率 | <30% | 改得越少说明 AI 填得越准 |
| 帮助气泡打开率 | <15% | 打开得多 = 界面不够自明 |
| 「稍后」使用率 | <25% | 高说明派活不准 |

## 17. 非目标（明确不做，防止 AI 发挥过度）

| 不做 | 原因 |
|---|---|
| 权限矩阵配置界面 | 角色写死 3 个，配置本身就是认知负担 |

| 三级及以上目录 | 结构深度固定两级，Zendesk 侧也只有 Category/Section |

| 深色模式 | 本期不做 |

| 按版本灵活回滚到任意字段 | 回滚是**整版快照**，不提供「只回滚某一段」（想只改一段就正常编辑） |

| 自定义分类体系 / 多维标签组 | 只有「目录›章节」+「客户会怎么问」两个维度（§13.1） |
| 内容到期自动下架 | 只提醒不自动动，避免误伤线上（§13.4） |
