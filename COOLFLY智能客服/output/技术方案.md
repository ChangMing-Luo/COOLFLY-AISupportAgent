## 1. 产品技术画像

COOLFLY 智能客服是嵌入现有 App 的英文单语 AI 客服：RN Expo brownfield 前台（对话页）+ 渠道无关的服务端对话引擎（意图分类 → 三层拒答 → 路由，执行顺序写死）+ 结构化排障流程引擎 + 管理台权威知识库检索（F09 管理台 = 唯一权威源，发布生效 ≤24h；飞书 120+ 篇一次性迁移导入）+ 埋点/双口径看板 + 回流审核队列与导出。体量锚点：现有客服 3 人团队的月处理量级会话（G1 回填精确数），LLM 推理成本现体量约 ¥1 万/年量级（PRD §9.15）——这是一个**小体量、高确定性要求**的产品，选型全程按铁律 8 锚定 MVP。

**面向海外用户声明（铁律 7 语境）**：本产品服务北美英文用户，服务端部署在现有 App 后端所在云的**海外区域**（具体云 G2 确认，蓝图 §8 已拍板）。国内可达硬约束在本项目按**「管理面可达」**口径执行：允许使用部署在海外的运行时服务，但所选云/平台的**管理控制台与文档必须国内可稳定访问**（团队在国内运维）；容器化交付保持云中立。EAS Update（Expo 托管热更服务，海外）已由用户在蓝图 §1 拍板，属已确认依赖，此口径下如实说明其为海外托管服务。

### 1.1 产品形态

- 产品类型：移动端嵌入模块（RN Expo brownfield，iOS/Android 双端）+ 内部桌面 Web（效果看板 + F09 知识库管理台）+ 无界面服务端作业（索引更新/AI 整理与提炼异步任务/回流导出/预警推送）
- 主要入口：宿主 App 固定入口 / 错误态 Get help ×3 / push 深链回对话页
- 端的数量：双端 App（同一 RN 代码）+ 2 个内部 Web 页（看板 / 管理台，同一 Web 应用路由分区）

### 1.3 团队与规模画像

- 团队规模假设：内部技术团队 1–3 名全栈工程师（PRD §9.12：上线后仅承诺月人日级维护）
- 技术栈偏好：蓝图已拍板 RN Expo / Node.js + TypeScript 单体 / PostgreSQL + pgvector / Anthropic Claude 方向
- 用户规模预期：早期——会话量以现有 3 人客服月处理量为分母（G1 回填），非高并发场景
- 上线时间压力：紧（旺季红线 + G1 超 2 周自动落保守版 C）

### 1.4 非功能性需求

- 性能：流式首内容 P50/P95 监控；超时提示触发率 >5%（建议值）持续一周即优先处理（§9.9）
- 可用性：任何故障态不出死屏（§7 写死）；灰度远程开关即时回滚；服务端重启后会话可续
- 安全合规：DPA + 零留存；会话日志脱敏后留存（建议 12 个月）；开场 AI 身份披露（加州 bot 披露）；push 权限场景化请求；AI 不索取密码类信息
- 可审计：回流导出与看板访问轻量留痕；评测回归结果可追溯
- 备份：托管 PostgreSQL 每日自动备份 + PITR 7 天（蓝图 §9 建议值，终稿前确认）
- 无障碍：客户端 ≥44pt 可点击、字号缩放不破版（属设计/前端实现约束，不影响选型）

## 3. 前端技术选型

> **判定：直接默认**——RN Expo brownfield + EAS Update 已由用户在蓝图 §1/§8 拍板，本节不再制造候选对比，只落配置、契约与风险。

### 3.1 推荐：React Native（Expo SDK 57）brownfield 嵌入 + EAS Update

**决策证据**：
1. 蓝图 §1 用户拍板：客户端前台用 RN Expo 开发，brownfield 集成进两个原生工程（RN 容器页 + 导航桥接）。
2. EAS Update 使排障卡片 UI/按钮组/文案随 JS bundle 热更，把 PRD §9.5「发版线覆盖率爬坡」风险收窄到原生入口本身——这是发版线风险的结构性缓解，蓝图已拍板。
3. 实测版本：`expo@57.0.9`、`react-native@0.86.2`（npm 实测；工程内 RN/React 版本以 `npx expo install` 按 SDK 57 锁定为准，不手写）。

**当前代价**：
- brownfield 集成需在两个原生工程各做一次容器接线（G2 盘点主 App 工程兼容细节，蓝图待确认事项 2）；
- EAS Update 是 Expo 的海外托管服务：热更发布走 expo.dev，管理面可达口径下如实登记（已拍板依赖，不新增）；旧版本（未装 RN 容器）用户走纯文本降级路径（§7.6/AC-C-04），不依赖热更。

**升级触发条件**：阶段二语音渠道启动时，RN 容器不扩权——语音走独立适配层接引擎 REST API（§3.7-1），前台形态不因此重选。

### 3.2 核心配置建议

- 语言与构建：TypeScript `7.0.2`（strict）；Expo SDK 57 管理 RN/React 版本；`eas-cli@21.4.0` 做 Update 发布
- 状态管理：`zustand@5.0.14`——会话流、排障进度、离线队列三块 store；**不引入 @tanstack/react-query**（接口面小且以 SSE 为主，引入即过度设计；列为升级备选）
- 网络：`fetch` + SSE 解析（回答流式）；离线时输入可编辑、发送置灰（§7.1 C3），恢复后自动可发送
- 本地存储：`@react-native-async-storage/async-storage@3.1.1`——埋点暂存补报队列 + 排障进度本地缓存（服务端为唯一事实，本地仅加速恢复）
- 样式：RN StyleSheet + 设计 tokens（蓝图 §6，浅色单模式）；不引入 UI 组件库（页面数=1 个对话页 + 1 个抽屉，组件库属过度设计）

### 3.3 宿主桥接注入契约（版本化稳定接口 · 蓝图 §4 锁定）

宿主 App → RN 容器的注入契约，设计为**版本化稳定接口**：`contract_version` 起版 `1`，字段**只增补不改义**（同埋点 schema 治理规则）；它是未来所有入口形态（含阶段二语音）的接线底稿。

| 字段 | 类型（概念） | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| contract_version | 整数 | 是 | 契约版本，宿主与 RN 双侧校验，不兼容即降级通用进入 |
| user_token | 字符串（不透明凭证） | 是 | 宿主登录态签发凭证，引擎服务端校验（§7.2 认证）；RN 层不解析不落盘 |
| sn | 字符串 | 否 | 设备序列号（转人工三件套来源；无绑定设备时缺省） |
| device_model | 字符串 | 否 | 设备型号 |
| error_context_type | 枚举（掉线/配对失败/扫码失败/不可判定） | 否 | 错误态入口携带；不可判定 → 降级首屏通用进入（§3.5） |
| entry_source | 枚举（固定入口/错误态入口） | 是 | 会话级一次写死，埋点公共属性直传（§4.2） |

传递机制：原生 → RN 用容器初始化参数（initialProps/等价机制）一次注入；push 深链回对话页时经同一契约字段还原上下文。转人工交接契约（6 字段顺序固定，§12.3）与本契约独立、同治理规则。

### 3.4 风险与缓解

- 风险 1：brownfield 集成在两个原生工程的兼容成本超预期（老工程 Gradle/Pods 冲突）→ 缓解：G2 盘点列专项；第一周先打通「空 RN 容器页双端能起」再写业务。
- 风险 2：EAS Update 服务异常导致热更不可发 → 缓解：热更只承载 UI/文案迭代，引擎行为全在服务端灰度开关；热更停摆不影响线上功能，只延缓 UI 迭代。

## 4. 后端技术选型

> **判定：需要对比**——Node.js/TypeScript 单体已由蓝图 §8 拍板，但**框架**未定，且框架选择影响交付速度与长期维护，做候选对比。
> 同类开源产品架构参考（GitHub 实存项目）：Botpress（TypeScript 对话引擎单体，github.com/botpress/botpress）、Tiledesk（Node.js 客服平台，github.com/Tiledesk）、Chatwoot（Rails 客服平台，github.com/chatwoot/chatwoot，作为非 Node 参照）——对话引擎 + REST API + 单体起步是该品类的主流形态，验证蓝图拍板的单体方向与业界一致。

### 4.2 推荐：Fastify 5

**推荐理由**：
1. 内建 JSON Schema 校验 + TypeScript 类型推导，与 zod 4 配合可把「引擎 REST API 渠道无关契约」「交接契约 6 字段顺序」做成编译期+运行期双重约束——本产品契约密度高（桥接契约/交接契约/埋点 schema），这是决定性优势。
2. 原生支持 SSE/流式 reply 与 hooks 生命周期，pino 即其默认日志器（零胶水）；`@fastify/basic-auth@6.2.0` 直接覆盖看板认证。
3. 生态与 AI 语料充足（npm 周下载千万级），插件体系满足限流（`@fastify/rate-limit@11.2.0`）等需求而无需引入更重框架。
4. 单体 + 单实例的 MVP 体量下，NestJS 的模块/DI/装饰器体系纯属额外复杂度（铁律 8）。

**核心配置建议**：
- 运行时：Node.js 24 LTS（nodejs/Release schedule 实测：Active LTS 至 2028-04；Node 26 于 2026-10 才进 LTS，不追新）
- 校验：zod `4.4.3` 定义全部请求/响应/事件 schema，单一事实来源，RN 侧共享类型
- 进程模型：**单进程单容器**承载 API + 定时作业（node-cron `4.6.0`：索引增量同步、周度回流导出、预警检查）——不引入独立 worker/队列（铁律 8：会话量小、任务皆分钟级容忍）
- 测试：vitest `4.1.10`（单测 + 契约测试 + 图遍历校验断言复用）

**次选**：NestJS 11——如果拍板 1 后团队扩到 5 人以上、且确定引擎将长期承载多渠道多模块，模块化约束的收益才会超过其复杂度成本。

**不推荐**：Express 5——无内建 schema 校验与类型推导（契约全靠手写中间件）、无内建日志/生命周期钩子，流式与错误处理仍是回调时代设计；在契约密度高的本产品里意味着大量自建胶水，等于自己重写半个 Fastify。

### 4.3 引擎 REST API 面（渠道无关 · §3.7-1 落地）

### 4.4 拍板 1 分叉：选 A 重建（推荐主线）vs 选 B 升级现有系统

**推荐主线 = 选 A 重建**，理由：
1. §3.1 决策总顺序、三层拒答、引用忠实校验是引擎的**内核行为**，在自有代码里是一周量级的 pipeline；插进未知旧系统则受 G2 三集成点可插拔性摆布，风险不对称。
2. §3.7 五条演进约束（渠道无关/schema 中立/埋点 channel）在重建时是零成本起手式，在旧系统上是改造项。
3. 现有系统能力未知（G2 尚未盘点），而 MVP 体量小、重建面积有限——重建成本可控、改造成本不可控。

**选 B 适配面（G2 三集成点，行为规格与数据产出两案完全不变）**：

| 集成点 | 选 A（本方案默认） | 选 B（G2 判定可插拔后） |
| :--- | :--- | :--- |
| 拒答阈值判断 | pipeline 内检索分数阈值 + 引用校验（§6.4） | 在现有系统回答出口前插入同一判定模块（阈值配置化不变） |
| 埋点钩子 | pipeline 各节点原生埋点（§4.2 事件表） | 在现有系统消息收发/转人工节点挂钩子，事件 schema 不变 |
| 排障流程引擎 | 单体内流程引擎模块 | 作为独立模块挂接现有系统会话流（schema 与校验工具不变） |

选 B 时：本章框架选型让位于现有系统技术栈；但**引擎 REST 契约、评测集、埋点 schema、交接契约、图遍历校验工具**仍为硬约束——达不成的项按 AR-3 逐条摆回企业家桌面重拍，不许静默缩水。成本对比数字依 §9.15 成本账 G2 后回填。

### 4.5 风险与缓解

- 风险 1：单进程内跑定时作业，索引重建高峰拖慢 API → 缓解：增量同步分批执行 + 低峰调度；实测拖累 P95 再拆独立进程（同镜像双进程即可，无需队列）。
- 风险 2：拍板 1 拖延导致两线并行准备 → 缓解：先做两案共用的不变资产（评测集、埋点 schema、流程 schema+校验工具、REST 契约），拍板后只拼装。

### 5.1 主数据库

> **判定：直接默认**——PostgreSQL（含 pgvector）已由蓝图 §8 拍板；托管形态（每日备份 + PITR 7 天）由蓝图 §9 拍板。

**推荐**：现有 App 后端所在云的**托管 PostgreSQL**（海外区域，具体云 G2 确认），引擎版本选云上可用的 **PostgreSQL 16+**（社区最新大版本实测 18.x，托管云通常滞后 1–2 个大版本；16 起 pgvector 生态完全成熟），启用 `pgvector` 扩展（GitHub 实测最新 **v0.8.6**；托管云以其支持的扩展版本为准，≥0.7 即满足 HNSW 需求）。

- **决策证据**：会话/排障进度要求强一致（§4.5）；检索需向量能力（蓝图拍板 pgvector）；体量 = 3 人团队月处理量级会话 + 120+ 篇知识条目——单库单实例绰绰有余；托管备份直接兑现蓝图 §9 备份拍板。

- **升级触发条件**：会话量随销量涨 2–3 倍后 P95 查询劣化，或多实例部署需求出现 → 升级读写规格/加只读副本，不换库。

**ORM 选择（简单对比，2 候选）**：

| 候选（实测版本） | DX | Perf | Eco | AI | Scale | Learn | TCO | 加权总分 |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| **Drizzle ORM 0.45.2**（+ drizzle-kit 0.31.10、pg 8.22.0） | 5 | 5 | 4 | 5 | 4 | 4 | 5 | **4.6** |

### 5.2 缓存层

**未激活**。理由（铁律 8）：会话强一致读写直连主库；知识检索语料 120+ 篇、QPS 个位数，PG 自身缓冲足够；看板按周呈报、最终一致。引入 Redis 属过度设计。升级触发条件：检索 P95 实测劣化且定位为库压力时再评估。

### 5.3 搜索引擎

**不引入独立搜索引擎**。关键词检索由 **PostgreSQL FTS（tsvector，english 配置）**承担，与 pgvector 组成混合检索（详见 §6.2）——数据量 120–数百条目，Elasticsearch/Meilisearch 属过度设计。升级触发条件：知识条目破万或需复杂多语言分词时再评估。

## 6. AI 能力选型（激活：PRD 核心即 AI 问答）

### 6.1 LLM 选型

> **判定：直接默认**——供应商方向已由蓝图 §8 拍板（Anthropic Claude 方向，用户拍板、技术负责人终确认）。**本节为架构建议，技术负责人确认（含 DPA 签约核验）前非最终决定。**

- 主模型（对话/话术生成/知识问答）：**claude-sonnet-5**
- 轻任务模型（意图分类五类/语言检测步骤 0）：**claude-haiku-4-5-20251001**（低延迟低成本，分类与检测为每条消息前置节点，延迟直接叠加在 §9.9 超时预算上）
- 备用模型：同供应商内降档（Sonnet 不可用时对话临时走 Haiku 档并如实降质）；**跨供应商更换必须整套评测集回归通过后切换**（§9.2 写死）
- **决策证据**：蓝图拍板方向；DPA + 输入零留存不训练为签约硬条件（§9.14，任一未就绪 = 不满足上线条件）；成本按 §9.15 现体量约 ¥1 万/年量级，G1 会话量回填后复算。
- **当前代价**：单一供应商依赖（PRD §9.2 已登记）；缓解 = 评测集为供应商无关行为契约 + 接口层供应商可插拔（§6.3）。
- **升级触发条件**：评测集命中率不达标且归因于模型能力，或成本随会话量放大超预算线 → 触发跨供应商评测对比（回归通过才切）。
- LLM 全链路失败形态：熔断 + 降级卡 C2（转人工与排障文章为确定性路径，§7.5）——**不存在「LLM 兜底 LLM」的设计**。

### 6.2 向量数据库与检索（RAG）

> **判定：直接默认**——pgvector 已由蓝图 §8 拍板；Embedding 来源按依赖门禁选不新增外部服务的方案。

- 向量库：**pgvector v0.8.6**（主库内扩展，HNSW 索引；语料数百条不设分库）
- Embedding：**fastembed `2.1.0` 进程内推理**（默认 bge-small-en-v1.5，ONNX，英文语料适配；384 维，百级条目秒级全量重嵌）——**零新增外部服务**：蓝图外部对接清单只确认了 LLM API/飞书/push/飞书机器人，托管 Embedding API（如 Voyage）属蓝图未确认的新外部服务，依赖门禁禁止本阶段静默引入；若后续评测显示检索召回是瓶颈，引入托管 Embedding **须回蓝图补拍板**。
- 检索策略：**混合检索** = pgvector 语义相似 + PG FTS 关键词（型号/错误码等专名词靠词面命中）+ **问题标签匹配（F09 增量）**：人工确认后的问题标签（用户问法变体，多值）作为高置信词面信号进入融合——标签精确/前缀匹配加权（权重高于普通 FTS 命中，具体权重为配置化参数随评测调优）；加权融合分数；**融合分数阈值 = 三层拒答第①层判定值，配置化商业参数**（上线后调优为技术月人日第一用途，§3.3）。标签信号对**命中率 ≥80% 验收（§8.2 放量前置条件）的贡献路径**：bge-small 对长尾问法变体召回偏弱（本节已登记代价），标签让同一条目被更多问法变体词面直接命中，扩充召回且不稀释精度（标签经人工确认，非 AI 自由生成）——命中率仍以评测集验收，不新增指标。
- 索引流水线：管理台**已上线**条目（发布门禁通过，§6.9）→ 清洗分块（按标题/步骤结构）→ 嵌入（正文 + 问题标签）→ 版本化写入（`kb_index_version`）；重建期间旧版本继续服务，原子切换（§7.4 用户无感知）。
- **当前代价**：bge-small 对长尾表述的召回弱于大模型 Embedding；缓解 = 混合检索 + 评测集高频误拒题看守。
- **升级触发条件**：评测集命中率 <80%（§8.2 放量前置条件）且归因于向量召回 → 先升级 bge-base/large（仍进程内），再考虑托管 API（回蓝图）。

### 6.3 编排层：单轮结构化调用，明确不引入 Agent 框架

**两个能力层次的判定（铁律 6）**：本产品**只需要「单轮 LLM 调用」层次，不需要「Agent 多步推理」层次**——这是 PRD 的硬性推导而非偏好：§3.1 决策总顺序写死（语言检测→关键词→分类→拒答→路由，每步由自有代码判定流转）；§3.6 写死排障步骤由结构化流程引擎承载、「LLM 不负责发明步骤」。Agent 框架的核心价值（模型自主规划步骤与工具调用）恰恰是本产品**禁止**的行为。多步编排 = 自有 TypeScript pipeline（可测、可埋点、确定性）。

统一接口层做候选对比（影响供应商更换成本与结构化输出实现）：

| 候选（实测版本） | DX | Perf | Eco | AI | Scale | Learn | TCO | 加权总分 |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| **Vercel AI SDK：ai 7.0.48 + @ai-sdk/anthropic 4.0.27**（开源 npm 库，非托管服务） | 5 | 4 | 5 | 5 | 4 | 4 | 5 | **4.7** |
| 直连 @anthropic-ai/sdk 0.115.0 | 4 | 5 | 4 | 5 | 3 | 4 | 5 | 4.3 |
| LangChain 1.5.4 | 3 | 3 | 4 | 4 | 4 | 3 | 4 | 3.6 |

**推荐：Vercel AI SDK（`ai@7`）+ `@ai-sdk/anthropic@4` provider**。理由：①`generateObject`（zod schema 约束输出）是三层拒答第②层「结构化强制引用」的最短实现路径，`streamText` 原生对接 SSE；②provider 抽象使「更换供应商须评测集回归」的切换成本 = 换 provider 包 + 跑回归，不动业务代码——直连官方 SDK 则供应商锁死在调用层；③开源 npm 库、代码跑在自有服务器，不属海外托管服务。供应商专属能力（prompt caching 等）经 providerOptions 透传，不损失。

**次选**：直连 `@anthropic-ai/sdk`——若技术负责人确认永不换供应商且需要第一时间用到 SDK 独占新特性。
**不推荐**：LangChain——其链/图抽象与本产品自有确定性 pipeline 职责重叠，等于双重编排；调试面加厚而收益为零（本产品无自主多步推理需求）。

### 6.4 三层拒答与引用忠实：实现路径（关键技术义务）

```text
用户消息 → [0] 语言检测（Haiku 档，蓝图拍板；判定不确定按英语，§7.7）
        → [1] 退款/愤怒关键词规则：确定性字符串匹配（§12.7 清单 v1，纯代码，非 LLM，可硬验收）
        → [2] 意图分类（Haiku 档，五类枚举结构化输出）
        → 仅知识求解类 ↓
        → 层①：混合检索融合分数 < 阈值（配置化）→ 拒答
        → 层②：generateObject({ answer, citations: 条目标识[] })
                 服务端校验 citations ⊆ 本次检索命中集合；空引用/越界引用 → 拒答
                 来源标注由**服务端**按 citations 渲染条目标题（LLM 不自写来源）
                 ⇒ 用户可见来源 = 实际命中条目，§4.3 陷阱题②闭环由构造保证
        → 层③：敏感/超范围硬规则表（确定性类目匹配）→ 拒答
        → 连续拒答计数（成功事实性解答清零、豁免类不清零不累加，§3.3）在会话状态内维护
```

豁免类（情绪/闲聊/流程推进/追问澄清）prompt 显式禁止输出事实性内容，评测集陷阱题③看守；情绪会话内拒答形态切共情短语 + 大按钮（§3.3 R4-P0），由 pipeline 状态驱动话术模板选择，非 LLM 自由发挥。

### 6.5 评测集回归执行与留痕（§9.8 技术债 1 落地）

- Runner：仓库内 `eval` 目录，tsx `4.23.5` 脚本驱动 + vitest 断言复用；题库读评测题表（脱敏层）。
- **留痕**：每次运行写 `eval_run`（run_id、触发人、git_sha、model_id、prompt 版本、kb_index_version、汇总指标）+ `eval_case_result` 逐题结果——放量前置条件（命中率 ≥80% 且拒答率在区间，§8.2）**只认此表记录**，人工触发可接受、无留痕不算跑过。
- 触发时机：发版前必跑（🟩）；**F09 条目发布门禁必跑（🟩，发布 API 触发，§6.9）**；prompt/模型/知识库变更全量回归自动化为 🟨 技术债，起步用 GitHub Actions 手动 workflow 触发。

### 6.6 排障流程引擎与图遍历校验工具（§9.8 技术债 1 落地）

- 流程 schema：渠道中立 JSON（节点/两出口分支/终止类型，§4.1），存内容域表，版本化；进行中会话锁定其开始版本（§7.3）。
- **校验工具**：仓库内独立脚本（vitest 断言），对每份流程执行图遍历：①有向图无环，或环上必存在转人工出口节点；②全部叶子节点 ∈ {确认解决, 转人工}；③每个节点自根可达。接入三处：CI（流程 JSON 变更即跑）+ F09 管理台排障编辑器保存时校验（不过不允许发布、编辑器标出问题节点，§5.10）+ 发布 API（不通过不得置为已上线状态）。**先于内容改造完成交付**（PRD 排序要求）。

### 6.7 知识库权威源与索引更新（F09 权威源切换 · ≤24h 义务落地）

**权威源 = F09 管理台**（08-04 拍板，§9.2）：飞书角色从"持续同步源"改为**一次性迁移导入**，此后不做双向同步，防口径分叉。

- **一次性导入管道**：飞书 API 导出 → 解析切条（按标题/步骤结构）→ 全部进管理台「待整理」队列（不直接上线）→ AI 整理建议（§6.8）→ 人工确认后走正常发布链路。迁移完成即该链路生命周期结束，不留同步代码路径。**兜底（§9.2）**：飞书 API 权限未就绪/迁移失败 → 人工从飞书导出 Markdown/CSV 文件，经管理台批量导入——同一入口、同一「待整理」队列，迁移失败不阻塞管理台其余能力。
- **索引更新链路：管理台发布（过发布门禁，§6.9）→ 增量索引**——发布成功即触发该条目重嵌与版本化写入，≤24h 承诺由发布驱动的分钟级增量兑现，留足重试余量；node-cron 每日一次全量校对（既有进程内调度，防漏防漂移）。
- 失败处置（§7.4/§9.2 统一口径不变）：索引更新失败沿用上一版索引（用户无感知）；中断 >24h 飞书机器人告警运营；>48h（建议值）升级呈报。

### 6.8 AI 整理与提炼管道（F09 · 全部建议态，无人审不生效）

两条管道均为**异步任务**，跑在既有单进程内的**进程内任务队列**（内存队列 + node-cron 兜底扫描未处理项，复用 §4.2 既有调度方案）——铁律 8：条目量百级、任务分钟级容忍，**禁止为此引入 Redis/消息队列等蓝图外新依赖**。

1. **切条 + 问题标签生成（录入/导入触发）**：新进「待整理」队列的内容 → **Claude Haiku 档批处理**（generateObject 结构化输出：切条建议 / 问题标签建议〔多值，每条目 ≤20 建议值〕/ 场景与型号归类建议）→ **建议态存库**（独立建议表，不写条目正文）→ 管理台建议卡展示，运营逐项采纳/修改/拒绝后方生效；拒绝不阻塞人工直接编辑发布（AC-E-13）。
2. **会话提炼（F05 回流触发源驱动，§4.4）**：回流触发源①–④会话（**只读脱敏层**，§5.1 脱敏管道）→ 按聚合键聚类（有命中按条目标识 / 无命中按规范化问题文本，频次计数）→ **Claude Sonnet 档起草**条目草稿（正文 + 问题标签建议 + 来源会话脱敏摘要 + 频次）→ 写入审核队列（按频次降序）→ 运营三操作：通过发布 / 驳回（须填原因）/ 改后发布。

**无人审不生效在 API 层强制（非 UI 约束）**：检索索引的唯一写入源 = 发布 API 成功路径（§6.9）；草稿/待整理/未审核状态的条目在数据层就不进 `kb_index_version`，F01 检索按当前索引版本查询——**构造上不可能命中未审内容**（AC-M-15 由构造保证，与 §6.4 引用忠实同一设计哲学）。AI 服务不可用时两管道停摆、建议卡隐藏并明示，但人工录入/编辑/审核/发布全部照常（AI 为增强非依赖，§7.5 降级原则同源）。

成本影响：两管道均为小批量批处理（导入切条一次性 120+ 篇、回流提炼周级几十条），Haiku 档为主、Sonnet 档仅起草触发，增量成本在 §9.15 现体量 ¥1 万/年量级内可忽略，G1 会话量回填后随整体复算。

### 6.9 发布门禁（F09 · 复用评测回归留痕机制）

发布 API（含「改后发布」）执行链，**全程复用 §6.5 既有 runner 与留痕表，不建第二套回归机制**：

```text
条目发布请求 → 排障流程型先过 §6.6 图遍历校验（不过即拒，标出问题节点）
            → 触发评测集回归（同一 runner；eval_run 记录带触发条目标识与触发类型=发布门禁）
            → 通过：条目置「已上线」+ 触发增量索引（§6.7），状态流转留痕
            → 失败：条目回炉（回草稿），失败原因与失败用例写库，管理台结果面板可见
```

状态流转与回归结果同事务收口——**不存在「回归失败但条目已上线」的中间态**（PRD §5.10 异常场景硬约束）。放量前置条件（§8.2）与发布门禁读同一 `eval_run` 表，留痕口径一致。

## 7. 基础设施选型

### 7.1 部署与托管

> **判定：直接默认**——蓝图 §8 拍板：跟随现有 App 后端所在云海外区域，容器化保持云中立，不新增部署平台。

**推荐**：单 Docker 镜像（引擎 API + 看板静态文件 + 进程内定时作业）部署于现有 App 后端云的海外区域计算实例，Docker Compose 编排（应用容器 + 反向代理/TLS）；数据库用同云托管 PostgreSQL（§5.1）。

- **决策证据**：蓝图拍板 + 会话量小（单实例足够）+ 团队维护人力月人日级——K8s/多实例/Serverless 均属过度设计（铁律 8；常驻 SSE 连接也不适合 Serverless）。具体云与区域为 G2 盘点确认项（蓝图待确认事项 2），镜像云中立保证结论出来即插即用。
- **管理面可达（铁律 7 本项目口径）**：候选云限定为现有 App 后端已在用的云（沿用既有账号，不新增平台账号）；其管理控制台与文档国内可访问为 G2 确认项之一，如实呈报。
- **当前代价**：单实例发布有秒级中断窗口（进行中会话按 §7.8 恢复语义兜底：历史不丢、恢复期间走超时/降级态）；无跨区容灾。
- **升级触发条件**：会话量随销量 2–3 倍增长后单实例资源饱和 → 先垂直扩容，再考虑双实例 +负载均衡（届时定时作业拆独立进程，埋点幂等设计已兼容多实例）。

### 7.2 认证与授权

> **判定：直接默认**——蓝图 §3/§9 拍板：无新增账号体系。

**推荐**：App 侧复用宿主登录态——桥接契约注入 `user_token`，引擎侧按宿主签发机制校验（验签或回调宿主后端，取哪种由 G2 盘点现有凭证体系后定，两种皆不新增账号体系）；LLM/飞书等密钥全部 deployment-secret（requirements 外部配置表，无用户可见配置界面）。看板与 F09 管理台 = 同一 `@fastify/basic-auth@6.2.0` 口令 + 访问链接不公开（蓝图建议值，终稿前确认；PRD §5.10 明示与看板同机制）；看板使用者 = 业务负责人 + 运营三岗，管理台使用者 = 知识库内容运营岗（2 名）+ 业务负责人。**管理台写操作全量审计留痕**（时间/操作者/动作/条目标识，落 §5.1 运营域审计表）——Basic Auth 无个人级身份，留痕记到口令持有组，与蓝图 §9 轻量审计口径一致。

- **决策证据**：PRD 无注册/登录 REQ；单直接角色产品；看板内部只读。
- **当前代价**：Basic Auth 无个人级审计粒度（看板访问留痕记到口令持有组）；凭证校验方式依赖 G2 结论。
- **升级触发条件**：看板使用者扩编或需分权 → 升级为独立账号 + 会话（届时再选型，本期不建）。

### 7.3 可观测性

> **判定：直接默认**——蓝图 §9 拍板轻量审计留痕；不新增外部 SaaS（依赖门禁）。

**推荐**：pino `10.3.1` 结构化日志（Fastify 原生）→ stdout → 所在云托管日志服务收集（沿用现有云能力，G2 确认）；`/healthz` 探活 + 云监控基础告警；业务指标即 F06 埋点看板自身（首内容 P50/P95、超时触发率、降级触发率、拒答分层——§9.9 监控项全部走埋点事件，不另建监控栈）；告警推送统一走**飞书机器人**（蓝图已确认载体：容量预警、索引中断 >24h、超时率超线）。

- **决策证据**：单体单实例无分布式追踪需求；错误可从结构化日志 + 会话 ID 直接回放；Sentry（SaaS 或自托管）均未出现在蓝图依赖清单，自托管 Sentry 的运维成本对月人日级维护团队不成立（铁律 8）。
- **当前代价**：无自动错误聚合分组，靠日志检索与告警规则。
- **升级触发条件**：线上错误定位耗时成为实际瓶颈（如每周 >0.5 人日耗在日志翻检）→ 评估自托管开源错误追踪，且须回蓝图登记新增部署组件。

### 7.4 CI/CD

**推荐**：GitHub Actions（仓库实测托管于 github.com/ChangMing-Luo/COOLFLY-AISupportAgent，沿用既有平台账号，不新增依赖）。流水线：
- PR 门禁：typecheck（TS 7）+ lint + vitest 单测/契约测试 + **排障流程图遍历校验**（§6.6）
- 手动触发：评测集回归 workflow（结果落库留痕，§6.5）
- 发布：Docker 镜像构建推送（云中立 registry，G2 定云后接部署）；RN 侧 `eas-cli@21.4.0` 发 EAS Update；原生壳发版走宿主 App 现有发版流程（发版线，覆盖率如实呈报）

### 7.5 条件能力（按需激活）

- **实时通信（激活：流式回答 + 目标态回复触达）**：服务端 → 客户端回答流用 **SSE**（单向流，满足 §9.9 首 token 体验，比 WebSocket 少一套连接管理）；人工回复触达复用**现有 App push 基建**（requirements 外部配置表已确认，G3 查证）+ 会话页轮询兜底。不自建 WebSocket/推送通道。
- **文件/富媒体（激活：排障配图）**：**决策门禁证据**——单实例部署；配图为 Top3 场景关键分支图（🟩 范围十余张，🟨 增量有限）；无用户上传、无客户端直传、无 CDN 要求；RPO 由 git 版本管理天然满足。**结论：配图作为版本化静态资源随仓库管理、打进容器镜像/持久化目录，由引擎静态路由或 RN bundle 内置服务**；不引入对象存储（蓝图 §8 明示不预先引入；若后续图量/直传需求出现，回蓝图确认后按现有云对象存储升级）。
- **支付/计费**：未激活（PRD 无交易）。
- **多端/跨平台**：见 §3（RN Expo 双端，蓝图拍板）。
- **埋点暂存补报（激活：§4.2 交付约束 + 蓝图 §7 同步策略）**：客户端 AsyncStorage 队列（event_id 为 UUID，公共属性入队时写死）→ 批量 POST /v1/events（网络恢复/前台切回触发）→ 服务端按 event_id 幂等去重；看板读聚合视图，最终一致按周呈报。schema 治理：事件语义只增补不改义，schema 版本随契约仓库管理。
- **人工通路 G3 双态适配（激活：F03 目标态/底线态分层）**：定义 `HandoffChannel` 接口（提交交接契约/回复写回/关闭信号三能力位），两个实现——**目标态**：回复写回会话流 + push 触达 + 人工会话关闭信号（G3 查证来源；查无信号则按建议值「客服末条回复后 24h 自动判关闭」降级）；**底线态**：邮件通路 + 等待窗口 24h（建议值）+ 转接确认时只触达服务体验反馈。G3 结论落地 = 切配置选实现，话术/评分触达/首响埋点口径随实现自动分层，行为规格不改代码结构。

### 8.5 技术负责人的最终结论

#### 是否可以立即开工

**有条件开工**：§8.2 第 1–10 步（脚手架 + 两案共用不变资产）现在即可动手；对话引擎的实现形态在拍板 1 落定后拼装；具体云/区域、凭证校验方式、错误码结构化程度等 G2 结论回填后收口部署与 F08 携带上下文粒度。LLM 供应商为架构建议，技术负责人确认 + DPA 核验通过后转为最终决定。

#### 最大的技术不确定性

> 不是任何框架选型，而是**飞书迁移入库的 120+ 篇存量内容的真实质量能否支撑 ≥80% 评测命中率**——这决定拒答率是否落在放量区间，是整个技术方案的第一命门（AR-1）。第一周先跑通「迁移导入→发布→索引→评测」闭环拿到真实命中率，比任何架构讨论都值钱；F09 的问题标签联动（§6.2）是命中率不够时的第一调优抓手。

#### 现在最不应该做的事

> ①在拍板 1 未决时提前深耕引擎与任一形态的深度耦合——先做两案共用的契约与工具资产；②引入 Agent 框架、Redis、消息队列、K8s、独立搜索引擎中的任何一个——本产品的确定性 pipeline 和小体量都不需要它们，每一项都在偷走撞旺季红线前的工期；③绕过蓝图依赖门禁静默接入任何新外部服务（托管 Embedding、错误追踪 SaaS 等）——发现需要就回蓝图补拍板，不许先斩后奏。
