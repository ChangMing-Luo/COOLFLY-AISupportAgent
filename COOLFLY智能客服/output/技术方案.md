## 1. 产品技术画像

COOLFLY 智能客服的自研范围 = **知识运营中台**：内部桌面 Web（十视图五组，简体中文，RBAC 四角色真实账号）+ 三类无界面服务端能力（中台→Zendesk 单向同步与 drift 检测 / Zendesk 会话每日批次挖掘 / 中→英 AI 翻译管道）。C 端体验（帮助中心、AI bot 在线聊天、邮件与转人工工单）与客服工作报表全部由 Zendesk 承担——**本方案零 C 端界面、零对话运行时**。知识质量是 Zendesk bot 回答质量的唯一自变量，中台即质量杠杆（PRD §1.1）。

体量锚点：知识条目初始 120+ 篇（飞书一次性迁移）、中台用户 = 四角色若干真实账号（个位数）、挖掘批次 = 每日一批数十会话、同步任务 = 分钟级推送——**小体量、高确定性、强留痕**的内部系统，选型全程按铁律 8 锚定 MVP。

### 1.1 产品形态

- 产品类型：**独立内部 Web**（桌面 1280+，十视图五组，§5.10）+ 无界面服务端作业（同步推送 / drift 周期检测 / 每日挖掘批次 / 翻译任务 / 复核到期扫描 / 效果聚合刷新）
- 使用者：知识管理员 / 知识审核员 / AI 运营（只读+建议）/ 系统管理员——RBAC 四角色真实账号（PRD §2.1）
- C 端归属：App 用户与帮助中心访客全部经 Zendesk 触达；App 侧本期完全不动（D-10 拍板）

### 1.2 核心技术约束

| 约束 | 来源（PRD 章节） | 技术含义 |
| :--- | :--- | :--- |
| 中台 = 知识唯一权威源；中台→Zendesk **单向同步**；Zendesk 端被直接改写 = drift，须检测报警并处置（覆盖/拉回） | §5.10 权威原则 1、§7.3 | 同步器持有条目↔Article 映射与已发布版本哈希；drift 周期比对（建议值每小时）+ 双处置动作留痕 |
| **统一过审**：全部新条目/修订/候选/建议经审核中心 + 发布门禁后才生效同步；任何角色无绕过路径 | §5.10 权威原则 2、AC-P-05 | 发布路径唯一且在 **API 层强制**（状态机 + 同步队列唯一写入源 = 发布 API 成功路径）；UI 禁用只是表象 |
| **翻译人工校验率 100%（铁律）**：英文「已确认」前同步阻断；中文变更即英文置「待重新校验」并阻断 | §5.10 翻译工作流、§8.2、ZR-3 | 英文状态机由服务端强制；中文保存钩子联动置态；同步器按状态硬拦 |
| 可见性三档拆分：仅内部条目只挂客服 segment；混合条目**内部段落不进对外文章、不翻译、不同步对外** | §4.1、§7.4、AC-P-14 | 正文段落带内部标记；同步器/翻译器按标记剥离，发布门禁第②查强制核验 |
| RBAC 10 项权限点 × 4 角色矩阵约束全部界面动作；四眼原则（不可自审自发）；权限变更即时生效 | §5.10 矩阵、AC-P-22/23 | 权限中间件覆盖全部写 API；矩阵存库 + 进程内缓存写时失效；审核通过接口校验提交人 ≠ 审核人 |
| 审计日志全量：谁/角色/对象/动作/**字段级前后值**，只增不改不删、长期保留 | §4.5、AC-P-21 | 独立 append-only 审计表；写操作在服务层统一拦截记录 diff |
| Zendesk API 429 限流：挖掘批次失败如实标注次日重拉；同步退避重试（建议值 3 次）后告警；批量迁移分批推送 | §7.2 | 集成层统一处理 Retry-After 退避；批次状态表落库不静默 |
| 信号确定性分档：工单/投票/flag 必得；bot 锚点引用、面板引用、automated resolution 口径**待核实** | §4.3、§8.2、ZR-6 | 信号采集表带确定性档位字段；待核实信号核实前不进达标判定，界面如实标注 |
| 向量只服务本台内部（挖掘查重 / 缺口聚类 / 发布门禁代理评测）；Zendesk AI 有自己的索引，两者独立 | §4.1、§8.3 | pgvector 用途降级为内部工具；代理评测结果固定标注「不等于 Zendesk AI 真实表现」 |
| 任何失败态**如实标注 + 保留上次可用内容 + 提供重试路径**，不静默吞错 | §5.1 异常原则（写死） | 同步/翻译/向量/批次全部状态机化落库；无「阻断但已同步」类中间态 |
| 并发编辑冲突：后提交者收到冲突提示，不静默覆盖 | §4.6、§7.1 | 条目乐观锁（版本号比对），冲突返回 409 与最新版本 |

### 1.3 团队与规模画像

- 团队规模假设：内部技术团队 1–3 名全栈工程师；上线后月人日级维护
- 技术栈偏好：既有拍板栈全部保留（Node.js + TypeScript 单体 / PostgreSQL + pgvector / Vite + React / Anthropic Claude 方向）
- 用户规模预期：中台账号个位数、并发极低；Zendesk 侧流量与本系统无关
- 上线时间压力：拍板 3 随 D-10 重估中（待 Zendesk 核实清单回填后排期，§0.6）——选型权重仍偏开发效率与生态成熟度

### 1.4 非功能性需求

- 性能：内部系统无高并发要求；挖掘/翻译为分钟级容忍的异步任务；同步入队后分钟级推送
- 可用性：中台短暂不可用不影响 Zendesk 端 C 端服务（上一版内容继续服务）；失败态全部可重试
- 安全合规：LLM 供应商 DPA + 输入不用于训练（选型硬条件，§9.7）；挖掘来源会话脱敏后才进中台；账号最小权限 + 首次登录强制改密；审计日志长期保留；Zendesk API 凭据 deployment-secret
- 可审计：全量操作写审计日志（字段级前后值）；版本历史与各版效果指标永久保留
- 备份：托管 PostgreSQL 每日自动备份 + PITR 7 天（沿用既有拍板，终稿前确认）

## 3. 前端技术选型（中台 Web）

> **判定：直接沿用 + 两项增补**——Vite + React + ECharts 为既有拍板栈（原看板/管理台同栈），转向后升级为中台唯一前端，不再制造候选对比；按 PRD §5.10 新增两项界面能力（富文本编辑、版本 diff 渲染）做最小选型。

### 3.1 推荐:Vite 8 + React 19 单页应用（十视图五组路由）

- 结构：单 SPA，五组一级导航 → 十视图路由（`/workbench` `/kb` `/entry/:id` `/mine` `/review` `/sync` `/dashboard` `/feedback` `/audit` `/admin`）；随引擎同仓构建、静态文件由 Fastify 托管，部署形态不变。
- 沿用版本：`vite@8.2.0`、`react@19.2.8`、`echarts@6.1.0`（数据看板：场景覆盖条 / 条目效果列表 / 各版解决率对比）、TypeScript `7.0.2`（strict，与后端共享 zod 契约类型）。
- 状态与数据：视图数据以服务端为唯一事实，`fetch` + 常规请求即可（内部系统低并发，不引入 react-query/状态库——铁律 8）。

### 3.2 新增界面能力选型（v2.0 · 版本 2026-08-04 实测）

| 能力 | 选型 | 理由 |
| :--- | :--- | :--- |
| 富文本编辑器（PRD 视图③：标题层级/加粗/列表/表格/图片/超链接/引用块 + **内部段落标记**） | **TipTap `@tiptap/react@3.29.2` + `@tiptap/starter-kit@3.29.2`**（headless，基于 ProseMirror） | ①headless 无样式绑定，贴合既有 tokens 设计系统；②节点模型可自定义「内部段落」节点（可见性拆分的结构化前提——内部段落须是文档树上可识别的节点，不能靠富文本 HTML 里的约定注释）；③输出结构化 JSON + HTML 双格式，服务端按节点剥离内部段落后生成对外 HTML（§4.4 同步器输入）。自研 contentEditable 不可行（表格/协作粘贴边界成本远超一个成熟编辑器）；重量级替代（CKEditor/TinyMCE 商业授权面）不符内部工具体量 |
| 版本 diff 渲染（PRD 视图③：任意两版左右并排，删除红/新增绿） | **`diff@9.0.0`**（jsdiff，行级/词级 diff 算法库） | 纯算法库零 UI 绑定；对版本快照的规范化文本做行级 diff，渲染层用既有 tokens 上色；自研 diff 算法属重复造轮子 |
| 界面语言 | 沿用 zh-CN 语言资源机制（key→文案映射，同仓构建，零 i18n 框架） | PRD §5.1：界面 100% 简体中文；多语言切换为后置增强，加语言 = 加资源文件 |

### 3.3 风险与缓解

- 风险 1：TipTap「内部段落」自定义节点与 Zendesk HTML 的转换出现标记丢失 → 内部内容泄漏到对外文章。缓解：剥离逻辑放**服务端**且为纯函数（单测覆盖混合条目样本）；发布门禁第②查独立核验产物 HTML 不含内部标记（双保险，AC-P-14）。
- 风险 2：富文本粘贴（自飞书/Word）带入脏 HTML，同步到 Zendesk 后排版破碎。缓解：编辑器白名单 schema（TipTap 节点集即白名单，未注册节点自动剥离）；批量导入管道统一走同一解析器。

## 4. 后端技术选型

> **判定：框架沿用 v1.1 对比结论**——Fastify 5 的加权对比（vs NestJS/Hono/Express，4.6 分居首）在 v1.1 已完成且团队画像未变，本版不重跑；理由摘要保留：内建 JSON Schema 校验 + zod 类型推导（本系统契约密度仍高：权限矩阵/状态机/同步映射）、pino 零胶水、生态与 AI 语料充足、单体体量下 NestJS 属额外复杂度。

### 4.1 推荐：Fastify 5 单体（沿用）

- 沿用版本：`fastify@5.11.2`、`zod@4.4.3`、Node.js 24 LTS、`@fastify/rate-limit@11.2.0`（登录接口防爆破 + API 面兜底限流）。
- 进程模型：**单进程单容器**承载中台 API + 全部定时作业（node-cron `4.6.0`：每日挖掘批次 / drift 每小时扫描 / 同步重试 / 复核到期扫描 / 效果聚合刷新）——不引入独立 worker/队列（铁律 8：任务皆分钟级容忍、账号个位数并发）。
- 测试：vitest `4.1.10`（单测 + 契约测试：权限矩阵逐格断言、状态机流转断言、内部段落剥离纯函数断言）；tsx `4.23.5` 驱动迁移/导入脚本。

### 4.2 核心横切件（服务层统一实现，非散落各路由）

1. **RBAC 权限中间件**：每个写路由声明所需权限点（10 项之一）；preHandler 读「角色×权限」矩阵（存库 + 进程内缓存，矩阵/角色变更即失效缓存）→ 越权返回 403 带原因文案 key。四眼原则在审核通过接口内校验（提交人 = 当前用户则拒绝）。
2. **审计拦截**：写操作统一经服务层 audit 包装——取变更前快照、执行、取变更后快照、写审计表（时间/操作人+角色/对象/动作/字段级前后值/备注）；审计表 append-only，无 UPDATE/DELETE 路径。
3. **状态机守卫**：条目状态（草稿→…→已发布/已驳回/已下线）、英文状态、同步状态、向量状态四条状态机的合法流转表内聚在领域层；非法流转直接 409——「无人审不生效」「已确认前不同步」由构造保证而非 UI 约束。

### 4.3 中台 API 面（分组骨架，详细字段归实现期 OpenAPI）

### 4.4 Zendesk 集成层（新架构面 · 零 SDK：Node 24 原生 fetch + API token）

Zendesk 无官方 Node SDK 依赖必要——REST API + fetch 直连，凭据（subdomain + email/API token）为 deployment-secret（owner = 内部技术团队，PRD §9.2）。集成层为独立模块，统一处理认证头、429 退避（读 `Retry-After`，指数退避封顶）、错误分类（凭据失效单列告警指向 owner）。四个面：

1. **同步推送（Guide / Help Center API）**：条目发布 → 按映射表推送。结构映射（规则唯一落点 PRD §4.1）：知识库→brand、目录→Category、章节→Section、条目→Article、标签→`label_names`、仅内部→挂客服 user segment（`user_segment_id`）、英文→Article Translation（locale `en-us`）。动作三类：更新正文+labels / 创建（待过审后）/ 归档+重定向（下线条目不裸删）。推送前按可见性拆分：混合条目剥离内部段落后生成对外 HTML；英文非「已确认」整条阻断（中英同发策略建议值）。章节管理变更 → 同步器按映射更新 Zendesk 结构；目标 Section 不存在 → 同步失败并提示先修复映射，**不自动创建未经确认的 Zendesk 结构**（§7.2）。批量迁移（120+ 篇）分批推送避开限流。
2. **挖掘拉取（Support API + 在线聊天导出）**：每日批次（node-cron）增量拉取昨日邮件工单与在线聊天会话（增量导出接口按 start_time 游标推进；在线聊天会话的具体导出端点依订阅形态 Live Chat vs Messaging 而异，**列核实清单实现期核验**，PRD §0.6）。拉取失败（429/网络）→ 批次表落「失败」+ 原因，次日照常拉取，不静默缺批次。拉取内容先过**脱敏管道**（邮箱/SN/家庭 Wi-Fi 名打码，纯函数单测覆盖）再进挖掘（§4.6 PII 边界）。
3. **drift 检测（轮询为主）**：中台为每篇已同步 Article 持有「已发布内容规范化哈希」；周期扫描（建议值每小时）先比对 Article `updated_at` 缩小面、再比对正文哈希 → 检出差异写 drift 表（文章/修改方/差异摘要/时间）→ 同步中心报警 + 飞书机器人推送 → 审核员双处置：**覆盖**（推送中台版本，Zendesk 端修改丢弃留痕）或**拉回**（Zendesk 端内容作为待审来源进审核中心）。Webhook（Zendesk 事件订阅）作为降低轮询延迟的升级位，事件覆盖面实现期核验后再启用（§8.3），轮询兜底不撤。drift 与本台待发版本冲突：先处置 drift 再放行同步（§5.10 异常）。
4. **信号采集（只读）**：工单 solved/reopen/CSAT、文章投票、客服 flag 随每日批次/周期拉取落信号表（§5.1），带确定性档位；**Explore 不集成**——客服工作数据页签只做口径说明与链接指向（AC-P-19，本台不重建报表）。bot 锚点引用等待核实信号：核实通过前信号表对应行标「待核实」，不进达标判定。

### 4.5 风险与缓解

- 风险 1：Zendesk API 能力口径与订阅档位不符（在线聊天导出端点、automated resolution、segment 能力受限）→ 挖掘或信号面缩水。缓解：PRD §0.6 核实清单 5 项为实现前置；集成层四个面彼此独立，必得信号（工单/投票/flag）先行闭环（ZR-6 缓解同源）；缩水项如实回 PRD 重估不静默降级。
- 风险 2：单进程内每日批次（拉取+LLM 聚类）拖慢 API → 缓解：批次跑在低峰时段（业务时区凌晨）；内部系统白天低并发，实测拖累再拆同镜像双进程，无需队列。

## 6. AI 能力选型（用途重写：挖掘 · 切条与标签 · 翻译）

### 6.1 LLM 选型（供应商沿用，任务面改写）

> **判定：直接沿用**——Anthropic Claude 方向为既有拍板（架构建议，技术负责人确认 + DPA 签约核验前非最终决定）；**DPA + 输入零留存不训练仍为签约硬条件**（PRD §9.7，任一未就绪 = 不满足上线条件）。

| 任务 | 模型档 | 说明 |
| :--- | :--- | :--- |
| 挖掘聚类起草（每日批次会话→候选草稿：正文+标题+建议动作） | **claude-sonnet-5** | 质量敏感（草稿直接进审核队列供人审改），日频小批量 |
| 中→英翻译（段落级，政策口径敏感） | **claude-sonnet-5** | ZR-3 风险面：质量优先；**人工校验 100% 铁律兜底**，模型不是唯一防线 |
| 切条建议 / 标签建议（≤20/条）/ 两级场景归类 / 章节归类建议 | **claude-haiku-4-5-20251001** | 结构化小任务批处理，低成本低延迟 |

- 失败形态：AI 服务不可用 → 挖掘批次标失败（次日照常）、翻译失败保留上次英文并阻断同步、建议卡隐藏并明示——**人工录入/审核/发布全部照常，AI 为增强非依赖**（§7.1 状态矩阵）。无任何「LLM 兜底 LLM」设计。
- 成本：日批数十会话聚类 + 条目级翻译按需触发，量级远小于原对话运行时；随核实清单①（Zendesk 订阅成本）合并进运营成本核实项（§9.8）。

### 6.2 向量与查重（pgvector 用途降级为内部工具）

> pgvector 不再服务任何 C 端检索——三个内部用途（PRD §4.1「向量只服务本台内部」）：

1. **挖掘查重**：候选与既有条目相似度 ≥0.85（v3 定稿）→ 不新建、挂为该条目修订建议；条目间互查发现合并候选（两条目相似且互相分流）。
2. **缺口聚类**：无命中会话按语义聚类计频（三重准入①频次的分组键）。
3. **发布门禁代理评测**：以真实用户问法对本台索引做召回验证（§6.6），结果固定标注「代理指标不等于 Zendesk AI 真实表现」。

- Embedding：沿用 **fastembed `2.1.0` 进程内推理（bge-small-en-v1.5，英文模型）**，零新增外部服务。**语料语言策略（v2.0 明确）**：查重/聚类的主语料是 Zendesk 英文会话与条目**英文版本**——同为英文侧，bge-small-en 适配；英文未生成的条目以标题+标签 FTS 兜底参与查重（界面如实标注覆盖面）。**登记代价**：中文条目间纯中文语义查重不可用；若实测漏判重复建条成为真问题，升级位 = fastembed 多语模型（进程内，须实测支持清单）→ 仍不够再评估托管 Embedding（新外部服务，**须回蓝图补拍板**，门禁不变）。
- 向量状态机：未向量化/向量化中/已向量化/待重建/向量失败——内容变更置「待重建」；失败/待重建条目**不参与查重与代理评测**且界面明示（会漏判重复，§7.1）；发布前待重建须先重建（门禁提示条）。
- 索引形态：条目英文版+标签分块嵌入，HNSW；百级条目秒级全量重嵌，无分库。

### 6.3 LLM 接口层（沿用）

沿用 **Vercel AI SDK：`ai@7.0.48` + `@ai-sdk/anthropic@4.0.27`**（开源 npm 库，代码跑在自有服务器）。v1.1 对比结论（vs 直连官方 SDK / LangChain）继续成立且更贴合新任务面：`generateObject`（zod schema 约束输出）正是三类结构化任务（候选草稿/切条与标签建议/段落级译文对）的最短实现路径；provider 抽象保留供应商可切换性。不引入 Agent 框架——挖掘/翻译是**确定性批处理管道**（自有 TypeScript 编排），无自主多步推理需求。

### 6.4 AI 对话挖掘管道（每日批次 + 三重准入 + 三类候选）

```text
node-cron 每日批次（建议值，业务时区低峰）
  → Zendesk 拉取昨日会话（邮件工单 + 在线聊天，增量游标；失败→批次表标失败+原因，次日照常）
  → 脱敏（纯函数，仅脱敏摘要落库）
  → 语义聚类计频（fastembed + pgvector，英文侧）
  → 三重准入：①频次 ≥10 次/周（建议值）②查重 ≥0.85 → 挂修订不新建 ③缺口判定（对照场景覆盖）
  → Claude sonnet 档起草（generateObject：类型新增/修订/合并、标题、正文草稿、建议动作、AI 摘要）
  → 候选落库（批次表 + 候选表）→ 挖掘视图处置：起草提交审核 / 挂修订建议 / 发起合并 / 丢弃留痕
  → 全部产出经审核中心（统一过审，无直接入库路径，AC-P-09）
```

切条/标签/场景/章节归类建议（人工录入与批量导入触发，haiku 档）同为**建议态**：存独立建议位不写正文，运营逐项采纳/修改/拒绝。冷启动语料：原 G1 历史数据导出（保留项，§9.3）作聚类初始输入。

### 6.5 中→英翻译管道（人工校验 100% 铁律）

```text
中文条目（权威源）→ 触发翻译（条目工作台，按权限）
  → 段落级拆分：内部段落跳过（不翻译、不同步，标记随 TipTap 节点）
  → Claude sonnet 档逐段翻译（generateObject：段落对齐输出）→ 英文状态「待人工校验」
  → 人工逐段校验（可修正表述不得改口径，修订留痕）→「已确认」
  → 才可随同步任务推送 en-us translation →「已同步」
联动（服务端强制）：中文变更 → 英文置「待重新校验」+ 同步阻断（AC-P-04/16）
失败：保留上次英文、阻断同步、可重试；连续失败 3 次（建议值）飞书告警
```

### 6.6 发布门禁四查（代理评测取代原评测集回归）

发布 API（/review/:id/publish，含「改后发布」与回滚产生的新修订）执行链：

```text
①格式与字段完整性（标题/章节/可见性/标签已填）
②敏感信息与内部口径（内部段落已标记，剥离产物核验不含内部内容）
③英文版本状态（未「已确认」→ 阻断并展示原因）
④代理评测（本台向量检索召回验证：真实问法样本能否召回本条目；结果留痕，
  固定标注「代理指标不等于 Zendesk AI 真实表现」——§8.3 防欺骗机制）
→ 全过：状态置「已发布」+ 写同步任务（同事务收口，不存在「门禁不过但已入队」中间态）
→ 不过：阻断并展示原因，条目留在审核通过态待整改
```

原 golden set 评测集与 eval runner 留痕机制随自研运行时废止（§1.5 登记）；代理评测结果与门禁结论落审计与门禁结果面板，硬门禁语义（AC-P-12）保留。

## 7. 基础设施选型

### 7.1 部署与托管（不变）

**沿用既有拍板**：单 Docker 镜像（中台 API + 前端静态文件 + 进程内定时作业）+ Docker Compose（应用容器 + 反向代理/TLS）部署于现有云；数据库用同云托管 PostgreSQL。会话量与作业量比原方案更小，单实例结论更稳固；K8s/多实例/Serverless 仍属过度设计。管理面可达口径（控制台与文档国内可稳定访问）不变。中台为内部系统，访问面建议收敛（内网/VPN 或 IP 白名单，随反向代理配置，终稿前确认）。

### 7.2 认证与授权（重写：中台账号体系）

> 原「宿主凭证校验 + Basic Auth」随自研 C 端与旧管理台废止（§1.5）。PRD §0.5 新前置：**真实账号体系，无账号则 RBAC 与审计失去主体、不可上线**。

- **账号**：邮箱 + 密码**邀请制**（建议值，终稿前确认）——系统管理员创建用户（选角色 + 知识库范围）→ 邀请落地 → **首次登录强制改密**（AC-P-24）。密码哈希 **argon2（`argon2@0.45.1`，Argon2id 默认）**；登录接口挂 @fastify/rate-limit 防爆破。**不引入外部 IdP/OAuth**——四角色个位数账号，自建最小账号体系符合体量（铁律 8），升级触发条件：接入企业统一身份需求出现时再评估。
- **会话**：`@fastify/cookie@11.1.2` 签名 cookie（HttpOnly/Secure/SameSite=Lax）承载会话 ID → 服务端会话表（PostgreSQL）；禁用用户即删其会话行 = **会话即时失效**（AC-P-24），零缓存层依赖。
- **授权**：RBAC 权限中间件 + 四眼原则校验 + 审计拦截（§4.2）；权限矩阵 10 项×4 角色存库，仅系统管理员可改且每次写审计（AC-P-22）。
- **密钥**：Zendesk API token、LLM API key、cookie 签名密钥全部 deployment-secret，无用户可见配置界面。

### 7.3 可观测性（沿用，告警面改写）

pino `10.3.1` 结构化日志 → stdout → 云托管日志；`/healthz` 探活。**飞书机器人告警面（v2.0）**：同步失败重试耗尽 / 翻译连续失败（3 次建议值）/ drift 检出 / Zendesk 凭据失效（指向 owner）/ 挖掘批次连续失败。业务健康度即中台自有指标（§8.2：同步成功率/审核时效/挖掘消化率/drift 处置时效），由数据看板与各视图统计承载，不另建监控栈。

### 7.4 CI/CD（沿用，流水线瘦身）

GitHub Actions：PR 门禁 = typecheck（TS 7）+ lint + vitest（单测/契约测试：权限矩阵、状态机、内部段落剥离、脱敏规则）；发布 = Docker 镜像构建推送。原图遍历校验与评测回归 workflow 随自研线废止；eas-cli/EAS 发布链整体移除。

### 7.5 条件能力（按需激活）

- **定时作业清单（node-cron 进程内，全部落库留痕）**：每日挖掘批次（低峰）/ drift 扫描（每小时建议值）/ 同步失败重试（退避）/ 复核到期扫描（临期 30 天提醒、超期标红）/ 条目效果聚合刷新（周粒度）。
- **文件/富媒体（激活：条目配图）**：条目图片存持久化卷（体量小、无 C 端直传），同步时经 Zendesk 文章附件接口上传并回填对外 URL；不引入对象存储（依赖门禁不变，图量增长再回蓝图）。
- **实时通信**：未激活——SSE/WebSocket 随对话运行时废止；中台界面常规请求刷新即可。
- **支付/多端**：未激活（内部桌面 Web 单形态；移动端不适配，PRD 桌面 1280+）。
- **界面语言机制**：zh-CN 语言资源（§3.2）；后置多语言 = 加资源文件。

### 8.2 第一周脚手架建议（MVP 范围 · v2.0 更新）

1. Monorepo 收敛为三包（pnpm workspaces：`server` / `web` / `contracts`），TS 7 strict 统一配置；原 `app-rn` 包不再创建
2. `contracts` 先行：zod 定义条目/章节/版本 schema、四条状态机流转表、10 项权限点枚举、API 请求响应类型（前后端共享）
3. `server`：Fastify 起服务 + /healthz + pino；Drizzle 建核心表域（知识/版本/翻译/同步/挖掘/信号/治理七域）+ 迁移
4. **账号体系与 RBAC 骨架**：argon2 + cookie 会话 + 权限中间件 + 审计拦截——先于业务路由落地（全部写 API 都要过它）
5. **Zendesk 连通冒烟**：API token 配通，跑通「建测试 Article → 更新 → 归档」与「增量拉取昨日工单」两条最小链路，验证核实清单⑤（凭证权限）并实测限流表现
6. 条目编辑最小闭环：TipTap 编辑器（含内部段落节点）→ 保存草稿 → 提交审核 → 审核通过 → 门禁四查 → 同步任务推送 Zendesk（统一过审链路端到端）
7. 翻译管道：段落拆分（内部段落跳过）→ sonnet 翻译 → 待校验 → 确认 → en-us 同步；中文变更联动置态
8. 批量导入：飞书导出文件解析 → 审核队列（来源「批量导入」）；haiku 切条/标签/归类建议态
9. 挖掘批次骨架：node-cron 每日批次 → 拉取+脱敏+聚类+三重准入+起草 → 候选落库 → 挖掘视图处置
10. drift 检测：哈希基准落库 + 每小时比对 + 报警与双处置；GitHub Actions PR 门禁（typecheck/lint/vitest）

### 8.5 技术负责人的最终结论

#### 是否可以立即开工

**有条件开工**：§8.2 第 1–4 步（脚手架 + 账号 RBAC + 契约）现在即可动手；第 5 步 Zendesk 连通冒烟依赖 API 凭据到位（committed，owner=内部技术团队），应与核实清单 5 项并行推进——**冒烟结果本身就是核实清单③⑤的最好证据**。LLM 供应商为架构建议，技术负责人确认 + DPA 核验通过后转为最终决定。

#### 最大的技术不确定性

> 不是任何框架选型，而是 **Zendesk API 能力口径与订阅档位的实际匹配度**（在线聊天会话导出形态、bot 引用信号可得性、segment 与 translation 能力边界）——它决定挖掘与信号闭环的成色。第一周先跑通「建 Article→改→归档」与「拉昨日工单」两条真实 API 链路拿到事实，比任何架构讨论都值钱；必得信号（工单/投票/flag）保证最坏情况下闭环仍然成立。

#### 现在最不应该做的事

> ①给已废止的自研对话线写任何新代码（RN 容器、SSE 对话流、拒答 pipeline）——D-10 已拍板，每一行都是沉没成本；②引入 Zendesk SDK 封装库、Agent 框架、Redis、消息队列、独立搜索引擎、外部 IdP 中的任何一个——本系统的确定性管道与个位数账号体量都不需要；③在 Zendesk 端直接手工维护内容「先顶一阵」——这正是 drift 本身，权威源纪律从第一篇迁移文章起就必须成立。
