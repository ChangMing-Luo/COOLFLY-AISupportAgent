## 0. PRD 类型判定

- 类型：🏗 功能型（在现有 App 内重建/升级智能客服能力，重建 vs 升级见决策 0）

## 1. 解决思路（用户视角）

用户在 COOLFLY App 里遇到装不上、连不上、配不了对、会员疑问时，**不用在"迷宫 App"里找客服**——设备掉线、配对失败、扫码失败的错误提示旁边就有"Get help"，一键进入对话并自动带上故障现场。进来后**不用打字也能求助**：首屏就是高频问题按钮（Setup / Won't connect / Pairing failed / Membership），点按直接进入一步一屏的分步引导；也可以自由输入，AI 基于升级后的知识库准确回答、主动追问澄清。它**答不准时不硬撑**——检索不到可靠依据就明说"这个我没把握"，主动给转人工；转人工时自动带上会话摘要 + SN + 设备型号（用户可见、可补充），并明确告知回复渠道与预计时间，**不让用户对着聊天窗干等一个不会来的回复**。

第一阶段的定位是诚实的：**体验补课到及格线（答得准 + 转得顺 + 找得到门 + 出得去门），同时为第二阶段攒数据与回流体系**。差异化王牌（AI + 设备诊断，全品类无人做到）留在第二阶段，本期不做，但接口争取从现在并行启动。

## 4. 功能清单

优先级用"必做 / 应做 / 可做"。编号沿用需求 ID 注册表，F08 为本版新增。

| 编号 | 功能 | 优先级 | 一句话说明 | 对应用户痛点 |
|------|------|--------|-----------|-------------|
| F01 | 智能问答会话 | 必做 | 基于知识库（RAG）的英文多轮对话，主动追问澄清；**三层拒答策略兜底**（见 §5），没把握就承认并引导转人工，不编答案、不硬拦截；首屏零打字路径，自由文本先意图分类再路由 | 高频问题解决慢、口径不一；中老年用户面对空白输入框不知道打什么 |
| F02 | 引导式排障 | 必做 | 安装/联网/配对三大场景结构化分步引导（含 2.4GHz/双频路由等品类高发分支）；卡片化、进度持久化、按钮推进 | 配对卡死无分支指引；"掉线了却没有任何指引"（自身差评原话） |
| F03 | 人机衔接 | 必做 | 一键转人工带摘要+SN+型号（用户可见可补充）；**回复通路分层承诺**：目标态=人工回复桥接回同一会话流+push；若 G3 查证现有渠道无写回接口，底线=转人工时明确告知回复渠道与预计时限；转人工三件套（确认+可离开+超时安抚） | 竞品最大差评源"复读机客服"；用户对着聊天窗干等不会来的回复 |
| F04 | 会话反馈（两层） | 必做 | 单条回答 👍/👎（点踩可选原因：不相关/看不懂/试了没用）+ 会话结束轻量评分；结束判定三类：确认解决/转人工完成/静默 30 分钟超时（静默流失不追弹） | 被答错的用户直接弃聊，走不到会话结束评分；负样本漏掉则知识库改进方向失真 |
| F05 | 知识库升级与回流闭环 | 应做 | 高频条目前置改造（排在 G1 之后）；回流四触发源：①检索无命中/拒答 ②点踩或"未解决"标记 ③转人工会话 ④48h 复问，统一落待补清单周度导出 | 知识库不完善直接拖累回答质量（A-001 第一命门） |
| F06 | 效果度量与预警 | 必做 | 双口径解决率（宽：未转人工+48h 内无任何新会话；严：宽口径∩F04 显式确认已解决）；转人工绝对量周监控+容量预警线（3 人团队月处理上限的 80% 触发预警推送企业家）；语言分布；退货归因月报 | 没有度量无法验收；单口径会把"放弃去退货"算成功；容量预警不做，销量翻倍时客服被淹没 |
| F07 | 多语言能力预留 | 可做 | 收敛为两条可检查约束：面向用户的文案与 prompt 模板不硬编码语言；知识条目带语言字段。其余不做 | 非英语咨询占比 >15% 时提前（占比由 F06 语言分布字段实测，A-002 触发条件从此有传感器） |
| F08 | 入口与场景化触达 | 必做 | 固定一级入口 + 错误状态处"Get help"按钮，一键进对话并自动携带故障上下文（设备型号/错误类型） | App 被差评"labyrinthian maze"，最该被服务的人走不到服务门口 |

不做（边界重申）：设备状态诊断与自动解决方案（第二阶段王牌）；客服工作台（未来 Zendesk）；邮箱/社媒/官网渠道改造；硬拦截降转人工率；客服容量/排班方案（产品只交付预警数据，容量应对是业务侧决策）。

## 5. 技术形态与状态约束（工程评审要求明确，供 PRD/设计消化）

- **RAG + 三层拒答**：①检索相关度低于阈值 → 走"承认不会 + 转人工"分支；②回答必须引用命中知识条目，无引用即拒答；③敏感/超范围类目硬规则拒答。拒答准确率/幻觉率用离线评测集验收。
- **排障形态**：三大场景用结构化流程（步骤+分支显式建模，即知识库改造产出格式）；LLM 负责意图识别、上下文衔接与话术生成；"无死胡同"用图遍历自动验证。
- **系统关系与灰度**：新系统为服务端对话引擎（重建 vs 升级现有待决策 0），App 端复用现有客服入口 UI 微调；灰度分流由服务端按**用户维度**分桶 + 远程配置开关控制，不依赖客户端发版；同一用户始终见同一版本，两版入口文案一致。
- **知识库接入**：飞书文档导出 + 定期增量重建索引（不做请求时实时调飞书），文档变更到 AI 生效 ≤24h；飞书 API 权限申请登记前置能力表。
- **状态矩阵（任何故障态不出死屏）**：AI 流式响应打字指示；响应超时（>N 秒）重试提示；LLM 超时/限流/不可用 → 降级直达转人工入口 + 相关排障文章链接；手机离线本地提示。
- **埋点**：事件 schema（会话开始/结束、转人工、评分、解决标记、语言）与功能同步交付、同步验收——晚于功能上线则灰度对比数据作废。
- **设计一致性与无障碍（NFR）**：沿用现有 App 设计规范，聊天交互遵循 iOS/Android 平台惯例（类 iMessage）不发明新模式；系统字体缩放不破版、关键按钮 ≥44pt、基础 VoiceOver 走查通过。

## 6. 核心用户旅程

**旅程 A · 自助解决（主路径，目标占高频类 60%）**
北美用户 Sarah 刚收到喂鸟器，配对到一半卡住，App 配对失败页直接显示"Get help" → 点进去，首屏就有"Pairing failed"按钮，不用打字 → 进入分步引导，第一步问"你连的是 2.4GHz 还是 5GHz？"配一张路由器设置示意图 → Sarah 切出 App 去改路由器设置，回来后引导自动恢复到当前步骤 → 点"Done"，配对成功 → AI 确认解决，弹出轻量评分 → 全程 8 分钟，零打字也零等待。

**旅程 B · 转人工兜底（不干等、不复述、知道去哪等）**
用户 Mike 扫码后一直绑定失败，引导两轮自查仍失败 → AI 主动说"这个情况需要人工用你的设备序列号定位"，展示将发给客服的摘要（已试过：重启、重扫码、确认 2.4GHz + SN + 型号），Mike 补充一句"绑定时 App 闪退过一次" → 确认转人工，界面显示"已转接，预计 X 小时内回复；你可以关闭页面，回复会通知你" → 人工客服按 SOP 首条回复即引用摘要直奔问题 → Mike 全程零复述，也没有对着屏幕干等。

**旅程 C · 情绪崩溃路径（退货率的直接来源）**
用户折腾 2 小时后带着怒气打出"this thing is garbage, I want a refund" → AI 不追问技术细节，先共情，直接给两个出口：转人工（优先接入）+ 退货政策入口 → 若用户愿意，再提供"最后试一步"的最短排障路径。验收点：愤怒表达触发的会话绝不进入多轮技术追问。

## 7. 指标与验收口径

| 指标 | 口径 | 目标 |
|------|------|------|
| 自助解决率（宽口径，对外可比） | 未转人工 且 48h 内该用户无任何新客服会话 | 高频类 60% / 整体 50%（3 个月，G1 后校准） |
| 自助解决率（严口径，验收用） | 宽口径 ∩ F04 显式确认"已解决"（未答复按保守折算） | 双档：目标 60%（高频类）/ 底线 45% |
| 沉默放弃率预警 | 宽严口径差值，进周报 | 持续扩大即触发口径复查 |
| 解决时长 / 转人工率 / 转人工绝对量 | 自动统计；绝对量配容量预警线（3 人月上限 80% 触发） | 首响不劣于现状；预警推送企业家 |
| 退货归因 | 月度看板，退货原因码"装不上/连不上/太复杂"单列 | 3 个月验收项，与解决率同级 |
| 交叉校验 | 解决率 × 满意度趋势 × 退货月度趋势，三者背离即触发口径复查 | — |

**切采购扳机（现在写死）**：高频类解决率连续 2 个月低于底线 45%，且回流机制已正常运转（排除运营缺位因素），触发 Fin for Zendesk（$49/月）小规模试点复评。
**90 天价值兑现检查点**：上线 3 个月，用真实数据回填价值账三块（退货归因/人力容量/解决率），向企业家 15 分钟汇报——假设换成事实的固定仪式。

## 9. 关键决策点（待企业家拍板）

### 决策 0（新增）：现有 AI 客服处置——重建服务端对话引擎，还是升级现有系统？

前置：G1 基线分析 + G2 系统盘点完成后拍板。
- **选项 A · 重建服务端引擎（App 端复用入口）**：好处：拒答机制、结构化排障、度量埋点从零建到位。代价：最大工程投入；若旧系统本可修补，即机会成本黑洞。
- **选项 B · 升级现有系统 + 知识库工程为主**：好处：可能 1/3 成本拿 70% 价值。代价：受旧架构约束，拒答/排障/埋点上限未知。
- **我的建议**：倾向 A（现有系统缺的不只是知识库这箱"油"，拒答/排障/埋点这半个引擎同样不存在）；但盘点若显示旧系统可插拔改造，转 B。

### 决策 1：直接切换 vs 灰度并行（内容已修订）

- 灰度机制修订为：服务端按用户分桶 + 远程开关，不依赖发版（"2 周走完"因此才成立）。
- 旧系统基线诚实化：二选一——灰度前给旧系统补最小埋点先跑 2 周，或承认基线来自 G1 历史数据估算口径；不许诺采不到的对比数据。
- 灰度值守分工（谁看数据、谁抽检、每周几小时）随本决策同步确认。
- **我的建议**：维持选 B（灰度），2 周目标不变。

### 决策 2：知识库改造顺序（内容已修订）

- 维持建议：A 的最小版——三大高频场景条目上线前改造，其余走回流补齐。
- 修订：改造清单排序必须在 G1 数据分析之后（若会员/账号类占比意外高，清单跟着改）；改造完成标准=schema 校验 + 评测集命中率 ≥80%。

### 决策 3：转人工落到现有渠道 vs 提前接 Zendesk（内容已修订）

- 维持建议：选 A（沿用现有渠道），但前提=G3 查证渠道具备消息写入能力；无接口则按最低可行形态（结构化消息推送工作群/邮件模板）交付，并如实降级 F03 回复通路承诺层级。
- 摘要按最小交接数据契约交付，未来迁 Zendesk 时即字段映射底稿，"预留"不再是一句空话。

### 待决 P2：运营与投入承诺实名化（本版新增，最高优先）

三个运营岗 + 技术投入必须落到实名与工时，否则机制空转、宁可缩范围：
①知识库内容运营（前置改造人日 + 每周消化 Top10 回流）②退货归因月报 owner ③客服 SOP 培训与抽检 owner（建议企业家团队）④技术团队上线后 6 个月每月人日承诺。
选项：现有人员兼任（零现金成本，风险=没人真干）vs 新增 0.5 人力（费用记入成本账）。
**我的建议**：知识库运营岗必须有实名 owner + 周工时数字；给不出就砍 F05 回流承诺并下调目标。

### 待决 P4：价值账口径修正确认

## 12. 风险与缓解（方案级，扩充）
