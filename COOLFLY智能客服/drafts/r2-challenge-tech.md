**T1 残留问题 1｜"引用即可信"是工程上不成立的等式。** 三层拒答第②层写"回答必须引用命中知识条目，无引用即拒答"。强制引用在工程上很好做，但 LLM 完全可以**引用了正确文档、答案却超出该文档内容**（引用 ≠ 忠实）。第②层照现在的写法只能拦"零引用"，拦不住"挂着引用编内容"——而后者才是幻觉的主形态。评测集里必须加"引用存在但答案不忠实"的陷阱题型，且验收指标要区分"拒答准确率"与"有引用回答的忠实率"，否则第②层是纸防线。

**T1 残留问题 2｜拒答层与意图路由的执行顺序未定义，且和旅程 C 直接冲突。** "this thing is garbage, I want a refund" 这句话检索相关度必然低于阈值——按第①层规则应触发"承认不会 + 转人工"话术；但旅程 C 的验收点要求它走共情分支。同理，问候语、纯情绪表达、追问澄清的短回复，都会被第①层误伤。必须写明：**意图分类在拒答层之前执行**，情绪类/闲聊类/流程推进类意图豁免检索阈值判定，只有"知识求解类"意图才进三层拒答。一行架构顺序的事，不写清楚 PRD 阶段必然做错。

## 2. 对其他三方的 challenge

### 对设计（及 PM 对 D2 的采纳）：G3 查证清单查错了方向的一半

D2 的分层承诺方向对，但注意 F03 目标态需要的是**双向**通路：正向（摘要写入客服渠道）+ 反向（客服回复写回 App 会话流 + push + 会话 ID 关联）。G3 的查证清单只写了"有无消息写入接口"——这是正向。反向通路的成本远大于正向：客服在旧渠道里回复时如何带上会话 ID、写回 App 用什么接口、push 基建是否现成，一项都没进查证清单。**风险：G3 查证"通过"，结果只证明了正向可行，F03 层级拍板时才发现目标态照样做不了。** 修法：G3 清单拆成正向/反向两栏分别查证，反向查不到接口则 F03 目标态在本期直接降级为底线态，不留"争取一下"的模糊区。

### 对商业 B1（及 PM 采纳的"退货归因看板"）：这个度量在技术上可能根本采不到

看板作为交付物写进了 V0.5，但**数据链路可行性从未被查证**：退货发生在 Amazon/渠道侧，不在 App 里。"退货原因码口径上线前锁定（装不上/连不上/太复杂单列）"——Amazon 的退货原因码是平台固定枚举，COOLFLY 无权新增自定义码；而"退货用户是否咨询过"的归因需要 SN↔订单↔App 用户三方映射，这条映射链是否存在没人查过。商业评审要求"与解决率同级验收"，PM 照单全收，但**谁都没问一句这数据从哪来**。修法：前置门槛加一条 G4——退货数据源盘点（渠道原因码枚举、SN-订单-用户关联能力、数据拉取方式与负责人）；查证不通过，看板降级为"渠道原因码粗分类 + 月度趋势"，B1 的验收承诺同步降级，别签一张兑现不了的支票。

### 对商业 B13（切采购扳机）：$49/月是个虚假锚点

"Fin for Zendesk（$49/月）小规模试点"——Fin for Zendesk 的前提是**有 Zendesk 工作台和座席**，而本期边界明确"客服工作台（未来 Zendesk）不做"。扳机真被触发时，实际动作是"先迁工作台再试 Fin"，成本量级远超 $49/月。扳机条件本身写得好（连续 2 个月低于 45% 且回流正常运转），但把 $49 写进方案会让企业家对"切采购"的代价产生数量级误判。修法：扳机动作改写为"触发采购路线复评（含 Zendesk 工作台迁移成本评估）"，删掉 $49 锚点。

### 对战略 S2 / 决策 0：G2 的"≥3 条可验证缺陷"是个偏向性标准

任何跑了几年的旧系统都能挑出 3 条缺陷——这个完成标准天然导向选 A（重建），等于用一个必然满足的条件给倾向性结论盖章。工程上真正决定 A/B 的不是缺陷数量，而是**旧系统对话流水线是否可插拔**：能否在其中插入检索阈值判断（拒答第①层）、能否挂埋点钩子（F06）、排障流程引擎能否外挂。修法：G2 产出改为"三个集成点的可插拔性逐项判定（可插/需改造/不可插）"，缺陷清单只作背景材料。附带一句对战略 S5 采纳的提醒：决策 1 里"给旧系统补最小埋点跑 2 周"这条路的可行性本身依赖 G2 结论——若旧系统代码归属不清或无人敢动，这个选项是空的，二选一会退化成只剩"承认估算口径"一条。

## 3. V0.5 新增内容的增量问题（新问题，不翻旧账）

| # | 位置 | 问题 |
|---|------|------|
| N1 | F08 + §5 灰度 | **F08 把发版依赖带回来了，且污染灰度对比。** 错误状态处"Get help"按钮 + 携带故障上下文是客户端改动，必须发版 + 商店审核 + 等升级率——"灰度 2 周不依赖发版"只对引擎成立，对 F08 不成立。更隐蔽的是流量构成偏差：从故障现场进来的用户问题更难、情绪更差，新系统的解决率会被这批增量流量**结构性拉低**，与旧系统（只有固定入口流量）直接对比是不公平对比。修法：①F08 与引擎灰度解耦为两条上线线，写明 F08 覆盖率随升级率爬坡；②埋点 schema 增加 entry_source（固定入口/错误态入口）与 app_version 字段，解决率按入口分层统计，否则 60% 目标和灰度结论都会被质疑。 |
| N2 | F08 完成标准 | "自动携带故障上下文（设备型号/错误类型）"隐含前提：现有客户端错误态有结构化错误码可取。App 被骂"迷宫"，错误提示很可能是散落的文案而非统一错误码体系。G2 盘点应加一项：客户端错误态清单与结构化程度——没有错误码，F08 的"携带上下文"就要先做错误码治理，工作量完全不同。 |
| N3 | F02 持久化 × F04 结束判定 × F06 口径 | 三者存在未定义的交互：会话静默 30 分钟判"结束"，但 F02 鼓励用户切出去改路由器再回来**恢复同一会话**。用户第 26 小时回到持久化会话继续挣扎——这算"复问"吗？按现口径"无任何**新**会话"，恢复旧会话不计新会话，宽口径会把这个未解决用户算成功。修法：定义"已判结束的会话被重新激活并产生用户消息 = 等价于新会话"，一句话堵住口径漏洞。 |
| N4 | 交付物·离线评测集 | 评测集的构建与维护 owner 不在 P2 清单里（P2 只列了知识库运营/退货月报/SOP 抽检/技术调优）。每次知识库变更跑回归意味着评测集要随知识库同步更新，这是持续性工作，不是一次性交付。建议并入 P2 第④项技术团队承诺，明确"评测集维护"在月人日之内。 |

## 4. 我的立场

**⚠️ 带条件可以进入 V1。** V0.5 相比 V0 的工程成熟度是质变（拒答有机制、排障有形态、口径可计算、灰度不赌发版），没有推翻性缺陷。但四个条件必须在 V1 写作中消化，全部是规格级修正、不是架构返工：

1. 拒答第②层补"引用忠实性"验收 + 意图分类先于拒答层的执行顺序（§1）；
2. F08 与引擎灰度解耦，埋点加 entry_source/app_version，解决率分入口统计（N1）；
3. G3 查证拆正向/反向双栏，前置门槛新增 G4 退货数据源盘点（§2）；
4. 会话重激活的复问口径补丁（N3）。

条件 2、3 若不满足，F06 的灰度结论和 B1 的验收承诺会在上线后被自己的数据打脸——那时修比现在贵十倍。
