## 2. 对其他三方的 challenge

### 2.1 challenge 工程：三层拒答会不会把体验做成"动不动就转人工"？

**C1（严重）｜拒答规则②会误杀一半正常对话。** "回答必须引用命中知识条目，无引用即拒答"——但一场好的多轮对话里大量话语天然不引用知识条目：主动追问澄清（F01 明写要做）、旅程 C 的共情话术、"我来帮你看看"的过程性衔接、对用户补充信息的确认复述。这些全都"无引用"。规则②按字面执行，AI 每说一句非答案的话都算违规，要么机制形同虚设，要么对话被阉割成"检索命中→贴答案，否则→转人工"的一问一答机——这恰好是竞品被骂"do-loop 复读机"的形态。**修法**：规则②的适用范围必须限定为"对用户问题给出事实性解答的消息"，追问/共情/流程话术显式豁免，豁免类别写进评测集用陷阱题验证不被滥用。

**C2（严重）｜评测集只测"拒答准确率/幻觉率"，没有拒答率上限——AI 靠全拒答就能刷满分。** 三层拒答的验收指标全是"该拒的拒了没有"，没有一个指标管"不该拒的拒了多少"。阈值调保守一点，拒答准确率 100%、幻觉率 0%，评测全绿，用户体验是每两句话被塞一次"这个我没把握，帮你转人工"。转人工率暴涨还会直接撞 B5 的容量预警线——工程指标漂亮、商业和体验一起爆。**修法**：评测集加两个反向指标：高频问题误拒率上限（该答出的 Top 问题被拒答的比例）+ 单会话连续拒答次数上限（连续 2 次拒答必须直接给转人工大按钮，不许第三次"我没把握"）。

**C3（严重）｜"App 端复用现有入口 UI 微调、灰度不依赖发版"——这句话对 F08 不成立。** 服务端分桶解决的是对话引擎切换，但 F08 的核心是客户端改动：设备 offline/配对失败/扫码失败页面新增 Get help 按钮、对话首屏新增零打字按钮组、F02 步骤卡片 UI——这些都要发版，iOS 审核和用户升级率照样卡着（T2 自己论证过的约束，回应时只解了分流、没解入口）。后果：灰度期里未升级 App 的用户根本看不到新入口，"入口触达"这一环在灰度对比数据里是缺失的，而 D1/F08 恰恰是我 Round 1 的第一致命项。**修法**：灰度计划里把"客户端发版节奏 + 版本覆盖率"单列一行；灰度对比结论必须区分"引擎效果"（服务端可控）与"入口效果"（受版本覆盖率污染），2 周走完的承诺只对前者有效。

### 2.2 challenge 商业：度量的手别伸进对话里

**C4（严重）｜F02 步骤卡片上按钮堆叠：Done / It didn't work / 👍 / 👎 同屏。** B7+D7 合并后的方案让每条回答带 👍/👎，但 F02 的步骤卡片自己已有"Done / It didn't work"两个大按钮。目标用户是中老年，一张卡片上出现 4 个可点目标，"It didn't work"和 👎 语义还重叠——用户分不清点哪个，度量数据也会互相污染（点了 It didn't work 还要不要再点踩？）。**修法**：引导流卡片内不显示消息级 👍/👎，"It didn't work"本身就是该步骤的负反馈信号、直接入 F05 回流；👍/👎 只挂在 F01 自由问答的回答消息上。埋点服务于体验，不能反过来在最需要减负的界面上加按钮。

**C5（一般）｜容量预警线推给企业家没问题，但用户侧的"预计 X 小时"必须跟着容量走。** B5 驳回"容量方案附录"我不挑战——加人排班确实是业务侧决策。但转人工三件套承诺"预计 X 小时内回复"，如果 X 是写死的数（按现状 1–2 小时），旺季容量被打爆时它就是当着用户面撒谎——预期落差比等待本身更伤（我 Round 1 D4 的原话）。**修法**：F03 完成标准补一句：预计响应时间取近期实际首响的滚动值或分档展示（如"通常 2 小时内，当前咨询较多可能延长"），禁止硬编码。

### 2.3 challenge 战略：前置门槛别把体验补课拖成无限期

**C6（严重）｜G1–G3 + 决策 0 没有时限，而现有的烂体验每天都在产生差评。** S1"先导出数据再投工程"我完全支持——但战略自己说这是"花一天能消除的不确定性"，现在它变成了 G1+G2+G3 三项动作 + 决策 0 拍板的串行链，每一项都没有截止日期。链条每多拖一周，"labyrinthian maze"里就多一批走不到客服门口的用户。用户价值的延迟本身就是成本，这笔账战略视角不能只算工程投入那一边。**修法**：给 G1–G3 定死时限（建议合计 ≤2 周）；到期未完成的项按"估算口径 + 如实标注"降级推进（G1 已有此机制，G2/G3 补上），不许门槛变闸门。

**C7（严重）｜决策 0 若选 B（升级现有），用户可见的验收标准一条都不许降级。** 选项 B 的诱惑是"1/3 成本拿 70% 价值"，但 V0.5 自己写了 B 的代价是"拒答/排障/埋点上限未知"——翻译成体验语言：三件套可能做不了、卡片化排障可能落不了地、状态矩阵可能补不齐。如果丢掉的 30% 全是这些，那丢掉的恰好是本期定位"体验补课到及格线"的及格线本身。**修法**：把 F01–F08 的用户可见完成标准声明为"形态无关的硬验收"——无论 A/B，拒答话术、三件套、卡片化、状态矩阵、入口触达必须原样成立；选 B 后达不成的项要逐条摆回企业家桌面重新拍，不许在实现过程中静默缩水。

## 4. 我的立场

**带条件可以进入 V1。**

理由：我 Round 1 最担心的"两端归零"（入口发现 + 回复通路）已被 F08 和 F03 分层承诺正面接住，中老年零打字路径、状态矩阵、无障碍 NFR 全部落进了可验收的条款——V0.5 不是话术修补，是结构性补课。剩余问题都是文档级修订，不动方案骨架。

**进入 V1 的三个条件（不满足则体验会在已修好的地方重新裂开）**：

1. **修 N1**：三件套承诺随 G3 结果分层，底线态不许出现"回复会通知你"这类兑现不了的话；push 权限请求时机写进 F03。
2. **修 N2**：排障进行中会话豁免 30 分钟静默结束、返回接续原会话 ID，F06 口径同步豁免——这条同时是体验问题和指标正确性问题。
3. **回应 C3**：F08 入口的客户端发版依赖写进灰度计划，灰度对比结论区分引擎效果与入口覆盖率，别让"2 周不依赖发版"这句话覆盖它覆盖不了的东西。

另请 Lead PM 在 V1 处理 C1/C2（拒答豁免范围 + 误拒率/连续拒答上限入评测集）——拒答机制是工程 Round 1 的最大贡献，但只有加上这两条反向约束，它才不会把"答得准"修成"答得少"。
